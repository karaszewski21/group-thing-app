TL;DR

  • categories becomes a tree (parent_id, external_id), seeded once from a reviewed Polish Vinted JSON snapshot. The legacy flat catalog is wiped, products can only use leaf categories, and admins manage the tree without reparenting.
  • One shared CategoryTreePicker (ModalSheet, search with full paths + drill-down) replaces every "Typ" <select>. The add-item form ends with three buttons: Oddam / Zamienię / Wersja robocza.
  • Items get inventory_items.listing_status (DRAFT/ACTIVE), kept in lockstep with the item_listing_preferences row. The mode is set atomically at registration, and the backend enforces the 10-gift limit.
  • The photo-moderation listing gate and withdraw-on-upload/re-point are removed. Needed items become plain names (no product link), and existing needed items and pledges are wiped.

Key Decisions

DecisionRationale
listing_status / ItemListingStatus, not statusInventoryBalance.status and ItemDetailsResponse.status already exist, so a bare status would be ambiguous.
Enum holds only DRAFT/ACTIVE; VARCHAR(20)MODERATION/REJECTED can be added later without a type change. No speculative enum members.
Status mirrors the pref row (ACTIVE ⇔ a pref row exists)Listing reads stay pref-driven and unchanged, the smallest regression surface.
Mode set at registration (listing_mode on POST /api/inventory-items), before photo uploadsThe "after uploads" order only existed for withdraw-on-upload. Atomic creation means a gift-limit 409 persists nothing: the form keeps its data and there is no duplicate draft.
Implicit Enter submission does nothing; buttons are type="button"The visibility outcome is always an explicit choice.
Path labels and search run client-side over cached useCategoriesNo new endpoint, no response key-set churn.
Leaf-only through require_leaf_category (409 non-leaf, 404 unknown)One check reused by product create, update and resolve.
uq_categories_parent_id_name + partial uq_categories_root_name; business key (parent_id, name)Vinted repeats names under different parents.
Wipe every pre-existing category with its products and dependentsA leftover flat root would break the taxonomy. This is dev data.
Needed-item DTOs expose name; MyPledgeResponse.item_name; outbox key stays product_nameThe value is no longer a product name, and the key-set tests change anyway. Queued outbox events stay valid.
Needed-item names are text-moderated like product namesThey render on the anonymous public term page.
Separate schema and data revisions 0064–0069, each with a round-trip testPer migrations.md.
Admin tree uses nested lists + disclosure buttons, not role="tree"Avoids a roving-tabindex model that is not required here. The mockup layout is kept.

Scope

In scope
  • Category tree schema, Vinted JSON seed, legacy wipe
  • Leaf-only product categories
  • Admin tree: create root/child, rename, sibling reorder, delete with 409s
  • listing_status DRAFT/ACTIVE in lockstep with prefs; mode at registration
  • Backend gift limit (10) on register and mode change
  • Removal of the photo-moderation listing gate and withdraw paths
  • Needed items as plain names; existing data wiped
  • Shared CategoryTreePicker everywhere; three add-item buttons
Out of scope
  • Renaming the needed-items entity
  • MODERATION/REJECTED statuses; other moderation changes
  • Reparenting, drag-and-drop, subtree product filter
  • Runtime Vinted fetch or sync
  • Restoring legacy products or Spaces objects; client gift pre-check on the add page
  • Edits to the user's uncommitted files
Goal: Owners classify each item with a leaf from the Polish Vinted category tree and, in the same step, decide whether it is offered (Oddam/Zamienię) or kept as a draft. Category data and listing semantics stay consistent across the backend, the admin tooling and the term's needed list.

User Stories

Owner (add)
Pick "Kategoria" from a searchable Vinted tree, so the item is classified the way I know from Vinted.
Owner (add)
Finish with Oddam, Zamienię or Wersja robocza, and decide visibility immediately.
Owner (edit)
Change the category with the same picker and see whether the item is a draft.
Owner (moderation)
Still offer my item while its photos are in moderation.
Organizer
List needed items by plain name, without a category.
Admin
Manage the category tree, with clear errors when an operation is not allowed.

Create-item flow and listing invariant

Frontend: profile → personal inventory → POST /api/products/resolve (leaf check) → POST /api/inventory-items {…, listing_mode} → photo uploads → navigate to /product/{id}.

Backend: register_item (status from the mode) → flush → groups hook (gift-limit count → insert pref) → a single commit. On an exception nothing persists.

Pref existence stays the only input to listing reads, and none of them change. listing_status is a mirror written in the same transaction as each pref insert or delete: register, set/clear, confirm, backfill.

Cross-module boundaries, authorization, docs
  • Groups writes listing_status only through circulation_bridge.
  • Product checks leaves through app.category.service.
  • No new relationship(); tree assembly is client-side.
  • No new routes, so AUTHORIZATION_MATRIX is unchanged (GET READ, mutations ADMIN).
  • Update .maister/docs/project/architecture.md: remove the "Publish gate and withdraw" section and the cleanup script; add notes on listing_status lockstep and the category tree.

Success Criteria

  • After upgrade head, only the reviewed Vinted tree exists: 9 ordered roots, no legacy rows. A downgrade to 0063 followed by upgrade head succeeds.
  • Non-leaf product writes return 409, and pickers allow only leaves (except the admin parent picker).
  • The three buttons create ACTIVE+GIFT / ACTIVE+SWAP / DRAFT. An 11th GIFT returns 409 and persists nothing.
  • ACTIVE ⇔ a pref row exists, after register, set, clear, confirm and backfill.
  • A pending photo upload or re-point never removes a pref, and PUT while photos are pending returns 200.
  • Needed items work end to end by name.
  • The picker meets the a11y rules: keyboard selection works, Esc in search does not close the sheet, focus returns to the trigger.
  • New and changed tests pass. mypy and ruff are no worse than the HEAD baseline. tsc is clean except the blocked AppPage.test.tsx.
