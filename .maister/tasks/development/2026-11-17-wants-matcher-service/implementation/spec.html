TL;DR

„Szukam” matching moves out of the FastAPI process into a new Python app src/matcher (own compose service, same DB, login aj). It talks raw SQL to a DB contract added by amending migration 0099: the text functions words_pl/stem_word_pl/stem_pl/stem_query_pl (stop-words skipped, every inner call public.-qualified), generated stem columns, match_requested_at with a NOTIFY trigger, want_matches.tier/missing_words, and the inlinable views group_holdings, private_group_peers, matchable_listings.

MATCH requires every (non-stop) want word in the item name, by stemmed prefix or per-word word_similarity ≥ 0.65. SUGGESTION covers wants of ≥3 such words with exactly one missing, ≤10 per want, never belled.

The backend keeps the API and the bell rows (a wants.bells_due outbox handler that re-checks visibility). Writes only flag a want; edits lock the want row first. The frontend polls a pending state and adds „Może Cię zainteresuje”, per the five binding mockups.

Key Decisions
  • Amend 0099, no 0100. Old-0099 DBs run downgrade 0098 + upgrade head from the new image (deletes all wants, matches, WANT_* notifications); acceptable only while 0099 is unreleased.
  • (C1) Shape-tolerant downgrade: new-only objects dropped with IF EXISTS (views, functions) or with their tables (trigger, new indexes, checks, generated columns); old-shape downgrade test.
  • (M1) Order: WANT_* notifications → views matchable_listings, private_group_peers, group_holdings → tables → functions wants_notify_match_requested(), stem_query_pl, stem_pl, stem_word_pl, words_pl.
  • (H1) Inlinable visibility: no scalar function; PUBLIC branch at the call site, PRIVATE branch EXISTS over view private_group_peers (single named definition for the parity test); can_see_listing dropped.
  • (H2) PRIVATE rule copies membership.py + visibility.py exactly; bell handler re-checks every pair through reads.visible_matches.
  • (H3) update_want locks the want FOR NO KEY UPDATE before deleting pairs and flagging.
  • (H4) In-memory backoff map per matcher process (60 s doubling to 15 min, cleared on success); claim skips backing-off ids.
  • (H5) Every non-pg_catalog call in contract bodies is public.-qualified; empty-search_path test.
  • (M3, user decision) 24 stop-words skipped by words_pl: a, albo, ani, bez, dla, do, i, ku, lub, na, nad, o, od, oraz, po, pod, przez, przy, u, w, we, z, za, ze; stop-words-only name → 400.
  • One tokenizer, aligned by construction (L1): words_pl on the raw name; stem_pl maps stem_word_pl (folds internally) over the same array.
  • short_words_query replaced: ≤4-char words are exact weight-A lexemes, never typo path (blocks lego → Legowisko).
  • ę/ą exception: a short raw word ending in ę/ą with ≥3 chars before it is stemmed (zimę → zim:*), required by the M3 acceptance example.
  • Typo path per want word: word_similarity(fold_pl(word), name_folded) ≥ 0.65 for words >4 chars; category thresholds deleted.
  • (M2) Candidate operand order want.name_folded <% l.name_folded, relying on the 0.6 GUC default (pinned).
  • (M5) Matcher constants only in src/matcher/matcher/rules.py; REMINDER_LEAD drift test; 4-char limit pinned behaviourally.
  • Forward runs born seen, no bell; window runs unseen and belled; suggestions never in the outbox. The window also stores suggestions.
  • matching = match_requested_at IS NOT NULL AND status = ACTIVE.
  • Startup gate: revision ≥ 99 and to_regclass('public.matchable_listings').
  • (M6) Backend lifespan fails fast on an old-0099 schema; no image-only rollback.
  • (L7) Claims take FOR NO KEY UPDATE; window transaction under 30 s statement timeout.
  • (L8) ≤1000 pairs per wants.bells_due row, expiring in the first; counts are additive.
  • asyncpg directly, no SQLAlchemy at runtime. useWantMatches also fetches suggestions; /suggestions LIMIT 10.
  • (L4) A resumed want with stored matches keeps showing them while matching; skeleton only with no MATCH stored.

Goal and scope

Make „Szukam” find inflected and diminutive names („kurtka zimowa” → „Kurtka na zimę”). Add a „Może Cię zainteresuje” tier for near misses, and run all matching in a separate matcher process behind a documented DB contract.
In scope
  • Amended 0099 DB contract (text functions, stop-list, generated columns, trigger, tiers, views)
  • Backend: flag-only writes, row lock on edit, bells via outbox with visibility re-check, suggestions API, stop-words 400, contract fail-fast
  • New src/matcher service: request loop with backoff, window loop, sweep
  • Frontend: pending/slow states, suggestions section, list badge
  • Compose service, runbook, docs fixes, re-measurement
Out of scope
  • Separate DB role/login for the matcher
  • Rescanning items that become takeable later
  • Description words for MATCH or SUGGESTION
  • Switching backend items_visible_to to the SQL views
  • Running the release-gate labelling
  • Outbox NOTIFY / shorter outbox poll
  • Paging of match or suggestion lists
  • Persistent (DB) backoff; configurable stop-list

User Stories

As a seeker, I want „kurtka zimowa” to find „Kurtka na zimę”, so that I don't miss items named with a different word form.
As a seeker, I want small words like „na” or „dla” ignored, so that „kurtka na zimę” finds „Kurtka zimowa” as a real match.
As a seeker, I want to see items that differ by one word, with the missing word shown, so that I can decide whether they suit me.
As a seeker, after saving a want I want „Szukamy pasujących rzeczy…”, and later „Wyniki pojawią się wkrótce” with „Odśwież teraz”, so that I know results are coming.
As a seeker, I want my wanted list to show „Szukamy…” on a want still being matched.
As a seeker, I want a bell only for real matches of newly listed items I may see, never for suggestions.
As an operator, I want matching in its own container that I can stop, restart and verify independently of the API.

Technical Approach

Data flow

A seeker write sets match_requested_at and commits; the trigger NOTIFYs at commit; the request loop claims, inserts MATCH and SUGGESTION rows (seen, no bell) and clears the flag; polling sees matching: false.

A new listing is picked up by the next window run (≤60 s): unseen MATCH rows, suggestions, wants.bells_due rows. The backend outbox poller (≤60 s) re-checks visibility and writes WANT_MATCH_FOUND — bell ≤~2 min after listing. Expiry reminders take the same path.

Inlining (H1)

Views are query rewrites, so matchable_listings, group_holdings and private_group_peers always expand into the caller. No contract object used in a match predicate is a function. PUBLIC is a plain column comparison at the call site; PRIVATE an EXISTS over the peers view (semi-join or hashed SubPlan). Forward keeps plain ANDs so @@ and <% stay index conditions; reverse keeps the MATERIALIZED window CTE and plain-columns-first CASE. Text functions run only when generated columns are written and in the per-word check.

Per-word check

stem_words is position-aligned with words_pl(name) by construction. Per position: prefix/exact lexeme on weight A, then the typo path for long words; hit count and missing positions from one unnest … WITH ORDINALITY per candidate pair. Exact SQL left to implementation; behaviour pinned by acceptance tests.

Concurrency
  • Claims and update_want both take FOR NO KEY UPDATE and serialise on the want row (H3). Window inserts need only FK KEY SHARE, so they never wait behind a claim (L7). A rare 40P01 is a lost race and self-heals.
  • Compare-and-clear never erases a newer request; clearing doesn't bump updated_at; expire/remind do (409 as today).
  • Suggestion cap counted from the run's snapshot; concurrent runs may slightly exceed 10; /suggestions returns ≤10.
Backend module boundary
  • outbox_acl.py in infrastructure/.
  • bells_due.py imports only app.core, app.db, app.wants.
  • main.py remains the only importer of app.wants.

Runbook: amended 0099

Replaces the „Deploy / rollback for wants (migration 0099)” section of architecture.md. Commands run from the repo root; none prints configuration.

  1. Release gate unchanged; now scores stems, stop-list, 4-char exact limit, 0.65.
  2. Build new images first: docker compose build backend matcher web.
  3. Detect old 0099: docker compose exec -T postgres psql -U aj -d aj -tAc "SELECT to_regclass('public.matchable_listings') IS NULL AND EXISTS (SELECT 1 FROM alembic_version WHERE version_num = '0099')" → t = old 0099.
  4. Backup: docker compose exec -T postgres pg_dump -U aj -Fc aj > pre-wants-matcher.dump (restorable thanks to H5).
  5. Old-0099 DBs only (dev/test; deletes every want, match, WANT_* notification):
    1. docker compose stop backend matcher
    2. docker compose run --rm --no-deps backend alembic downgrade 0098 (uvicorn never starts)
    3. docker compose run --rm --no-deps backend alembic upgrade head
    warningDo not run docker compose up before 5.2: the backend's upgrade is a no-op, its contract check refuses to start, and the matcher waits at its gate.
  6. Deploy: docker compose up -d --remove-orphans; a pre-0099 DB migrates on backend start; the matcher waits at its gate.
  7. Verify: alembic_version = 0099 and step-3 query returns f; \d wants shows stem_query/stem_words/match_requested_at; \dv lists the three views; matcher logs „listening”; a new want shows „Szukamy…” then the item; flagged count drains to 0; marker advances each minute; wants.bells_due rows reach PROCESSED.
  8. Rollback (no image-only rollback): stop backend + matcher; with the new image docker compose run --rm --no-deps backend alembic downgrade 0098; old compose file + images, up -d --remove-orphans (removes matcher); or restore the step-4 dump with the matching image.
  9. Future changes: changing fold_pl, words_pl (stop-list) or stem_word_pl = new revision with DROP/ADD of name_folded, name_query, stem_query, stem_words; altering a column read by the views = drop/recreate them in the same revision; bodies stay public.-qualified.
  10. Measured cost: FR-OPS-03 summary table.
