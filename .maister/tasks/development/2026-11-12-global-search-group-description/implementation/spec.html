TL;DR

  • /search becomes a real search page that guests can use too (including the Kategoria filter: GET /api/categories becomes PUBLIC). It calls GET /api/public/search, which returns SearchPage{items,total,page,size,other_mode_count}. Each item has a kind, the common fields id,title,subtitle,href, and kind-specific meta.
  • One membership primitive, group_ids_for(parties, *, organizer_only, memberships_only, include_deleted), is built on active_membership_clause()/active_leadership_clause() and replaces all 11 backend definitions (D1–D12). A guard test keeps any other definition from coming back.
  • One SQL visibility predicate per subject drives search, and can_view_item = EXISTS(items_visible_to); "listed only" (R12) is the search base, not part of the gate. PRIVATE items still need a shared non-deleted PRIVATE group. The counterparty check moves into SQL.
  • Full-text search uses pg_trgm, an IMMUTABLE fold_pl(), GENERATED STORED search_vector columns ('simple', A/C weights), categories.path_text and concurrent GIN indexes. The new module app/search mirrors app/pages.
  • groups.description (≤500 characters, checked synchronously by check_text and ensure_no_contact_info) is shown on the search card and in the group terms header. The only intended behaviour change is that an organizer may pledge items on their own group's terms (changelog).

Key Decisions

  • Phase 1 and 2 decisions are binding: C1–C4 and I1–I14.
  • The primitive lives in app/groups/infrastructure/membership.py, so the guard test can allowlist one file.
  • visible_to lives in app/groups/infrastructure/visibility.py. The viewer's own items stay visible in the 404 gate; search excludes them on top (I12).
  • other_mode_count counts the other mode with the same q and scope and no filters (the frontend clears filters on a mode switch).
  • Meetings ordering (Q4, hard rule): match_class first (description-only group = 1, everything else 0), then sort_at ASC NULLS LAST, in_my_groups, rank, kind, id. A description-only group never ranks above a name-matched group; terms and events stay ordered by date.
  • remove_leadership on a deleted circle (Q1): row-level holds_active_leadership over active_leadership_clause(), not group_ids_for; include_deleted=True stays messaging-only, read-only.
  • "Moje terminy" family set (Q3): group_ids_for(me) ∪ group_ids_for(family, memberships_only=True), with only_private/exclude_led on top. Zero behaviour change.
  • Guest Kategoria (Q2): matrix row 55 GET /api/categories → PUBLIC, router drops ReadPrincipal. Chosen over a new /api/public/categories: static reference data, one path for useCategories, no duplicate route. Mutations stay ADMIN.
  • Guard rule (W-1): only comparisons of GroupRole.party_id are flagged; projections pass. One allowlist entry: list_groups_for_moderation.
  • Fuzzy matching uses fold_pl(:q) <% col at the default threshold 0.6. Ranking is ts_rank plus weighted word_similarity (A 1.0 / B 0.4 / C 0.2).
  • Index revisions are grouped by purpose; every other change is a revision of its own.
  • The membership predicate includes the role type and GroupRole.valid_to IS NULL (nil delta).
  • Moderation text follows the existing MESSAGES pattern; the frontend shows the server message verbatim.

Goal & Scope

Let anyone find listed items, upcoming meetings, groups and organizations from one field. One membership definition and one visibility predicate are shared by search and the existing gates. Organizers can describe their groups, and the description is searchable.

User Stories

As a member, I want to search items in "Moje grupy" so that I only see things offered by people I share a group with.
As a logged-in user, I want to switch to "Wszędzie" so that I also find public items, meetings, groups and organizations outside my groups.
As a guest, I want to search without logging in so that I can discover public meetings, PUBLIC groups, organizations and public items.
As a searcher, I want to see how many results the other mode has and switch to it with one click, keeping my query.
As a searcher with no item results, I want a shortcut to add the thing to my "szukam" list.
As an organizer, I want to write a group description (≤500 characters) so that people understand the group and find it by its description.
As a visitor of a group terms page, I want to read the full group description in its header.

Matching, ranking, ordering, module layout
  • Items: search_vector @@ tsq OR fq <% fold_pl(name) OR the category CTE (leaf name B, path_text C).
  • Terms: vector OR the group name (A), organization (B) or location (C) fuzzy. Events: vector OR name (A), organization (B), location (C). Groups: name (A), organization (B), description (C). Organizations: name and slug (A).
  • Rank = ts_rank + GREATEST(word_similarity × 1.0 / 0.4 / 0.2), with the constants in app/search/domain/ranking.py.
  • Items order: in_my_groups DESC, available before reserved, rank DESC, created_at DESC, id. Rule (1) is deferred.
  • Meetings: a UNION ALL of 4 kinds, ordered match_class ASC, sort_at ASC NULLS LAST, in_my_groups DESC, rank DESC, kind, id. Groups are class 1 when only the description matched; terms, events and organizations are always 0.
  • Result schema: SearchResult is a discriminated union of per-kind models (Literal kind, typed meta).
  • "Org-run": the current organizer owns an Organization; owner-less organizations are excluded. Running events (starts_at < now) are hidden.
  • Statement budget: viewer (1 joined select), category check, page rows, total, other_mode_count, organization slugs/names, then thumbnails (items) or display names + locations (meetings). Max 7 per mode, ≤8.
  • Module: app/search/{router,application,domain,infrastructure/*_acl.py,schemas.py}, plus tests/test_search_boundary.py. ACLs expose selects and re-export executed batched loaders, as in app/pages.
  • Group endpoints: description on the 3 create paths and on PATCH; 400/503 moderation; GroupResponse.description; OrganizationGroupTermsResponse.description.
