# Specification: Admin Panel — Managing Plugins and Product Categories

## Goal
Introduce a new `ADMIN` permission and give admin-permission holders a "Categories" screen (real CRUD over a resurrected `Category` entity) inside the existing Chakra admin shell, while gating the existing Plugins section on `ADMIN` as an additive alternative to `PLUGIN_MANAGEMENT` — without breaking the `editor` persona's existing product-management workflow or the public, unauthenticated circle/term page.

## User Stories
- As an `ADMIN`-permission holder, I want to see a "Categories" nav item in the Sidebar so I can discover category management the same way I discover Products/Plugins.
- As an `ADMIN`-permission holder, I want to create, rename, reorder, and delete product categories so the "rzeczy" (items) dictionary reflects what my organization actually needs, in Polish.
- As an `ADMIN`-permission holder, I want a blocked delete (category still in use) to tell me exactly how many products reference it, not a generic failure message, so I know what to fix before retrying.
- As an `editor`-permission holder (no `ADMIN`), I want product creation/editing to keep working exactly as today, including populating the category dropdown from live data, so this change causes no regression to my existing workflow.
- As any authenticated user with `PLUGIN_MANAGEMENT` *or* `ADMIN`, I want to keep reaching the Plugins section so neither permission holder loses access during/after this change.
- As a guest viewing a public circle/term page, I want "needed items" to keep showing a correct category name after the backend's category representation changes, so the public page doesn't silently break.

## Technical Approach

### Data model & migration sequencing
The migration is one Alembic revision (per `standards/backend/migrations.md`'s "small and focused" rule, with the accepted exception that schema-creation and its immediately-dependent backfill/column-drop are sequenced within it, analogous to how `0006` itself combined schema + column type change): create `categories`/`category_seq` → seed 5 Polish-named rows **with explicitly assigned ids** (not `nextval()`-generated, so the ids are known at authoring time for the backfill step immediately below — see Core Requirement #2) → add `products.category_id` nullable → backfill by enum-token, referencing those known seeded ids directly → set `NOT NULL` + FK + index → drop `products.category`/`ProductCategory` type (and, in `app/product/{models,schemas,service,router,query_service}.py`, every reference to it — Core Requirement #3) → grant `ADMIN` to the seeded `admin` account. `downgrade()` reverses every step in dependency order and must leave a clean database under `alembic downgrade base`.

### Backend authorization
Matrix-first: the two new category rows and the two updated plugin rows are added to `AUTHORIZATION_MATRIX` in the same change as the corresponding `require_any(...)` router declarations, per `standards/backend/security.md`'s explicit ordering convention. Category GETs stay on `("READ", "mcp:read")` — this is the single hard correctness requirement in this task (locked decision #5/gap-analysis Critical Decision 4): getting this wrong regresses the `editor` seed account's ability to create/edit products, since `ProductFormPage`'s category dropdown depends on `GET /api/categories` succeeding for a `READ`/`EDIT`-only user.

### Cross-bounded-context update (`app.groups`)
`app/groups` is DDD-layered (domain/application/infrastructure behind a facade, per project memory) and imports `ProductCategory` directly from `app.product.models` today, in three places: the join in `infrastructure/repository.py`, the dict-building in `application/terms.py`'s `_needed_item_view()`, and the explicit DTO construction in `application/public_view.py`. This task changes the `repository.py` join to instead resolve category id/name via the new `Category` entity, propagates the resulting id/name pair through `terms.py`'s dict shape, updates `public_view.py`'s `PublicNeededItemResponse(...)` call site accordingly, and renames both response schemas (`schemas.py`). This is the highest-risk integration point in the task (it reaches a public, unauthenticated endpoint) — the backend DTO change (all four files above) and the corresponding `api/groups.ts` + `api/terms.ts` + Panel-consumer frontend change must land in the same task group/deploy unit to avoid a broken intermediate state where the public page fetches a shape the frontend doesn't understand yet, or vice versa.

### Frontend data flow
`useCategories()` becomes the single source of truth for the category list on the frontend, replacing the compile-time `PRODUCT_CATEGORIES` constant. Forms that submit a category (`ProductFormPage`, `ItemQuickAddForm`, `NeededItemQuickAddForm`, `EditTermDialog`) render their `<select>` options from `useCategories()`'s live `data` and submit `category_id`; read-only displays (`ProductDetailPage`, `CarbonFootprintLandingPage`, `RzeczyView`) resolve the display name from the same hook's data by id, rather than from a static label map (which no longer exists post-migration of `utils/productCategory.ts`).

### Ordering (`sort_order`)
No drag-and-drop library is introduced. `CategoryListPage` renders per-row up/down arrow buttons; each click calls `moveCategory(id, direction)`, which the backend resolves by swapping the target row's `sort_order` with its immediate neighbor in current order (atomic within one transaction). `GET /api/categories` and `useCategories()` both order by `sort_order` (never `name`), consistent everywhere a category list is rendered (admin table, product/item `<select>` options, filter dropdowns).
