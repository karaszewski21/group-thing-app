TL;DR

A new app/email module queues mail in email_messages (the transactional outbox) in the same transaction as the bell or account write; a 60 s _run_email_send job sends it through an EmailSender port (Mailgun EU, SMTP to Mailpit, log, fake in tests).
It covers 3 account mails and 7 bell kinds, opt-out preferences with RFC 8058 unsubscribe, a signed Mailgun webhook feeding email_suppressions, account_tokens in auth, and user_profiles.email_verified_at with a Google backfill (0110–0112).
EMAIL_ENABLED gates everything; EMAIL_NOTIFICATIONS_ENABLED (default false) gates bell mail at enqueue and claim (warm-up and emergency stop), with a „Powiadomienia e-mail ruszają wkrótce” note on /settings.
The frontend gets /settings, /verify-email, /reset-password (token form for logged-in users too), /unsubscribe, a neutral Home banner, a login link and an Account row from the binding mockups. This revision applies the spec audit (see Audit resolution).

Open Questions / Risks

  • riskD14 privacy policy and the Mailgun DPA are rollout prerequisites outside the code.
  • riskCopy not in mockups is proposed and needs a product read: BOUNCE state on /settings, scope=all confirmation, subjects/CTAs per kind, reset/changed bodies; the mockup's gendered „zakładałaś” becomes neutral.
  • riskMailgun's own suppression lists are not cleared by a local BOUNCE delete (runbook note).
  • riskWebhook replay memory is per process (single backend instance).
  • riskForgot-password timing is not equalised (accepted, no HTTP rate limit).
  • riskemail_messages/email_preferences party_id have no ON DELETE rule; account deletion must handle them.
  • riskPre-existing outbox duplicate-bell bug: mail dedup only for TERM_CONFIRMATION_NEEDED; a term_confirmation key dedups forever (L-13, accepted).
  • riskAccepted (M-3): an older token's queued mail goes out with a dead link (410).
  • riskAccepted (M-1): webhook retries older than 5 min are rejected as stale.
  • riskNew reserved slugs could collide with existing Organization slugs: runbook pre-deploy check query.
  • riskProposed copy for loading/error states, toggle-revert alert, unknown address, „wkrótce” note and neutral verify success (M-7, M-8).

User Stories

As a new user registering with a password, I want a link to confirm my address right away so that I start getting mail about my exchanges.
As an existing user, I want a banner on Start and a button in settings to verify my address so that I can turn mail on without re-registering.
As anyone who forgot a password (including a Google-only account), I want a reset link by mail so that I can set a new password; the page never reveals whether an account exists.
As a participant in an exchange, I want a mail when someone takes my item, proposes or answers a swap, a reservation is cancelled or a hand-over needs confirming, so that exchanges do not stall.
As a seeker, I want at most one mail a day per want about new matching items.
As a recipient, I want to switch categories off in /settings or with one click from a mail, so that I only get what I want.
As the operator, I want a delivery log, bounce and complaint suppression and a daily cap so that the sending domain keeps its reputation.

Technical depth

Data model (0110–0112)
  • email_messages: idempotency_key (uq), party_id (FK parties), stream, category (NULL ⇔ TRANSACTIONAL), template, loose notification_id/kind, payload JSONB, status (8), skip_reason (7 incl. expired, set ⇔ SKIPPED), attempts, send_after, expires_at, claimed_at, sent_at, delivered_at, event_at, provider_message_id, last_error (code only). Partial indexes on PENDING send_after and SENDING claimed_at; ix on sent_at, provider_message_id, party_id.
  • email_preferences (party_id, category, enabled; uq party+category; full category catalogue), email_suppressions (address_normalized uq, BOUNCE|COMPLAINT), account_tokens (user_id CASCADE, purpose, token_hash uq, email snapshot, expires_at, used_at, ix user+purpose+created_at).
  • 0111 nullable user_profiles.email_verified_at; 0112 backfill from verified, matching Google identities (downgrade no-op).
Keys, rules and job
  • Keys: notification:<id>, want_match:<want>:<Warsaw day of send window>, term_confirmation:<proposal|reservation>:<party>, auth:<token_id>, auth:<token_id>:changed.
  • Job (60 s, max_instances 1): recover stuck SENDING (N → PENDING, T → FAILED) → expire → claim 50 SKIP LOCKED (T only 22–07 or with notifications off) → 4 binding reads → one skip write + commit → sends under wait_for(10 s) → one result write, every outcome only WHERE status='SENDING' (sent_at/provider id/token removal always).
  • Skip order for NOTIFICATION: organization, no_address, unverified, suppressed, category_disabled, daily_cap. TRANSACTIONAL: no_address only.
  • Backoff 1/5/15/60/240 min, MAX_ATTEMPTS 6; log line 'email send: claimed=… sent=… skipped=… retried=… failed=… expired=… recovered=…'.
Flags, imports, config
  • EMAIL_ENABLED=false: no enqueue, no job, request endpoints 503, email_verified null. EMAIL_NOTIFICATIONS_ENABLED=false: no bell enqueue and only TRANSACTIONAL claimed (queued bell rows expire), notifications_live=false shows the „wkrótce” note.
  • Imports: notifications → notifications/infrastructure/email_acl → app.email.service; users.service → auth.account_tokens → auth/infrastructure/email_acl → app.email.service.
  • Config names: EMAIL_ENABLED, EMAIL_NOTIFICATIONS_ENABLED, EMAIL_BACKEND, EMAIL_PROVIDER_API_URL, EMAIL_PROVIDER_API_KEY, EMAIL_FROM_ADDRESS, EMAIL_FROM_NAME, EMAIL_REPLY_TO_ADDRESS, EMAIL_LINK_SIGNING_SECRET, EMAIL_WEBHOOK_SIGNING_KEY, EMAIL_DAILY_CAP, EMAIL_SMTP_HOST, EMAIL_SMTP_PORT, APP_PUBLIC_BASE_URL; fail-fast email_configuration_errors names only.
  • clock.local_to_utc; matrix rows 74–82; reserved slugs verify-email, reset-password, unsubscribe.

Success Criteria

  1. A bell and its queue row commit atomically; the hook costs at most one extra statement and none for empty or non-MVP input.
  2. Outside quiet hours a mail reaches the provider within 2 minutes; TRANSACTIONAL is never delayed by quiet hours.
  3. No NOTIFICATION mail to unverified, suppressed, opted-out or organization recipients; an unsubscribe takes effect by the next run (≤ 2 min).
  4. No address, token or content in logs or last_error; raw tokens leave payload at final states.
  5. Forgot-password always 202; every account with an address, Google-only included, can set a password.
  6. Webhook events idempotent and never lower a status; BOUNCE/COMPLAINT stop NOTIFICATION mail.
  7. All 11 design-context IDs implemented with mockup copy, order and states; new tests pass with no regressions beyond the baseline.
  8. Migrations 0110–0112 pass downgrade-then-upgrade tests; runbook in architecture.md.
