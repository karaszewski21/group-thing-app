TL;DR

Every PRIVATE group gets one 6-digit code, stored in plaintext in groups.join_code. The code is created lazily on the organizer's first GET (with one bounded retry after a concurrent write), and only "Wygeneruj nowy kod" rotates it.

Organizers see the code in a presentational JoinCodeCard, fed by its host page (GroupDetailsPage, stepper done screen). Visitors enter it in a JoinByCodeSheet (<form noValidate>). TermPage owns ?code= and the sheet state, and auto-submits a valid ?code= once. On success the visitor becomes an active member through the unchanged add_active_membership.

Redeem follows 401 → 404 → 429 → 409 → 200 {created}, behind an in-process limiter with two keys: 10 failed attempts per 15 min per (party, group), and 30 per hour per group. Any correct-code 200 clears that user's key.

The "poproś o dostęp" mechanism is deleted end to end: backend, frontend, notifications, tests, the table (migrations 0059 and 0060) and two .maister prose items.

Key Decisions (14)
  • 6-digit numeric code bounded by a per-group failure budget rather than by entropy — the user chose 6 digits; at 30 failures per hour per group, expected guessing time is about 1.9 years (ADR-001).
  • Plaintext nullable groups.join_code VARCHAR(6), no index, exposed only through the organizer endpoints — organizers must be able to read and copy it, and hashing 10^6 values adds no protection (ADR-002).
  • In-process sliding-window limiter at app/groups/application/join_code_limiter.py with an injectable clock and reset() — single uvicorn process, no new dependency, no DB writes; single consumer, so it lives in the groups BC (ADR-003, scope decision 8).
  • Lazy get-or-create GET plus an explicit regenerate; no expiry, no backfill. On StaleDataError the GET rolls back, re-reads and re-decides once: PUBLIC → 409, code present → return it, still null → generate one more time; a second failure goes to the existing 409 handler. Never None or 500 (ADR-004, clarification 2, audit M1).
  • JoinByCodeSheet is built on the krag ModalSheet as a <form noValidate>: Enter submits, and a pasted 482 913/482-913 is accepted and normalized by parseJoinCode (ADR-005, audit M3).
  • TermPage owns ?code=, the one-shot guard, the sheet's open state and the join callback; PrivateGroupGate only renders from props. A malformed ?code= is stripped at once and opens the sheet empty (audit M2).
  • The host page calls useJoinCode (and, on GroupDetailsPage, useGroupTerms) and passes code, status, regenerate, onRetry, termId to a presentational JoinCodeCard — one subscriber per query (audit M4).
  • "Kopiuj kod" copies the raw 6 digits (482913); the card displays formatJoinCode (482 913) (audit M3).
  • Join requests are deleted in full, with no data migration — the app has no production data (ADR-006, clarification 3).
  • Redeem returns one 409 message for "wrong code" and "no code yet", and idempotent 200 {created:false} to members and organizers (ADR-007, scope decision 6). That path also clears the caller's (party, group) key; the group key is never cleared (user decision 5).
  • JoinCodeCard only for PRIVATE groups; 403 → nothing, loading → skeleton, other errors → inline retry — GroupResponse stays free of the code (ADR-008, audit M5).
  • Frontend writes use useCallback + api call + await invalidateQueries, not useMutation; errors rethrown as new Error(serverMessageOr(err, fallback)), so no dialog shows 409 Conflict (audit M9).
  • The regenerate confirm reuses ConfirmDeleteDialog with optional tone and busyLabel props — additive, keeps z-70, trapFocus, Esc and the registry.
  • "Kopiuj link z kodem" targets the nearest term from the start of today via a new useGroupTerms; with none, only "Kopiuj kod" (clarification 1, scope decision 7). AuthGateLinks is unchanged; the mockup's "Załóż konto" was an approximation (audit L10).

Open Questions / Risks

  • acceptedAccepted consequence: a member who joins by code is invisible to the organizer until they RSVP, because list_group_members lists RSVP attendees only. Nobody can remove them: POST /api/memberships/{id}/end is self-only and has no UI. Regenerating only blocks new joins. Follow-ups: active-member list, member removal, "dołączył(a) kodem" notification.
  • acceptedResidual brute force: about 2.2% success per 30 days and about 26% per year under sustained attack. Regenerating does not reset this risk.
  • acceptedAccepted DoS: any account can use up a group's 30-per-hour budget and block every visitor for up to 1 h (about 45 min for one account). Regenerating does not lift the block.
  • infoSingle process only: limiter state is lost on restart and weakens with more than one worker. Docstring caveat required; a DB-backed limiter is a follow-up.
  • infoDuplicate memberships: concurrent redeems can still insert two active memberships (no unique index). Mitigated by the in-request re-check, the busy-disabled submit and the one-shot ?code= ref.
  • infoCode not on the panel link: "Kopiuj link do terminu" (PanelDataContext.tsx:905-911) carries no code. Follow-up.
  • infoFocus after an auto-opened sheet: no opener button, so closing returns focus to the main[tabindex=-1] fallback (ModalSheet.tsx:37-41). On success the gate unmounts anyway.
  • infoDeviation from the HLD: TooManyAttemptsException(message, retry_after_seconds) vs the HLD's retry_after — same shape, clearer unit.

User Stories

Organizer

As an organizer of a PRIVATE group, I want to see, copy and share my group's access code (or a term link that carries it), so that the people I invite can join without waiting for my approval.

Organizer

As an organizer, I want to generate a new code after a leak, so that the old code stops working while existing members stay in.

Visitor

As a logged-in visitor on a private term page, I want to type the code I was given and see the term right away, so that I can RSVP in the same sitting.

Anonymous

As an anonymous visitor following a ?code= link, I want the code to survive login and be applied automatically, so that I don't have to retype it.

Member

As a member opening an old ?code= link, I want to land on the term directly, without errors.

Technical Approach

Layering, lazy write, limiter flow, matrix
  • Layering: router → application use case → repository, inside the groups BC. Use cases take (db, principal, group_id, …) and are re-exported from service.py. Membership creation goes only through add_active_membership, so /access and the RSVP PRIVATE guard work without logic changes.
  • Lazy write: the GET commits the code, bumping updated_at (the version_id_col). StaleDataError is caught only in the GET, only once: rollback, re-read via get_group, re-decide (PUBLIC → 409, code → return, null → one more generate-and-commit, whose failure goes to the global 409 handler). Never read the pre-rollback instance (MissingGreenlet). Regenerate lets the global 409 handler respond.
  • Limiter flow in redeem: check after 404, before reading or comparing. Both 409 paths call record_failure; both 200 paths call clear (user key only). In-flight overshoot is accepted; the R4 wait formula still reports the true wait. The submitted code is never logged.
  • Matrix: the redeem row must precede row 27 (asserted by the regression test). GET and regenerate fall through to rows 26 and 27.
Frontend data and ?code= lifecycle
  • One subscriber per query: hosts call useJoinCode/useGroupTerms and hand the results to the presentational card.
  • useJoinCode is enabled for PRIVATE groups only; 4xx is not retried, so a member's 403 costs one request; 5xx/network are retried twice before status: "error".
  • useGroupTerms is enabled only when status === "ready".
  • Writes await invalidation of their prefix and rethrow new Error(serverMessageOr(err, fallback)). Retry-After is invisible to the client; the minutes come from the server message.
  • ?code=: kept through login via returnTo; evaluated only when /access is ready and not stale (useTermAccess.ts:72, TermPage.tsx:37); one-shot ref keyed by groupId:code; stripped (only code, replace: true) at once for view or a malformed code, or when the auto-submit's onJoin settles.
Migration safety

0060 deletes the notification rows before dropping the column, because NotificationKind is string-backed. The downgrade rebuilds the post-0041 UUID shape (R12 types, gen_random_uuid() PK, pk_/fk_/ix_/uq_ names, partial unique index on PENDING, no sequence) and re-adds join_request_id UUID NULL, in the reverse of the upgrade order.

Success Criteria

  1. A logged-in non-member holding a valid code reaches the term content and a successful RSVP with one code submission and no organizer action, including the anonymous ?code= → login → auto-submit path (manual two-account check).
  2. No API response other than the two organizer endpoints contains join_code (exact key-set tests).
  3. At most 30 failed redemptions per group per rolling hour and 10 per (user, group) per 15 minutes; a correct code while locked out returns 429 with an integer Retry-After.
  4. A wrong code and "no code yet" are indistinguishable: same status, same message.
  5. The R31 rg -i … command returns nothing and the R32 prose items are updated; alembic downgrade 0058 && alembic upgrade head and alembic downgrade 0059 && alembic upgrade head succeed.
