TL;DR

  • The API process gets a third, bell-less tier SIMILAR. It embeds product names and want names (with zapytanie: ) using mmlw-roberta-base int8 ONNX and stores them as halfvec(768) in product_embeddings/want_embeddings (0100 vector, 0101 schema) on pgvector/pgvector:0.8.7-pg18-trixie.
  • The asyncpg-only matcher compares them by exact scan in SQL and runs SIMILAR last. Pairs are born seen, capped at 10 and inserted with ON CONFLICT DO NOTHING, behind gate 101. They are served by GET /api/wants/{id}/similar and shown under „Powiązane rzeczy” on /wanted/[id].
  • Vector writes are synchronous and best-effort (2 s timeout on one dedicated embed worker, fail open), with an embeddings.requested outbox retry and a 1-minute reconcile job (300 + 300 per tick).
  • Background re-triggers set the new wants.similar_requested_at, which runs SIMILAR only. Lexical MATCH/SUGGESTION, bells and counts do not change. list_wants(matched_item_id) ignores SIMILAR.
  • Shadow mode comes from deploy order (stop matcher → alembic → backend → drain → matcher → web). The 0.86 threshold is provisional until the labelled-sample gate.

Key Decisions

  • Architecture fixed by research ADR-001..009.
  • Defaults: embed timeout 2 s (one name), 10 s (reconcile batch of 32) · reconcile 300 + 300 per tick in sub-batches of 32 · SEMANTIC_CAP 10 · SEMANTIC_SIMILARITY_MIN 0.86 (provisional) · SIMILAR_LIMIT 10, score desc then item id.
  • Settings EMBEDDINGS_ENABLED (false) and its own EMBEDDINGS_MODEL_DIR (/models/embed). moderation_models_dir is not reused, because app/embeddings is compute-only and independent of moderation.
  • Model id sdadas/mmlw-roberta-base@<HF_COMMIT_SHA>+int8, pinned in the backend, the Dockerfile and the matcher. A drift test checks all three, and the loader refuses a mismatch.
  • halfvec binding: a text literal with CAST(:embedding AS halfvec). No pgvector Python package, and no vectors in responses.
  • The side tables are plain and unmapped, keyed by owner id, with CASCADE. The carve-out is approved (decision 18); /maister:standards-update records it in models.md and migrations.md when the tier ships.
  • A name change without a fresh vector deletes the stored vector.
  • Background re-triggers are SIMILAR-only (decision 15): the handler and reconcile set similar_requested_at, and the matcher runs FORWARD_SIMILAR alone, so no lexical pair is stored born seen. Seeker writes keep match_requested_at: a full run that clears both flags.
  • Locks (decision 16): handlers use plain FOR NO KEY UPDATE (wait, never "gone"); the sweep uses FOR NO KEY UPDATE OF p|w SKIP LOCKED.
  • The want re-trigger is a Core update of similar_requested_at (no updated_at bump), for ACTIVE wants only.
  • One embed at a time: a single-worker executor; a stuck call makes later calls fail fast as busy.
  • Matcher gate: revision ≥ 101 alone covers the new column (0101 is one transaction); the table to_regclass checks stay.
  • Deploy order (decision 17): stop matcher → alembic upgrade 0100 + head via compose run → up -d --remove-orphans.
  • Authorization matrix: no new row. Only the comment of rows 66–67 and a test row change.
  • WantSimilarResponse = {id, title, href, meta, reserved_by_me, proposed_by_me}.
  • The reconcile job is always scheduled and idle without an embedder.
  • A shared reservedCaption.ts.

Open Questions / Risks

  • criticalQuality is unproven: 0.86 comes from 41 positives. Release needs the ≥300-pair gate, and X and the 0.80 bound still need confirmation.
  • warningVPS A capacity is unmeasured (+~130 MB, +25–50 ms).
  • warning<HF_COMMIT_SHA> must be resolved at implementation (40-hex, never main).
  • warningOld backend images cannot start at 0100+ (alembic upgrade head fails on an unknown revision), so there is no image-only backend rollback. The old matcher at 0101 needs a staging check.
  • infoBackfill re-entry (R12) can ring capped-out MATCH bells, but never loses one (window MATCH pairs are born unseen). Drain before the matcher deploy.
  • infoAt the matcher deploy, every ACTIVE want carries a SIMILAR flag from the backfill. Full requests are claimed first; watch the flag count reach 0.
  • infoA handler can wait on a locked want for up to the matcher's forward transaction (≤ 3 × 30 s), holding up the dispatcher. This is rare and the same wait as update_want.
  • warningForward cost depends on the InitPlan pushdown. Record EXPLAIN; the target is p95 ≤ 150 ms.
  • infoA separate web deploy is assumed. If it cannot ship alone, fall back to the ADR-004 read-side hold.

Goal

Show seekers listings that mean the same thing in other words („Samochód zabawka” ↔ „Zabawka - auto mercedes”), as a quiet, honestly labelled „Powiązane rzeczy” tier. Every existing lexical behaviour, bell and count stays as it is.

Scope

In scope
  • 0100 vector extension, 0101 side tables, view and CHECKs
  • Compute-only app/embeddings (int8 ONNX, CLS + L2, prefix)
  • Product and want vector writers, outbox retry, 1-min reconcile job
  • Matcher SIMILAR statements run last, per-tier counts, gate 101, constants and drift test
  • GET /api/wants/{id}/similar; list_wants(matched_item_id) excludes SIMILAR
  • „Powiązane rzeczy” section, SimilarCard, shared reservedCaption
  • Dockerfile models stage (int8 + parity gate), compose, .env.example, conftests, docs and runbook
Out of scope
  • Semantic /api/public/search; LLM expansion or judging; GPU; VPS B models
  • A SIMILAR bell, badge, count or email; upgrading SIMILAR to MATCH
  • Category guard and lexical-anchor gate (scored only)
  • HNSW/ivfflat; a dedicated embedder process; int8 Bielik-Guard
  • Embedding descriptions or notes (the name + category template is only a challenger)
  • SIMILAR outside /wanted/[id] (e.g. the item closing prompt)
  • The labelled sample and the VPS A measurement (documented only)
  • A read-side hold switch (ADR-004 fallback only)

User Stories

Seeker
On /wanted/[id] of an active want, I want to see related items with other words, so that I find what the word matcher misses.
Seeker
I want related items to make no bell, badge, count or email, so that only real matches interrupt me.
Seeker
With a closed (expired or fulfilled) want, I see no related items, as with suggestions.
Lister
I want my item to reach seekers who describe it differently, and listing must never fail or slow down noticeably.
Operator
I want to deploy in shadow, measure, roll back step by step, and switch vector writing off with one flag.

Technical Approach

write ─► text checks ─► embed (≤2 s, to_thread) ─┬─ ok ─► upsert vector (same txn; want: + match_requested_at → NOTIFY) └─ miss ─► commit without vector, delete stale one, stage embeddings.requested outbox (60 s) ─► subject handler in savepoint ─► re-read name (FOR NO KEY UPDATE, waits) ─► embed ─► upsert ─► want: similar_requested_at │ product: e.updated_at reconcile job (1 min) ─► 300 products + 300 ACTIVE wants, 32 per txn, FOR NO KEY UPDATE OF p|w SKIP LOCKED ─► want: similar_requested_at matcher claim ─┬─ match_requested_at ─► MATCH ─► SUGGESTION ─► SIMILAR, clear both flags └─ similar_requested_at ─► SIMILAR only, clear it (window: MATCH unseen → bell, SIMILAR born seen) SIMILAR = pinned model id on both sides, distance ≤ 1 − 0.86, cap 10, born seen, DO NOTHING GET /similar ─► visible_matches ─► cards (no vectors, no score) ─► „Powiązane rzeczy”
Failure path, timestamps, concurrency
  • A miss never fails a write. Outbox retries ×5, then FAILED, then the sweep repairs. EMBEDDINGS_ENABLED=false freezes the tier; stored rows stay readable.
  • Naive UTC via datetime.utcnow() and the routes' now; the wants clock guard stays green.
  • Product reconcile FOR NO KEY UPDATE OF p SKIP LOCKED (compatible with the item FK KEY SHARE); want reconcile FOR NO KEY UPDATE OF w SKIP LOCKED.
  • Both handlers use plain FOR NO KEY UPDATE and wait, at most for the matcher's forward transaction (3 statements × 30 s), the same wait update_want has. The sweep holds its locks for one batch (≤ 10 s embed + upsert). The re-trigger leaves updated_at untouched.
  • A stuck inference (still running after its timeout) makes later calls fail fast as busy misses, which go down the same retry path.
  • User writes keep the shared 409 on deadlocks; the job logs one WARNING.
Cost budget and boundaries
  • Window +1–1.7 s per capped run (lexical ~13 s, timeout 30 s); forward ≤ 150 ms p95; writes +25–50 ms p95.
  • Backfill: ~50k products ≈ 167 ticks ≈ 3 h at one tick per minute, about 15–40 min of CPU in total; off-peak.
  • app.embeddings is imported by app/product/*, wants/infrastructure/embeddings_acl.py and main.py. A new test keeps it compute-only (app.config/app.core).
Compatibility
  • An old matcher at 0101 passes its ≥ 99 gate; the appended columns, the CHECKs and similar_requested_at (its claim never reads it) do not affect it.
  • Late product vectors move changed_at, and the window stores any not-yet-stored lexical pair unseen, so no bell is lost.
  • An old backend cannot alembic upgrade head at 0100 or later (unknown revision), hence the runbook order.
  • The old web image never calls /similar, and the closing prompt ignores SIMILAR, so shadow mode is invisible.

Runbook — Deploy / rollback for the semantic tier (0100–0101)
  1. Release gate: ≥300 labelled pairs on the int8 export, Wilson LB ≥ 0.80, hard-negative FP ≤ 10%, recall gain ≥ X, threshold set from the held-out sweep.
  2. 0b VPS A: probe.py is not in the image; run it from a mounted dev checkout (-v …/models-probe:/probe:ro), or time OnnxEmbedder in a python -c loop.
  3. Build: only docker compose build backend (the matcher image waits for step 6); the parity gate must pass; model_id.txt = EMBEDDING_MODEL_ID.
  4. Dump: pg_dump -Fc off the host; after 0100 it restores only into a pgvector image.
  5. Image swap: stop backend and matcher, switch to pgvector/pgvector:0.8.7-pg18-trixie, verify the version, collation versions and rolsuper. The old images are fine at 0099.
  6. Migrate, then backend: (1) docker compose stop matcher; (2) docker compose run --rm --no-deps backend alembic upgrade 0100, check \dx vector, then … alembic upgrade head; (3) EMBEDDINGS_ENABLED=true, docker compose up -d --remove-orphans (no --build; the old matcher returns and ignores the new flag). Retry step 2 on a lock timeout. Never start an older backend afterwards.
  7. Drain backfill: reconcile log lines, missing or stale vector counts to 0, capped= and bells, FAILED embeddings.requested.
  8. Matcher (shadow): docker compose build matcher + up -d --remove-orphans matcher; gate 101, similar= in the log, the marker advancing, similar_requested_at flag count falling to 0.
  9. Shadow metrics, 2–4 weeks: per-want counts, score histogram, spot check ≥ 0.80, window and forward timings, embed timeouts, RSS, FAILED rows, bells unchanged.
  10. Web: deploy „Powiązane rzeczy”; open rates per score band.

Rollback: web image → EMBEDDINGS_ENABLED=false → old matcher image → docker compose stop matcher backend, then from the new backend image alembic downgrade 0100 then 0099 (superuser; pg_extension ownership) → old images → postgres:18 only after the extension is dropped. No image-only backend rollback at 0100 or later; the downgrades are plain and lose only derived data.

Future changes: a model, prefix, pooling or revision change needs a new id in three places plus a re-scored threshold, deployed backend → sweep → matcher. A dimension change is a new revision. Any vector index needs iterative scan and short-result tests.
