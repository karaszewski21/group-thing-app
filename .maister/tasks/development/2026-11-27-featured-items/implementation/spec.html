TL;DR

Owners mark up to N listed items as featured with a „⭐ Wyróżnij” toggle in „Moje rzeczy”. N is set on a new admin page /admin/settings (default 3, range 0–20, 0 = off). The mark is a nullable featured_at on item_listing_preferences, so it disappears with the listing. It is set through an idempotent PUT /api/item-listing-preferences/{item_id}/featured (hidden items 404 first). An owner Party-row lock taken FOR NO KEY UPDATE serialises the cap. Featured items get a dark „⭐ Wyróżnione” pill and come first (most recently featured first) on term, event, owner, profile and organization pages. Search, wants cards and the order of „Moje rzeczy” do not change. The limit lives in a new app/settings module (single-row app_settings), behind ADMIN GET/PUT /api/admin/settings (matrix row 74).

Key Decisions

  • The featured state is featured_at on the listing row. It is deleted on unlist or hand-over, and clients only see is_featured.
  • The limit lives in a new app/settings module (the user's choice), not on points_config. Groups read it via settings_acl.py.
  • Two revisions. 0110 creates app_settings with its seed row. 0111 adds featured_at and its partial index. This follows the standard: a nullable column goes in a separate revision from a new table.
  • Schema and seed share 0110, as a recorded exception. load_settings uses scalar_one(), so a head without the row would answer 500. points_config could split 0103/0105 only because nothing read the row in between.
  • The 0111 index is not built concurrently. The table is small, the predicate is empty at creation, and the lock is bounded by lock_timeout 5s.
  • Downgrades are plain, unguarded and lossy. Featured marks are presentation state. There is no image-only rollback.
  • Order: require_item_visible, then Party row FOR NO KEY UPDATE → item → preference. FK inserts into rows referencing parties (owner notification, counterparty_party_id, preference insert, fulfill_exchange) take FOR KEY SHARE after the item or preference lock. A plain FOR UPDATE could deadlock with them. key_share=True still serialises toggles of one owner and never blocks FK checks. The plain FOR UPDATE of _lock_owner is not copied.
  • The toggle is idempotent. Re-featuring keeps featured_at and skips the cap check. Unfeaturing is always allowed. A lowered limit keeps existing marks.
  • The owner never sees the limit. It shows only in the 409 message, with the Polish plural: N = 1 → „Możesz wyróżnić maksymalnie 1 rzecz.”, otherwise „Możesz wyróżnić maksymalnie {N} rzeczy.”.
  • Accepted: the toggle bumps updated_at. This moves matchable_listings.changed_at, so the matcher re-reads the listing (idempotent, counts toward WINDOW_MAX_LISTINGS). Bypassing the version column would break BaseEntity optimistic locking.
  • Where the mockups differ, the existing app wins. Errors use the bottom ToastPill. The featured pill goes first in the „Moje rzeczy” chip row. „Settings” goes right after „Points” and no other entry moves.
  • The term page uses a stable client sort. Featured items come first in the server's order, the rest newest first, and the slice to 3 happens after the sort.

Open Questions / Risks

  • infoGuests may see a change up to 60 s late (s-maxage=60). Accepted.
  • infoWith a limit above 3, previews show only the 3 most recently featured items. The rest are behind „Pokaż więcej”.
  • infoThe preference PUT rewrites owner_party_id, and the cap counts by it. Harmless, noted only.
  • warningFeaturing bumps the preference version, so a concurrent stale mode or visibility PUT may get a 409. The existing toast + refresh handles it.
  • warningAbout 9 backend key-set test files and the typed frontend fixtures must gain is_featured.
  • warningMigrations 0110/0111 and matrix row 74 collide with an uncommitted email module in the main checkout (0110–0112). The user decided to keep the numbers here and renumber at merge. The plan must include that step: revision ids, down_revision, file names, migration test, runbook, matrix row and its test.

Scope

In scope

  • Featured toggle in „Moje rzeczy” (listed items only, any mode, PUBLIC or PRIVATE, reserved allowed)
  • Per-owner cap from the admin settings, 0 = off, Polish 409s
  • Featured-first order on term, event, owner, profile and organization pages
  • Badge on term and event previews, owner, profile and organization grids, the product header and Moje rzeczy
  • New app/settings module, /api/admin/settings, /admin/settings page and nav entry
  • Migrations 0110–0111, runbook line in architecture.md, INDEX.md

Out of scope

  • Search ordering and a search badge; wants match, suggestion and similar cards
  • An owner-visible limit, an N/limit counter or any owner read of the limit
  • Changing the order of Moje rzeczy or of the browse/mine term-item-listing lists
  • Paid or promoted featuring, expiry, moderation
  • Moving existing settings into app_settings
  • Featuring drafts, or keeping a mark across unlist/relist

User Stories

Owner
Marks their best listed items as featured in „Moje rzeczy”, so visitors see them first.
Owner
Gets a clear message at the limit or when featuring is off, so they know why the click had no effect.
Visitor
Sees a „⭐ Wyróżnione” badge, with featured items first on term, event and owner pages.
Admin
Sets the per-user limit (0–20, 0 = off) on an admin settings page without a deploy.

Technical Approach

Write path

The toggle calls AppDataContext.setItemFeatured, then api/itemListingPreferences.ts::setItemFeatured, then PUT …/featured. set_item_featured resolves the profile, then inside mapped_transaction_conflicts:

  1. require_item_visible (missing or hidden → 404).
  2. Lock the Party row FOR NO KEY UPDATE, the item (ownership → 403) and the preference (409 when missing).
  3. When featuring and not yet featured: read the limit via settings_acl, check limit 0, then count the others.
  4. Set or clear featured_at, commit, refresh, return.
Read path and ordering

One column is added to the shared select, to each consumer's outer select (term, owner, event window) and to the _my_items select. The flag is mapped in each builder, with no extra statements. Ordering is done in SQL with the leading key featured_at DESC NULLS LAST, plus the stable re-sort in termViewModel; eventViewModel keeps the server order. item_id stays the final key, so pagination is deterministic.

Settings, boundaries, caching

load_settings reads the row fresh. update_settings locks the row, compares updated_at (naive UTC), sets the value and commits. app.settings is imported only by main.py and groups/infrastructure/settings_acl.py, and code in app/settings imports only app.core/app.db/app.settings (boundary test). Personalised cache headers on public routes are unchanged; the admin routes send no cache headers; the frontend mutation awaits invalidation of the settings prefix.

Success Criteria

  • Up to N items can be featured. N+1 → 409 with N. Limit 0 → the "disabled" 409. A race never exceeds N.
  • Featured items come first (most recent first) on term, event, owner, profile and organization pages, and take the 3 preview slots.
  • The badge shows in every listed placement and never in search or on wants cards.
  • An admin can change the limit; a stale save → 409; non-admin → 403.
  • Unlist and hand-over clear the mark; a lowered limit keeps marks.
  • 0110–0111 upgrade and downgrade cleanly. New and updated tests pass with no new lint or type findings beyond the baseline.
