TL;DR

Eight decision areas, 31 alternatives explored. Recommended combination: 9-digit numeric code + in-process per-(user, group) failed-attempt limiter with 429, stored as one plaintext nullable column on groups, verified per group id with compare_digest, lazily created on the organizer's first read and rotated only by an explicit organizer action, entered through a ModalSheet-based JoinByCodeSheet opened from the existing gate with ?code= prefill + one-shot auto-submit, with existing PENDING requests abandoned at cutover (two migrations: additive 0059, destructive 0060).

The limiter is the load-bearing assumption: if it is dropped from the first iteration, the format must switch to 8-char Crockford Base32 (40 bits) — not 9 unthrottled digits. Every alternative stays inside "how to implement join-by-code"; approval toggles, per-invite codes, expiry and organizer notifications are deferred.

Key Decisions

  • 9 digits only as a pair with the limiter — 29.9 bits sits below NIST's 64-bit "no throttle needed" line but 1 000× above the 6-digit OTP floor; matches the user's reference product and the existing numeric input pattern (CapacityField).
  • Plaintext column on groups, no separate table — the organizer must read/copy the code; per-invite/expiry/max-uses are not required (minimal-implementation J1).
  • Per-group verification endpoint POST /api/groups/public/{id}/join-code — keeps the full 109 space.
  • In-process limiter keyed by (party_id, group_id) — single-instance OAuth2 store precedent; DB counters on groups would fight the updated_at optimistic lock.
  • Lazy get-or-create on organizer GET …/join-code — no backfill, no new side effect in create/update.
  • Idempotent 200 created:false for members and one generic 409 for "wrong code / no code yet" — no existence oracle.
  • PENDING rows abandoned (documented) rather than auto-approved — pre-production; auto-approve script is the fallback.

Open Questions / Risks

  • warningOperator must accept the limiter as a hard prerequisite of 9 digits; otherwise flip to Crockford-8 (1B).
  • warningRestart resets the in-process counter (negligible at 109); scaling to >1 worker weakens it by the worker count — same caveat as the OAuth2 stores.
  • infoDouble submit can create two active Membership rows (OQ-8) — busy guard + _is_active_member only; partial unique index deferred.
  • inforeturnTo not validated same-origin (OQ-10); ?code= links increase login round-trips — tiny startsWith("/") guard as a stretch item.
  • infoProduct-pattern references (Classroom, Slack) are second-hand; the recommendation rests on entropy math and the user's reference.

Problem reframing — How Might We

Research question: Jak dobrze zaimplementować dołączanie do grupy prywatnej (GroupVisibility.PRIVATE) przez kod dostępu, rezygnując całkowicie z mechanizmu "poproś o dostęp"? User framing: "poprawić zapisywanie się na termin do grupy prywatnej"; reference product = 9-digit numeric code shared by the organizer. Full replacement is the user's decision; hybrid approval toggle is deferred only.

Inherited constraints: login required (A1); reduced /access, no existence oracle (A2/A4/L9); membership only via add_active_membership (A5); service-level organizer checks (N1); no rate limiting / Redis / 429 today (V5); standards A–K; single-instance deployment.

Decision Area 1 — Code format & brute-force protection (coupled)

1A · 9 digits + per-user limiter (429) recommended

^[0-9]{9}$, secrets.choice, shown 123 456 789; 10 failures / 15 min per (party, group).

Strengths

Matches the reference; numeric keypad; fits validation.md F2 / CapacityField; no O/0 normalisation; ≈1 400 years to guess with limiter (F6).

Weaknesses

29.9 bits < 64 — security contingent on the limiter (F4); multi-account attackers pay registration per 10 tries.

Best when

Limiter ships in the same iteration; single instance.

Evidence: external F4, F6; synthesis C10, §5.2; report §5.2.

1B · 8-char Crockford Base32, limiter optional

40 bits, XXXX-XXXX, normalise case and O→0, I/L→1.

Strengths

1 100× larger space; ~105 000 years unthrottled; decouples from limiter correctness; Misskey precedent (F3).

Weaknesses

Letters on mobile; new normaliser + input pattern; diverges from reference; harder to dictate in Polish.

Best when

Limiter is deferred or distrusted.

Evidence: F2, F3, F6; synthesis C10.

1C · 10–12 digits, no limiter

Buy entropy with length (10 = 33.2 bits, 12 = 39.9).

Strengths

Keeps numeric UX; no 429 handler; 12 ≈ Crockford-8.

Weaknesses

10 still needs a limiter under F4; 12 is long to dictate; drifts from reference.

Best when

Numeric UX non-negotiable and no limiter accepted.

Evidence: F4, F6 (10-digit row computed in synthesis).

1D · Link-only opaque token

token_urlsafe in ?invite=; no field.

Strengths

128 bits, no limiter; trivial generation (OAuth2 store precedent).

Weaknesses

Contradicts "typed code" model; no verbal sharing; secret only in URLs (R3); F1 says not for human codes.

Best when

Sharing always digital; no typed code wanted.

Evidence: F1; report R3.

Decision Area 2 — Where the code lives

2A · Plaintext nullable column groups.join_code recommended

String(9), nullable, no index, no uniqueness; never in GroupResponse/PublicCircleResponse.

Strengths

models.md A1 plain columns; additive precedent 0056/0058; lookup by group id then compare_digest; shares group lifetime and soft-delete for free.

Weaknesses

Plaintext at rest (low-value, revocable — C3); no history / attribution.

Best when

One shared code per group with organizer rotation — the whole requirement.

Evidence: backend-reusable §2 Option A; report §5.1; synthesis C3.

2B · Separate group_join_codes table

Per-invite rows with expiry, max-uses, revocation.

Strengths

Audit trail; revoke one invite; home for expiry later.

Weaknesses

Nothing in the brief needs it (J1); full BaseEntity conventions; expiry collides with naive-UTC / freeze_local_now (E1/E4); card becomes a list.

Best when

Per-person or time-boxed invites become a requirement.

Evidence: report §5.1 Option B; synthesis C4; checklist E1/E4, J1.

2C · Hashed column, show-once

Store sha256(code); show plaintext only after generation.

Strengths

DB dump reveals nothing.

Weaknesses

Breaks "Kopiuj kod" on later visits; regenerate-to-see invalidates others' links; no standard requires it (A11).

Best when

High-value content or regulatory pressure.

Evidence: synthesis C3; checklist A11; report D8.

2D · Derived / no storage (HMAC)

HMAC(JWT_SECRET, group_id) truncated to 9 digits.

Strengths

No migration; always exists.

Weaknesses

No rotation without a salt (= storage); id-derived values are "not a secret" here; tied to JWT_SECRET.

Best when

Never for this brief — validates that storage is needed.

Evidence: report §5.2; synthesis §9.

Decision Area 3 — Attempt limiter placement

3A · In-process dict, sliding window recommended

dict[(party_id, group_id)] → (failures, window_start) on time.monotonic; TooManyAttemptsException → 429 + Retry-After; cleared on success; pruned on check.

Strengths

Zero dependencies; precedent app/oauth2/stores.py + security.md l.67; injectable clock; no DB writes on failure path; respects time.md.

Weaknesses

Resets on restart (one extra burst of 10); per-process only.

Best when

Single-instance deployment — the documented state.

Evidence: synthesis C5; report §5.3; config-inventory §4.

3B · DB-backed counter table / Core UPDATE

Strengths

Survives restarts and multiple workers; auditable.

Weaknesses

New table for a counter (J1); counter on groups bumps updated_at → 409 for organizer PATCH; writes per failure; separate commit needed.

Best when

Multi-worker / multi-host arrives.

Evidence: report §5.3 rows 2-3; backend-migrations §5 Q3.

3C · No limiter — rely on entropy

Strengths

Smallest change; no 429, no exception, no test.

Weaknesses

F4 still requires a limiter below 64 bits; leaves OQ-3 untouched; forces 1B/1C-12.

Best when

Speed over rule-compliance, with Crockford-8.

Evidence: F4, F6; OQ-3.

3D · Reverse-proxy limit_req (nginx)

Strengths

No app code; stops dumb bots.

Weaknesses

Per-IP only — the documented failure mode (F5); NAT collateral throttling; config not inspected; cannot key on user.

Best when

As a complement in production, never alone.

Evidence: F5; report §5.3 row 5; synthesis §7.

Decision Area 4 — Generation & rotation semantics

4A · Lazy get-or-create on organizer GET recommended

Strengths

No backfill; no side effect in create/update (keeps test_group_privacy.py:139-162 valid); precedent get_or_create_active_group_role; old PRIVATE groups covered.

Weaknesses

Redeem before first organizer view → generic 409 (acceptable); side-effecting GET (precedented).

Organizer surface always fetches the code for PRIVATE groups.

Recommended approach — the combination

1A 9 digits + per-user limiter · 2A plaintext groups.join_code · 3A in-process limiter, 429 + Retry-After · 4A lazy get-or-create, explicit regenerate · 5A JoinByCodeSheet on ModalSheet, ?code= prefill + one-shot auto-submit · 6A abandon PENDING with count check · 7A 401→404→429→409→200 idempotent · 8A card on GroupDetailsPage + stepper, hidden on 403.

Rationale: the only combination that honours the user's reference (typed 9-digit code) while satisfying the entropy rule (throttle below 64 bits), with zero new dependencies, zero changes to /access, create_rsvp or the organizer page, the smallest schema delta, and every UI piece on an existing shell.

Trade-offs accepted

  • Format security depends on shipping the limiter.
  • Plaintext at rest; revocation only by regenerating for everyone.
  • Limiter state per process, reset on restart.
  • PENDING requests not migrated.
  • Extra 403 request for members on GroupDetailsPage.

Key assumptions (if wrong → change)

  1. Single uvicorn process/instance → else 3B, or 1B to decouple.
  2. Limiter ships in the same iteration → else 1B; never 9 unthrottled digits.
  3. PENDING ≈ 0 at cutover → else 6B with organizer consent.
  4. Term link stays the shared artefact → else 5D.
  5. No external API consumer needs distinct statuses → else 7B.
