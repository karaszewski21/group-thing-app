# External: Google ID-token verification, discovery/JWKS caching and Python libraries

## TL;DR
- Verify locally (never via `tokeninfo` in production): RS256 signature against Google's JWKS, `iss` ∈ {`accounts.google.com`, `https://accounts.google.com`}, `aud` == aj's client ID, `exp` in the future, `nonce` == the value aj issued (if sent), and `hd` only if restricting to a Workspace domain.
- Key the account on `sub` (+ issuer); email is a lookup hint only. `email_verified` is authoritative only for `@gmail.com` or when `hd` is set; otherwise Google is "not authoritative" for that email.
- PyJWT (already a dependency) covers everything: `PyJWKClient` + `jwt.decode(..., algorithms=["RS256"], audience=CLIENT_ID, issuer=[both], options={"require": [...]})`. No need for google-auth (sync, `requests`-based, refetches certs every call unless wrapped) or Authlib (adds a session middleware and a dependency).
- `PyJWKClient` is synchronous (blocking HTTP) with a fixed-TTL cache (`lifespan`, default 300 s), not Cache-Control-driven — call it from a threadpool / at startup, or fetch the JWKS with the existing `httpx` client and build `jwt.PyJWKSet`.

## Key Decisions
- Use PyJWT rather than google-auth/Authlib — already pinned (`pyjwt>=2.13`), supports issuer containers, JWKS, `require`, leeway; google-auth would pull `requests`/`cachetools` and still need manual `hd`/nonce checks.
- Pin `algorithms=["RS256"]` — discovery lists only RS256; never derive the algorithm from the token header (alg-confusion).
- Store `sub` as the identity key with the issuer — OIDC Core §5.7: iss+sub "the only guaranteed unique identifier".

## Open Questions / Risks
- Exact Google JWKS `Cache-Control` max-age was not measured (docs say keys rotate "regularly"/"roughly once per day"; Medium confidence). A 300 s–1 h TTL plus PyJWKClient's unknown-`kid` refresh is safe either way.
- Clock skew: aj's VPS clock drift is unknown; a small `leeway` (≤ 60 s) is customary but not mandated by Google.
- PyJWT's `issuer` accepts a `Container[str]` per API docs (fetched 2026-11-25); behaviour verified only by docs, not by running code against the pinned version.

## 1. Verification rules (Google)

**Source**: https://developers.google.com/identity/gsi/web/guides/verify-google-id-token
**Evidence** (quoted):
- "The ID token is properly signed by Google." Keys in JWK or PEM form; "These keys are regularly rotated; examine the `Cache-Control` header in the response to determine when you should retrieve them again."
- "The value of `aud` in the ID token is equal to one of your app's client IDs."
- "The value of `iss` in the ID token is equal to `accounts.google.com` or `https://accounts.google.com`."
- "The expiry time (`exp`) of the ID token has not passed."
- `hd`: "This must be used when restricting access to a resource to only members of certain domains."
**Confidence**: High (100%).

**Source**: https://developers.google.com/identity/openid-connect/openid-connect ("Validating an ID token", "An ID token's payload")
- Same five checks; the `tokeninfo` endpoint is for debugging only — production validation should be local.
- "Always use the `sub` field as it is unique to a Google Account even if the user changes their email address." `email` "may not be unique to this account and could change over time"; you "can't rely on the domain of the `email` claim to identify users" of Workspace orgs — use `hd`.
- "Standard HTTP caching headers are used and should be respected" for the keys.
- Nonce: "a random value generated by your app that enables replay protection"; present it only once.
**Confidence**: High (100%).

### Email trust rules
**Source**: verify-google-id-token page (section "Get user info / account lookup")
- `email` ending `@gmail.com` → Gmail account (Google authoritative).
- `email_verified` true **and** `hd` set → Google Workspace account (authoritative).
- Otherwise (non-Gmail address, no `hd`): "Google is not authoritative and password or other challenge methods are recommended to verify the user." The page also warns that ownership of a third-party email may have changed even if `email_verified` is true.
- "a Google Account can have multiple email addresses at different points in time" — store `sub`; email may still be used "to look for an existing account".
**Relevance**: drives the auto-link policy in `external-google-security-linking.md`. **Confidence**: High (95%).

### OIDC Core cross-check
**Source**: https://openid.net/specs/openid-connect-core-1_0.html §3.1.3.7, §5.7
- `iss` "MUST exactly match"; `aud` "MUST" contain `client_id`, reject untrusted extra audiences; `azp` should equal client_id when present; `exp` "MUST" be in the future; `iat` may bound token age; `nonce` "MUST be present and its value checked" if sent, and the client should check for replays.
- §5.7: "The sub (subject) and iss (issuer) Claims … are the only Claims that an RP can rely upon as a stable identifier … an Issuer MAY re-use an email Claim Value across different End-Users at different points in time … email, phone_number, preferred_username, and name MUST NOT be used as unique identifiers."
- For ID tokens received directly from the token endpoint over TLS, TLS server validation may stand in for signature checking (§3.1.3.7) — still cheap to verify the signature, and mandatory for GIS-delivered tokens which arrive via the browser.
**Confidence**: High (100%).

## 2. Discovery document and JWKS

**Source**: https://accounts.google.com/.well-known/openid-configuration (live, 2026-11-25)
- `jwks_uri` = `https://www.googleapis.com/oauth2/v3/certs`; `issuer` = `https://accounts.google.com` (note: tokens may still carry the scheme-less `accounts.google.com`, hence the two-value issuer check); signing alg RS256 only.
- Recommendation (Google): hard-code the discovery URL, read endpoints from it. Practical alternative for a single provider: hard-code the three endpoints as constants (they have been stable for years) and skip a startup network call — trade-off for the synthesizer.
**Confidence**: High.

## 3. Library comparison (Python)

| | PyJWT `PyJWKClient` + `jwt.decode` | google-auth `id_token.verify_oauth2_token` | Authlib Starlette client |
|---|---|---|---|
| Already a dependency | **Yes** (`pyjwt>=2.13`) | No (+`requests`, `cachetools`, `pyasn1-modules`, `rsa`) | No (+`itsdangerous` SessionMiddleware) |
| Async | No (blocking fetch) — run in threadpool or prefetch | No (`requests` transport) | Yes (httpx) |
| Key caching | JWK Set cache TTL `lifespan` (default 300 s), per-key LRU optional, auto-refresh on unknown `kid` with `cooldown_duration` 30 s | **None by default** ("re-fetched for every verification"); docs recommend wrapping a `requests` session in CacheControl | Fetches JWKS from metadata; cached per app instance |
| iss check | `issuer=` str or Container (both Google values) | Built in (both values) | Built in from metadata |
| aud / exp | Built in | Built in (aud skipped if None!) | Built in |
| nonce | Manual compare | Manual | Automatic (stored in session) |
| hd / email_verified | Manual | Manual | Manual |
| Code flow plumbing (state, PKCE, exchange) | Manual with `httpx` | N/A | Built in (`authorize_redirect`, `authorize_access_token`) |
| Fits aj conventions | Hand-rolled auth already uses PyJWT; testable with a local RSA key + fake JWKS | Google-specific | Requires session middleware aj doesn't use; state in signed cookie |

**Sources**:
- PyJWT usage: https://pyjwt.readthedocs.io/en/stable/usage.html — `PyJWKClient(url)`, `get_signing_key_from_jwt(token)`, "If the `kid` is not found in the current key set, PyJWKClient automatically refreshes the JWKS"; OIDC example with discovery + `decode_complete` + `at_hash`; `options={"require": ["exp", "iss", "sub"]}`.
- PyJWT API: https://pyjwt.readthedocs.io/en/stable/api.html — `PyJWKClient(uri, cache_keys=False, max_cached_keys=16, cache_jwk_set=True, lifespan=300, headers=None, timeout=30, ssl_context=None, cooldown_duration=30)`; `issuer: str | Container[str] | None`.
- google-auth: https://googleapis.dev/python/google-auth/latest/reference/google.oauth2.id_token.html — `verify_oauth2_token(id_token, request, audience=None, clock_skew_in_seconds=0)`; "If None, the audience is not verified"; certs refetched per call by default.
- Google recommends its client libraries ("strongly recommend using a Google API client library") — verify-google-id-token page; but any JWT library performing the same checks is acceptable per OIDC Core.
- Authlib: Starlette/FastAPI integration (https://docs.authlib.org/ — the `/en/latest/client/starlette.html` URL from sources.md returned 404 on 2026-11-25; content corroborated via Debian-packaged docs https://sources.debian.org/src/python-authlib/1.6.6-1/docs/client/fastapi.rst and https://blog.authlib.org/2020/fastapi-google-login): `oauth.register(name="google", server_metadata_url=..., client_kwargs={"scope": "openid email profile"})`, needs `SessionMiddleware` to keep state/PKCE between redirect and callback; behind a reverse proxy `url_for` may produce `http://` URLs (proxy headers needed). **Confidence**: Medium (70%).

**Note on PyJWKClient sync-ness / Cache-Control** (Medium 75%): the docs show blocking calls and a fixed `lifespan`; they do not say it honours `Cache-Control`. From PyJWT source knowledge it uses `urllib.request`. In an async FastAPI handler, call `await run_in_threadpool(client.get_signing_key_from_jwt, token)` or prefetch keys with `httpx.AsyncClient` into `jwt.PyJWKSet.from_dict(...)` and refresh on unknown `kid`.

## 4. Reference verification sketch (PyJWT, illustrative)

```python
GOOGLE_ISSUERS = ("https://accounts.google.com", "accounts.google.com")
key = jwks_client.get_signing_key_from_jwt(id_token)          # in threadpool
claims = jwt.decode(
    id_token, key.key, algorithms=["RS256"],
    audience=settings.google_client_id, issuer=GOOGLE_ISSUERS,
    options={"require": ["iss", "aud", "sub", "exp", "iat"]}, leeway=30,
)
if expected_nonce is not None and not hmac.compare_digest(claims.get("nonce", ""), expected_nonce):
    raise InvalidGoogleToken
sub, email = claims["sub"], claims.get("email")
email_trusted = bool(claims.get("email_verified")) and (
    (email or "").lower().endswith("@gmail.com") or "hd" in claims)
```
Test strategy: generate an RSA key in the test, serve/stub a JWKS, sign tokens with each failing claim — no network to Google in pytest (inference; consistent with aj's testcontainers-only external deps).
**Confidence**: High (85%) for the rules; the snippet is illustrative, not run.
