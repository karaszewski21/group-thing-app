TL;DR

  • I compared 20 alternatives across 5 decision areas, ordered so that each earlier choice constrains the later ones.
  • Recommendation: use the GIS popup button, which posts the ID token with a server nonce cookie (1A). The aj token comes back in the JSON response (2A). On an email collision, refuse with a Polish 409; linking from settings comes later (3A). Every Google account starts as GUEST, the same as password sign-up (4C). v1 is a lean Google-only MVP (5B).
  • Correction to the research: RegisterForm no longer has a role chooser. It always sends role: "GUEST" (AuthContext.tsx:136, RegisterForm.tsx:7-9). Founding an Organization grants ORGANIZATOR later (organizations/service.py:184-189). So the proposed role request parameter is not needed.
  • Switch rule: choose the server code flow (1B + 2B) instead of 1A if the owner treats any of these as a must-have: the custom pill button, no Google script on aj pages, or Facebook next. The verifier and resolver are shared, so the backend barely changes.
  • Confidence: high for areas 2–5, medium-high for area 1 (it depends on how much weight the owner gives the in-page AuthSheet UX).

Key Decisions

  • Browser flow 1A (GIS popup + ID token + nonce cookie). It keeps the in-page AuthSheet login on six public surfaces, needs no client secret or redirect URIs, and has the fewest routes (2).
  • Handoff 2A (JSON {token, created, party_id} in the POST response). The frontend stays the single session writer, no token appears in a URL and there is no server store.
  • Collision policy 3A (409 "zaloguj się hasłem", no merge). aj never verifies emails and cannot revoke JWTs, so every merge-by-email variant opens the USENIX 2022 pre-hijack.
  • Role 4C (always GUEST, no role parameter). This matches password registration as it exists today, and the organizer path (founding an Organization) already exists.
  • Scope 5B. v1 has sign-in and sign-up, two migrations, the verifier, resolver and button, the deploy config and the docs. Linking/unlinking from settings, avatar import, setting a password, RISC and Facebook are deferred.

Open Questions / Risks

  • ownerOwner call on area 1: is the Google-rendered button acceptable, or is the custom pill a hard requirement? Is Facebook due in the next iteration? A "yes" to either flips the choice to 1B + 2B.
  • uxPopup blocking in in-app browsers (Instagram, Messenger and others) with 1A. It is not measured. If it shows up in practice, the fallback is 1E (adding the code flow next to the popup).
  • uxThe GIS iframe inside the focus-trapped AuthSheet (trapFocus.ts) and at narrow mobile widths has not been tried.
  • uxStrict 409 friction: existing password users who click Google get a refusal until "Połącz z Google" (deferred, D1) ships. Clear Polish copy is the mitigation.
  • prodProduction prerequisites outside the code: a domain, /about/privacy and a homepage are needed for brand verification. They block a branded production consent screen, but not the development work.
  • acceptedAccepted risks: no session revocation (1 h JWT) and no recovery for Google-only users who lose their Google account.

Problem Reframing

Research question: How should aj implement login and registration with a Google account end to end, consistently with the existing auth architecture and project standards?

The research settled the core (synthesis §9, report §12). Google is an upstream identity source that ends in encode_login_token with DB permissions. Accounts are keyed on user_identities (provider, subject) (0107), with a nullable password_hash and a guarded downgrade (0108). The verifier uses pyjwt[crypto]. app/oauth2, session.ts, proxy.ts and AuthGuard stay unchanged. This document covers only the decisions still open on top of that core.

  1. HMW-1 (flow): How might we let a visitor sign in with Google from any of the six AuthSheet surfaces without losing their page context, while keeping the attack surface and the config burden small?
  2. HMW-2 (handoff): How might we deliver the aj JWT to the browser so that setSession stays the only writer, the token never sits in a URL, and the solution works with several workers and survives restarts?
  3. HMW-3 (collision): How might we treat a Google sign-in whose email already belongs to an aj account without opening a pre-account-hijack window, given that aj has no email verification and no revocation?
  4. HMW-4 (role): How might we give a Google sign-up the same starting role and onboarding as a password sign-up, without a new decision point that the password path lacks?
  5. HMW-5 (scope): How might we draw the v1 line so that it ships a complete, safe sign-in while every deferred item stays cheap to add later?

Decision dependencies: area 1 determines area 2 (an ID-token popup has a natural JSON handoff, while a redirect flow needs an explicit handoff). Area 3 determines what area 5 must defer (the safe link path). Area 4 is mostly independent, but its options are constrained by where the button sits (AuthTabs.tsx:59, above both tabs).

Area 1: Browser flow

1A. GIS popup + ID token recommended

lib/googleIdentity.ts loads accounts.google.com/gsi/client lazily, following the googleMaps.ts pattern. renderButton in popup mode hands a credential (ID token) to a JS callback, and loginWithGoogle POSTs it as JSON to /api/auth/google. Before that, a GET /api/auth/google/nonce sets a signed HttpOnly g_nonce cookie, and the token must carry that nonce.

Strengths
  • AuthSheet stays in-page, a documented design intent on six conversion surfaces (F9, AuthSheet.tsx:9-32)
  • No client secret, no redirect URIs and no PUBLIC_BASE_URL (so the nginx base-URL bug in F11 does not apply)
  • Only two routes; the Google button is always on-brand (F14); One Tap is easy to add later
Weaknesses
  • Loads a third-party script and iframe, so a future CSP must list accounts.google.com/gsi/* (F12)
  • Popups can be blocked in in-app browsers
  • The button is Google-rendered, at a fixed pixel width, and has not been tested inside trapFocus
  • Google-specific, so Facebook would need another flow
Best when

The in-page AuthSheet login matters most and Google is the only provider in sight.

Evidence

F7(b), F9, F10, F13, F14; report §5.1, §7.2; synthesis insight 3.

1B. Server code flow, full redirect

A custom pill button navigates to /api/auth/google/start. The backend sets a signed g_tx cookie (state, nonce, PKCE verifier, returnTo) and 302s to Google. /callback exchanges the code using GOOGLE_CLIENT_SECRET and verifies the ID token. The aj token then reaches the frontend through a handoff (area 2).

Strengths
  • The custom button is allowed if it follows the branding rules (F14)
  • No Google script runs on aj pages; redirects are robust in in-app browsers
  • Works for any provider, so Facebook would reuse it (F15)
  • Textbook RFC 9700 protections (state + nonce + PKCE S256)
Weaknesses
  • The visitor leaves the page, which breaks the AuthSheet promise; only sessionStorage-backed state such as join codes survives
  • Needs a secret in the backend env, redirect URIs for each environment and an explicit PUBLIC_BASE_URL (F11)
  • Three routes plus a landing page and a handoff mechanism; a long returnTo (seven OAuth2 parameters, F3) must survive the round trip
Best when

The custom pill, a page free of third-party scripts or Facebook readiness are must-haves.

Evidence

F7(a), F11, F15; report §5.2, §7.2; synthesis insights 4–5.

1C. GIS redirect mode (login_uri)

The same Google-rendered button, but Google POSTs the ID token as a form to a backend login_uri, protected by a g_csrf_token double-submit cookie. The backend verifies it and hands off to a landing page.

Strengths
  • No secret and no popup, so it is robust in in-app browsers
  • Reuses the ID-token verifier exactly
Weaknesses
  • Leaves the page like 1B, without 1B's custom button or provider generality
  • Accepts a cross-site form POST, which needs g_csrf_token handling and conflicts with the JSON-only CSRF stance (synthesis insight 6)
  • Still needs a handoff and a landing page, a login_uri for each environment and the base URL
Best when

Popups must be avoided but a client secret cannot be held. aj has no such constraint.

Evidence

F7(b); report §7.2 (third column); synthesis §8.2 (rejected).

1D. GIS code client in popup mode

A custom aj button calls google.accounts.oauth2.initCodeClient(...).requestCode(). The popup returns an authorization code to JS, which POSTs it to /api/auth/google/code. The backend then exchanges it, using the secret and redirect_uri: "postmessage", and verifies the ID token.

Strengths
  • Keeps the AuthSheet in-page and allows the custom pill, so it combines the main advantages of 1A and 1B
  • The response is JSON, so handoff 2A applies
Weaknesses
  • Needs the client secret and a server token exchange (the costs of 1B) plus the script and popup risks (the costs of 1A)
  • CSRF protection relies on a X-Requested-With-style header plus state
  • Less common for pure sign-in; its docs are aimed at API authorization; still Google-specific
Best when

The custom button and the in-page sheet are both hard requirements.

Evidence

Synthesis insight 3 ("the code-client popup still needs a secret and an exchange"); F7, F14.

1E. Hybrid: 1A primary, 1B fallback

Ship the GIS popup on all surfaces. Also expose the code flow as a fallback link ("Nie działa? Kontynuuj w nowym oknie"), shown when GIS fails to load or the popup is blocked, or detected for in-app browsers.

Strengths
  • In-page UX for most users, robustness for the rest, and Facebook-ready plumbing
  • The shared verifier and resolver make running both cheap on the backend (report §7.2)
Weaknesses
  • The full config and secret burden of 1B plus the script of 1A
  • Two flows to test, two sets of console entries, the largest surface
  • Detecting a blocked popup is heuristic
Best when

Real usage shows popup failures on a meaningful share of traffic.

Evidence

Report §7.2 recommendation paragraph; SWOT threat "Popup blocking (A)".

Area 2: Token handoff

Constrained by area 1: 1A and 1D return JSON to a fetch, so 2A is the natural fit. 1B, 1C and 1E's fallback end on a backend redirect and need one of 2B–2E.

2A. JSON body of the POST recommended

POST /api/auth/google returns {token, created, party_id}, and AuthContext calls applyToken → setSession just as login and register do.

Strengths
  • Matches F1 exactly (the same shape as LoginResponse/RegisterResponse)
  • The token never appears in a URL, cookie or store, and nothing new is needed
  • Login CSRF is structurally blocked by JSON-only delivery (insight 6)
Weaknesses
  • Only works when the browser holds the Google credential in JS, so 1A or 1D
Best when

Area 1 is 1A or 1D.

Evidence

F1, insight 6, report §5.1 step 6-7.

2B. HttpOnly handoff cookie + JSON exchange

The callback sets g_handoff=<aj JWT>; HttpOnly; SameSite=Lax; Path=/api/auth/google; Max-Age=60 and 302s to /login/google?returnTo=…. That page POSTs /api/auth/google/exchange, which returns {token} and clears the cookie.

Strengths
  • The token stays out of URLs and history
  • No server store, so it works with several workers and survives restarts
  • setSession stays the single writer
Weaknesses
  • A route, a landing page (a thin route file plus a feature entry) and a cookie that can be read in transit for 60 s (HttpOnly keeps it from JS)
  • The backend sets a cookie that holds a credential for the first time
Best when

Area 1 is 1B, 1C or 1E.

Evidence

Report §5.2, synthesis insight 4.

2C. One-time code + server store

The callback stores {random code → user_id, exp 60 s} and redirects with ?code=…. The landing page POSTs the code to get the token. The store is either a new DB table or the per-process memory store that the OAuth2 server uses.

Strengths
  • The conventional pattern (it mirrors OAuth2 itself)
  • The URL carries only a short-lived one-time code, never the JWT
Weaknesses
  • The in-memory OAuth2 stores are per process (synthesis insight 4), so with more workers or a restart the exchange fails
  • A DB table means a third migration plus a purge job
  • The code still appears in the URL, history and referrer, even though it is single-use
Best when

You already have a shared store such as Redis. aj does not.

Evidence

Synthesis insight 4 (OAuth2 stores are per-process memory), F3.

2D. Token in the URL fragment

The callback 302s to /login/google#token=<JWT>. The page reads location.hash, calls applyToken and wipes the hash with history.replaceState.

Strengths
  • The simplest redirect handoff, with no store and no exchange route
  • The fragment is not sent to servers
Weaknesses
  • A bearer credential is readable by browser extensions and can land in history or a session-restore cache before it is wiped
  • Looks like the implicit-flow anti-pattern (RFC 9700 §2.1.2 spirit) and contradicts the checklist item "never in a query, fragment or Location header"
Best when

Never for a full-scope 1 h session token. Listed for completeness.

Evidence

Report §8 flow integrity; F7 (implicit flow must not be used).

2E. Backend sets auth_token

The callback sets the same auth_token cookie the frontend writes and redirects to returnTo. The frontend then picks up the cookie.

Strengths
  • Needs no landing page and no exchange route
Weaknesses
  • Forks the single-writer rule (F1)
  • A stale valid localStorage token beats the cookie (session.ts:87-88), which can log the user into the wrong account
  • The backend becomes a session-cookie setter, which reopens the login-CSRF analysis
Best when

localStorage is dropped entirely, which is out of scope.

Evidence

Synthesis §3.2 ("Backend-set cookie handoff", resolved as rejected).

Area 3: Existing-email collision and account linking

3A. Refuse with 409; link from settings later recommended

If a Google sub is unlinked and its email matches any user_profiles row (account or login-less), return 409 "Konto z tym adresem już istnieje — zaloguj się hasłem". Linking becomes a later "Połącz z Google" action for a logged-in user (POST /api/auth/google/link, EDIT).

Strengths
  • Opens no hijack window
  • Mirrors DuplicateEmailException (an established Polish 409), so it leaks no more than register already does
  • The least code, and it works whatever happens with email verification
Weaknesses
  • Existing password users who click Google meet a dead end until the link feature ships
  • One person can never have both credentials in v1
Best when

Email ownership is unverified and sessions cannot be revoked, which is aj today.

Evidence

F5, F8, report §7.3, synthesis insight 2.

3B. Link after password re-auth in the same flow

On a collision, the backend returns 409 with a signed, short-lived "link ticket" cookie holding the verified Google sub. The UI asks for the aj password, and POST /api/auth/google/link-with-password {password} checks the password and the ticket, links the identity and logs in.

Strengths
  • Safe against the pre-hijack: the victim does not know the attacker's password, and the attacker proving it only links the attacker's own Google
  • Turns the dead end into a two-step success; existing users get Google login on first try
Weaknesses
  • A ticket cookie, a route, password-entry UI inside the sheet and brute-force exposure on a new password-check endpoint (no rate limiting today, §8)
  • Does not help users who forgot their password, because there is no reset
  • Essentially phase-2 linking pulled into v1
Best when

There are many existing password users and Google adoption among them is a v1 goal.

Evidence

F8 (the defence is proof of ownership), F4 (no reset), report §8 (no rate limit on login).

3C. Auto-link when Google vouches and aj email verified

Link automatically when Google's email is authoritative (@gmail.com, or email_verified + hd) and the aj profile email is marked verified.

Strengths
  • The industry-standard frictionless policy, safe once both sides are verified
Weaknesses
  • aj has no verified state for any email (F5), so the branch never fires without an email-verification feature (sending mail, tokens, UI)
  • That is a separate project, well beyond this research question; until then it behaves exactly like 3A
Best when

Email verification exists.

Evidence

F5, F6, synthesis §3.2 ("Account linking" contradiction resolved).

3D. Auto-link and null the password

Merge into the existing account and set password_hash to NULL, so that an attacker's pre-set password stops working.

Strengths
  • No friction, and it applies the paper's "invalidate the password" defence
Weaknesses
  • An attacker's live JWT survives up to 1 h, because nothing can revoke it (F1)
  • Silently removes a legitimate user's password, and there is no reset to recover
  • Explicitly rejected by the research
Best when

A per-user token cutoff exists and password removal is announced. Neither is true today.

Evidence

F8, synthesis §3.2 ("Session revocation" resolved), report §7.3 (rejected).

Area 4: Role at Google sign-up

fact correction The research proposed an optional role because "GUEST or ORGANIZER is chosen in RegisterForm". The current RegisterForm has no chooser ("every new account starts as a guest", RegisterForm.tsx:7-9), and AuthContext.register always sends role: "GUEST" (AuthContext.tsx:136). The backend schema still accepts Literal["GUEST","ORGANIZER"] (users/schemas.py:132). Founding an Organization grants the global ORGANIZATOR role (organizations/service.py:184-189).

4A. Optional role param, default GUEST

POST /api/auth/google {credential, role?} passes the role to bootstrap_person_account. It is ignored for existing accounts.

Strengths
  • Parity with the backend RegisterRequest
  • Ready if an organizer sign-up entry point appears later
Weaknesses
  • No current UI would send ORGANIZER, so it is a speculative parameter (minimal-implementation standard)
  • An extra input means an extra test and an abuse surface (anyone can self-assign ORGANIZER, though the password register API already allows that)
Best when

An "I am an organizer" sign-up entry exists in the UI.

Evidence

Report §5.1, synthesis §8.3; contradicted by the current RegisterForm.

4B. Post-sign-up onboarding chooser

After a created: true response, show a one-step "Kim jesteś?" (GUEST / ORGANIZER) screen before the redirect, backed by a role-update endpoint.

Strengths
  • An explicit choice without crowding the button area
  • Could serve password sign-ups too
Weaknesses
  • A step the password path lacks, plus a new endpoint and a new view state
  • Interrupts the AuthSheet in-page return and duplicates the existing organizer path (founding an Organization)
Best when

The product wants a role choice for every sign-up. That is a product change, not a Google one.

Evidence

F9 (AuthGuard reload and sheet close), organizations/service.py:184-189.

4C. Always GUEST, no role input recommended

Google sign-up creates a GUEST account exactly as password sign-up does today. Organizers become organizers through the existing Organization founding flow.

Strengths
  • Full parity with the current password UX and zero new inputs or decision points
  • Nothing in the resolver depends on the request beyond the credential
  • The standards-preferred minimal option
Weaknesses
  • If an organizer sign-up entry returns, the parameter has to be added then (a small, additive change)
Best when

Password sign-up has no role choice, which is the case today.

Evidence

RegisterForm.tsx:7-9, AuthContext.tsx:136, minimal-implementation standard.

4D. Separate Google buttons per tab

Render the GIS button inside each tab panel ("Zaloguj" with context: "signin", "Załóż konto" with context: "signup"), and have the sign-up tab send a role.

Strengths
  • Google's own copy matches the tab ("Zaloguj się przez Google" or "Zarejestruj się przez Google")
Weaknesses
  • Two GIS button instances must be mounted and unmounted on tab switches; AuthTabs.tsx:59 renders the button once, above both tabs
  • A sign-in on the sign-up tab would still log in an existing account, so the tab is only a hint
  • The role part collapses into 4A or 4C anyway, because the register tab has no role
Best when

The tabs gain role semantics.

Area 5: MVP scope boundary

5A. Minimal sign-in only

Google can only sign in or create accounts. Login does not change for password users, and there are no docs or runbook updates beyond the migrations.

Strengths
  • The fastest to ship
Weaknesses
  • Skips the deploy config, the .env.example and the runbook (the no-image-only-rollback note past 0108 is safety-critical)
  • Leaves the register IntegrityError race (a 500) unfixed in a code path it touches anyway
Best when

A throwaway prototype. aj is not one.

Evidence

Report §6.3, §9; insight 8.

5B. Lean complete MVP recommended

v1 includes migrations 0107 and 0108 with tests and a runbook; a shared bootstrap_person_account with IntegrityError → 409; the login null-hash 401; _load_permissions; pyjwt[crypto] with the verifier and its unit tests; the resolver under policy 3A; the area 1 and 2 routes with matrix rows; the frontend button, loader and loginWithGoogle; Settings, compose, Dockerfile and .env.example; and the docs (tech-stack.md, architecture.md, INDEX.md). The feature is gated on GOOGLE_CLIENT_ID and NEXT_PUBLIC_GOOGLE_CLIENT_ID.

Strengths
  • Covers every item on the report's High-priority list (R2–R7) and nothing speculative
  • Shippable behind the presence gate before the legal pages exist
Weaknesses
  • Existing password users cannot attach Google yet (the 3A friction)
Best when

The default.

Evidence

Report §13 R2–R7, §6.4, §9.

5C. MVP + settings link/unlink

5B plus "Połącz z Google" (link from an authenticated session) and unlink with the "a credential must remain" rule.

Strengths
  • Removes the 3A dead end in the first release
  • The link path is the only safe one (insight 2)
Weaknesses
  • A settings UI surface, a second GIS mount in a panel view, a credential-count rule and more tests: roughly double the frontend work
  • Unlink cannot end live sessions (no revocation)
Best when

Many existing password users are expected to want Google from day one.

Evidence

Report §7.3 phase-2 rows, R9.

5C plus avatar import, setting a password for Google-only users, RISC and Facebook.

Strengths

Weaknesses
  • RISC needs a per-user token cutoff that does not exist (R10)
  • Facebook OIDC is "in testing" and needs its own flow (F15)
  • Avatar import brings SSRF hardening
  • Several features in one: scope creep against the research question

Never as one release.

Recommended Approach

1A + 2A + 3A + 4C + 5B: GIS popup button → POST /api/auth/google (JSON, nonce cookie) → JSON {token, created, party_id} → applyToken. Email collisions get a 409. Every new account is GUEST. v1 is the lean complete MVP.

Primary rationale: the in-page AuthSheet login on six conversion surfaces is the decisive UX factor (insight 3), and 1A is the cheapest option that keeps it: no secret, no redirect URIs, no PUBLIC_BASE_URL, two routes and a JSON handoff identical to the existing login. The collision and role choices follow from the evidence rather than from taste. Unverified emails plus unrevocable JWTs rule out every merge (3A). Password sign-up has no role choice, and an organizer path already exists (4C).

Trade-offs accepted
  • A Google-rendered button instead of the custom pill (F14 says the SDK button is preferred anyway)
  • A third-party script and iframe on auth surfaces; a future CSP must list the gsi sources
  • Popup fragility in in-app browsers (mitigation: 1E later if it is observed)
  • Google-specific in the browser; Facebook would add a flow, but would reuse user_identities and the resolver
  • Existing password users cannot use Google until "Połącz z Google" (D1) ships
Key assumptions (if wrong, revisit)
  1. The custom pill design is not a hard requirement. If it is: 1B + 2B, or 1D + 2A if the in-page sheet is also required.
  2. Facebook is not planned for the next iteration. If it is: 1B + 2B, so that both providers share one flow.
  3. Popups work for the main audience. If in-app-browser traffic proves significant: add the 1B fallback (1E).
  4. Password registration keeps no role choice. If an organizer sign-up entry is added: add the optional role (4A), which is additive.
  5. The number of existing password users who want Google is small enough that the 409 friction is acceptable until D1. If not: pull 5C into v1.

Confidence: medium-high overall. It is high for 2A, 3A, 4C and 5B (forced by the evidence). It is medium-high for 1A, because that depends on assumptions 1–3, which only the owner can confirm.
