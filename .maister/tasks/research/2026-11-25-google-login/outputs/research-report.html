TL;DR

Add Google sign-in as a new identity source that ends in aj's existing login path. The backend verifies the Google ID token with PyJWT + cryptography, resolves the user through a new user_identities table keyed on provider + sub, and returns the usual {token} from encode_login_token. The frontend stores it via applyToken → setSession, and the existing AuthGuard reload takes over. Nothing changes in app/oauth2, session.ts or the proxy. Two migrations are needed (0107 identities, 0108 nullable password_hash with a guarded downgrade). Email-based auto-linking is refused, because aj never verifies emails. Recommended flow: A, a GIS popup that posts the ID token, because it keeps the in-page AuthSheet login. B, the server-side OIDC code flow, is the alternative.

Key Decisions

  • Reuse encode_login_token and JSON token delivery. Every consumer keys off token, and the backend never sets cookies.
  • Use a separate, provider-generic user_identities table, unique on (provider, subject). sub is the only stable key (OIDC Core §5.7).
  • Never auto-link by email. Emails are never verified, so merging would allow a classic-federated-merge pre-hijack, and stateless JWTs can't be revoked to contain it.
  • Use pyjwt[crypto], not google-auth or Authlib. cryptography is absent from uv.lock, and this is the smallest addition that makes RS256 work.
  • Load permissions from the DB with _load_permissions. Otherwise admins who sign in with Google lose ADMIN.
  • Recommend flow A over B. This is a recommendation, not a decision. The trade-off matrix is below.

Open Questions / Risks

  • criticalOwner decision: flow A or B, and whether the custom pill button is a hard requirement.
  • warningProduction prerequisites: a domain, a privacy policy and a homepage on a verified domain (for brand verification).
  • warningSessions can't be revoked. Unlinking, deleting the account or a Google sessions-revoked event can't end a live JWT before exp (1 h).
  • infoThere is no password reset, so a Google-only user who loses their Google account has no fallback.
  • infoRole at sign-up: an optional role (default GUEST), honoured only when the account is created.
  • infoNot yet tested: the GIS iframe inside the focus-trapped AuthSheet, and popup blocking in in-app browsers.

Evidence highlights
  • The JWT is built in app/core/security.py:39-55. Login is at app/auth/router.py:57-87 and register at app/users/router.py:41-51. auth/session.ts:1-5,63-74 writes it; the backend never calls set_cookie.
  • POST /oauth2/authorize calls Depends(require_any()) and stores principal.username (app/oauth2/router.py:316-391). The consent page sends _token (OAuth2AuthorizePage.tsx:28,99-101).
  • password_hash is NOT NULL (app/auth/models.py:50), and verify_password(None) returns a 500 (core/security.py:23-25).
  • Google requires sub as the account key. An email is authoritative only for @gmail.com, or when email_verified is true and hd is set (verify-google-id-token page; OIDC Core §5.7).
  • nginx sets Host $host without the port, and uvicorn runs without --proxy-headers, so resolve_base_url returns http://localhost (metadata_router.py:45-62).
  • Re-checked during synthesis: grep -i cryptography src/backend/uv.lock finds no match.

Recommended flow: request sequences

recommended

A. GIS popup posts the ID token

1. SocialAuthButtons (hidden without NEXT_PUBLIC_GOOGLE_CLIENT_ID)
2. GET /api/auth/google/nonce
   → Set-Cookie g_nonce (signed, HttpOnly, Lax,
     Path=/api/auth/google, 600 s) → {nonce}
3. lib/googleIdentity.ts loads gsi/client;
   initialize({client_id, nonce, callback, ux_mode:"popup"})
   renderButton(locale "pl")
4. Google popup → callback({credential})
5. AuthContext.loginWithGoogle → POST /api/auth/google
   JSON {credential, role?}
6. app/auth/google.py: JSON only, check the nonce cookie,
   verify_google_id_token → resolve_google_sign_in
   → _load_permissions → encode_login_token
   → 200/201 {token, created, party_id?, role?}
7. applyToken → setSession → AuthGuard reload to returnTo
   (AuthSheet closes in place)
8. returnTo /oauth2/authorize → consent _token (unchanged)
alternative

B. Server code flow with a handoff cookie

1. Button → /api/auth/google/start?returnTo&role
2. Validate returnTo; state + nonce + PKCE verifier
   → Set-Cookie g_tx (signed, 600 s) → 302 Google (S256)
3. Google → PUBLIC_BASE_URL/api/auth/google/callback
4. Check state, clear g_tx; httpx token exchange
   (client_secret, code_verifier) → verify id_token
   → resolve → aj token in g_handoff (HttpOnly, 60 s)
   → 302 /login/google?returnTo
5. GoogleCallbackPage (AuthGuard requireAuth=false)
   → POST /api/auth/google/exchange → {token}
6. applyToken → AuthGuard reload → returnTo

The JWT never appears in a URL, no server-side store is needed, and setSession stays the only writer. The cost: a client secret, PUBLIC_BASE_URL, three routes plus a landing page, and the AuthSheet page context is lost.

Shared backend core
  • app/auth/google.py: verify_google_id_token using PyJWKClient(v3/certs, lifespan=3600) in a threadpool, algorithms=["RS256"], both issuers, aud, required iss/aud/sub/exp/iat, leeway=30, compare_digest on the nonce, and azp when present. It is exposed as the get_google_verifier dependency.
  • app/auth/google_service.py: resolve_google_sign_in applies the linking policy, uses a shared bootstrap_person_account(password=None) extracted from register(), and inserts the identity in the same transaction. An IntegrityError becomes a 409 or a re-read.
  • Errors use the ErrorResponse envelope with Polish messages: 401 for an invalid credential, 403 for an unverified email, 409 for an email conflict.
  • Login guard: app/auth/router.py:70 treats a NULL password_hash as a failed login and returns the same 401.

Rejected alternatives
  • Auto-link when the email is authoritative. aj's side of the email is unverified, which is exactly the pre-hijack case.
  • Link and set the password hash to NULL. An attacker's live JWT would survive for up to 1 h, and a legitimate user would silently lose their password.
  • The 409 does not leak anything new: register already reveals whether an email is taken.

Data model changes

0107: user_identities (schema only)

  • BaseEntity id, created_at, updated_at; pk_user_identities
  • user_id FK users ON DELETE CASCADE
  • provider VARCHAR(20) (string enum GOOGLE); subject VARCHAR(255), case-sensitive
  • email nullable snapshot, not unique; email_verified bool; optional last_login_at
  • uq_user_identities_provider_subject, uq_user_identities_user_id_provider
  • Downgrade: a plain reverse drop (it runs only after 0108's guard has passed)

0108: password_hash nullable

  • SET LOCAL lock_timeout = '5s', then DROP NOT NULL
  • Guarded downgrade: refuses while count(password_hash IS NULL) > 0 and names the recovery path
  • No image-only rollback past 0108: an old image returns a 500 for Google-only users
  • Runbook in architecture.md: pg_dump first, then the guard count

Security checklist

ID-token validation

  • Pin RS256 and verify against the Google JWKS; never trust the alg header
  • iss is one of the two Google issuer values
  • aud equals the client ID; azp equals it when present
  • exp and iat required, leeway ≤ 60 s
  • Nonce issued by the server, compared with compare_digest, used once
  • sub is the key; email is only a hint
  • email_verified required for sign-up; hd not used
  • Verify locally (never tokeninfo); JWKS fetched in a threadpool with a timeout
  • Discard the Google credential after use and never log it

Flow, accounts, secrets

  • A: the POST accepts JSON only; no session cookie is set by the backend
  • B: state + PKCE S256 + nonce in a signed one-time g_tx cookie
  • Cookies: HttpOnly, Lax, Path=/api/auth/google, Secure from the base-URL scheme
  • The JWT never goes in a URL; error redirects carry fixed codes only
  • returnTo checked with the isSafeReturnPath rules on both stacks
  • No automatic email linking; a login-less profile collision returns 409
  • A NULL hash returns the same 401; permissions come from the DB
  • IntegrityError returns 409, never a 500
  • nginx limit_req on /api/auth/
  • The secret lives only in the backend env; scopes are openid email profile
  • The avatar fetch is restricted to allowed hosts with size and time limits
  • Accepted risk: no revocation; RISC is deferred

Key insights

High

Google is an upstream identity source

Plugin/MCP OAuth2 is unchanged. The one requirement is that the seven-parameter returnTo survives the round trip.

High

aj's own gaps decide the linking policy

With unverified emails and no way to revoke sessions, every merge-by-email variant leaves a window for account hijacking.

High

AuthSheet decides the flow

In-page login on six surfaces works only with the GIS popup or a code-client popup.

Med-High

A handoff cookie needs no store

In flow B, a 60 s HttpOnly cookie plus a JSON exchange keeps the JWT out of URLs and avoids per-process memory stores.

High

Request-derived URLs break behind nginx

Redirect URIs need an explicit PUBLIC_BASE_URL. The OAuth2 metadata issuer already has this bug at :5174.

Med-High

JSON delivery blocks login CSRF

The backend sets no session cookie, so a cross-site POST cannot log the victim in.

High

Permissions trap

Register hard-codes READ/EDIT. Google sign-in must read permissions from the DB, or admins lose ADMIN.

SWOT

Strengths

  • One token shape; everything downstream is unchanged
  • Same-origin /api in every environment
  • Existing loader, guard and matrix patterns
  • PyJWT is already used

Weaknesses

  • No email verification, revocation, reset or deletion
  • The register race returns a 500
  • Base URL is wrong behind nginx

Opportunities

  • One Tap later (A)
  • Facebook through the same table and resolver (B)
  • Fix the race and the issuer while touching the code
  • Import the Google avatar

Threats

  • Pre-account hijack if linking is relaxed
  • Popup blocking (A)
  • Brand verification and the privacy policy
  • Changes to GIS and FedCM
