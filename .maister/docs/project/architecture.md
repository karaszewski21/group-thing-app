# System Architecture

## Overview

**aj** is a plugin-based microkernel platform. The backend (`src/backend/`) was migrated from a Java/Spring Boot scaffold to Python/FastAPI + SQLAlchemy + Alembic (see `.maister/tasks/migrations/2026-08-31-java-to-python-fastapi/` for the full migration record). The frontend (`src/frontend/`) runs on Next.js 16.4 App Router (migrated from a Vite + React Router SPA, see `.maister/tasks/migrations/2026-11-02-frontend-vite-to-nextjs/`; see **Frontend Application** below). The system is no longer pre-alpha scaffolding — it has real business logic across four verticals (category, product, plugin, footprint) plus a full hand-rolled OAuth2 authorization server, is runnable end-to-end via `docker-compose up`, and passed a 53/53-check integration verification pass with the fully wired application (no regressions across any prior module's acceptance criteria).

## Architecture Pattern

**Pattern**: Microkernel (Plugin-Based) — plugins are frontend iframes (`plugins/`) that talk to the host API via a browser SDK (`postMessage`/`hostApp.getToken()`) and a server-side SDK (`createServerSDK`), not a server-side plugin-loading framework. See `standards/backend/plugin-auth.md`.

**Current state**: A single FastAPI application (`app/main.py`) exposing category, product, plugin, footprint, auth, and OAuth2 routers behind one centralized authorization dependency layer. No server-side plugin-loading mechanism exists yet — that remains a future decision (see `project/tech-stack.md`'s "Architectural Decisions Pending").

## System Structure

### Application Core
- **Location**: `src/backend/app/`
- **Purpose**: FastAPI application bootstrap, cross-cutting infrastructure, and per-vertical routers
- **Key Files**: `app/main.py` (entry point — instantiates `FastAPI()`, wires CORS, registers every exception handler, includes every router with `system_router` registered last so its catch-all, which answers every unmatched GET with a JSON 404 in the `ErrorResponse` envelope, doesn't shadow more specific routes)

### Configuration
- **Location**: `src/backend/app/config.py`
- **Purpose**: Environment-variable-backed settings (`pydantic_settings.BaseSettings`). `JWT_SECRET` and `DATABASE_URL` are required with no default (fail-loud `ValidationError` on startup if missing); the remaining vars (`JWT_EXPIRATION_MS`, `CORS_ALLOWED_ORIGINS`, `FOOTPRINT_PROBLEM_BASE_URI`, `FOOTPRINT_AUDIT_RETRY_*`, `SPACES_*`, `MODERATION_*`) are operational tuning knobs with defaults matching `.env.example`/`docker-compose.yml`
- **Key Files**: `.env.example`, `docker-compose.yml`, `Dockerfile`

### Database Layer
- **Location**: `src/backend/alembic/`
- **Purpose**: Alembic database migrations
- **Technology**: PostgreSQL 18 via SQLAlchemy 2.0 (async, `asyncpg` driver)
- **Status**: One migration (`alembic/versions/0001_initial_schema.py`) reconstructs the entire schema, since no Liquibase changelog was ever populated in the Java source. Includes 6 explicitly-reconstructed FK/constraint items that existed nowhere as DDL in the original repo (see the migration's `work-log.md`, Group 2 entry, for the full checklist).

### Test Infrastructure
- **Status**: No automated pytest/TestContainers-python suite exists yet (deliberately deferred — see `project/tech-stack.md` and the migration's `spec.md` "Out of Scope"). Each vertical was verified during migration via live-uvicorn + real-Postgres manual verification scripts, not committed as a formal suite. `standards/testing/backend-testing.md` remains the target strategy for that follow-up work.

### Frontend Application
- **Location**: `src/frontend/` — Next.js 16.4 App Router (Turbopack), `output: "standalone"`; migrated from a Vite + React Router SPA (see `.maister/tasks/migrations/2026-11-02-frontend-vite-to-nextjs/`). The backend serves no HTML.
- **Route files only in `src/app/`**: the root `layout.tsx` (reads the `auth_token` cookie into `initialToken`, Google Fonts `<link>`, root default metadata), `providers.tsx` (`QueryClientProvider` with `getQueryClient()`, an Emotion `useServerInsertedHTML` registry for Chakra's SSR styles, `ChakraProvider`, `AuthProvider`, `NavigationTracker`), `not-found.tsx`, `globals.css`, and 62 `page.tsx` under the route groups `(public)` (every user-facing page under `components/layout/PublicLayout.tsx` — the top bar with the Gooo mark, the search field (hidden on `/search` and in a chat thread), Terminy and the bell, and the bottom tab bar Start · Czat · + · Moje rzeczy · Konto, a floating pill from `md` —, with `(panel)`, `search/` and `about/`; `[slug]/layout.tsx` gives every page under the slug the Organization palette, event and term pages nest their own), `(standalone)` (only the OAuth2 consent page `oauth2/authorize`, with no app chrome) and `admin/(shell)`. Pages are thin and render a feature entry from `src/features/<domain>/`. Legacy URLs are server `redirect()`s; such a page never sits under a layout that withholds `children` during SSR (it would become a client redirect with status 200), which is why the admin pages live in `admin/(shell)/` and the slug item page in `product/[id]/(item)/`. `/:slug/group/:groupId` has no page (404).
- **Rendering**: `(panel)`, `(standalone)` and admin render only in the browser (`routing/ClientOnly.tsx` returns `null` on the server). The panel layout renders `features/panel/PanelGate.tsx` around its `children`: the session gate, then `AppPage` (AppDataProvider, `PhoneFrame`, modals, toast), kept mounted while switching sections so the panel data loads once. Every section page renders its own view; `AppPage` puts every section but the chat thread in one padded scroller (`PanelSection`, matched by path, no route group), while `/messages/:conversationId` fills the frame between the top bar and the bottom tab bar. Panel pages render no header (no title row, no back link; navigation is the top bar and the bottom tab bar); places and organization re-read panel data via `usePanelReload()`. Tests render the real section pages through `test/panelPages.ts` + `test/PanelPageOutlet.tsx` (`panelPages.test.ts` keeps the list in step with `src/app`). Registration has no onboarding wizard: the login page's `AuthGuard` sends a new account to `returnTo` or `homePath`. The `(public)` chrome, `/`, `/login`, `/search`, `/product/*` and the slug pages are server-rendered.
- **Public metadata and palette**: the organization, event and term pages are server components with `generateMetadata` (`lib/publicMetadata.ts`: title, description, `og:*` and `twitter:*` tags, image) that wrap a `"use client"` feature entry in `theme/ServerThemeProvider.tsx`, so the organizer palette is in the first HTML response (`OrganizerThemeScope` prefers the page's own data). Server-side backend reads go only through `src/api/server.ts` (see `standards/frontend/data-fetching.md`); a failed read falls back to the root default metadata, and private circles get the default preview.
- **In-page login on public pages**: account-requiring actions on public pages (term/event sign-up, "Ja to przyniosę", item reserve/chat, a PRIVATE term's login step, an anonymous item 404) never navigate to `/login`. They open the one `features/auth/AuthSheet.tsx` bottom sheet (login and register tabs from `AuthTabs`, shared with `/login`), driven by `features/auth/useAccountGate.ts` (`guard(fn)`, `open(tab)`, closed once a token exists) or by `AuthPromptButtons` for an inline card. Logging in swaps the token in place; the page's token-aware queries refetch. There is no guest sign-up for terms or events and no anonymous-profile merge (removed 2026-11-04).
- **Request proxy** (`src/proxy.ts`, the pure `resolveProxy` plus a matcher that excludes `api/`, `_next/`, `assets/`, `.well-known/`, `favicon.svg` and `icons.svg`), rules in order: `/home` → 307 to `/` (query kept); `/` with an `auth_token` cookie → internal rewrite to `/home`, the visible URL stays `/`; `POST /oauth2/authorize` → rewrite to `${BACKEND_INTERNAL_URL}/oauth2/authorize` (the GET is the Next consent page); a `PROTECTED_PREFIXES` path (`routing/paths.ts`, segment-boundary match) without the cookie → `/login?returnTo=…`. It checks cookie presence only and never verifies the JWT; the client `AuthGuard` stays authoritative. `/api/*` is never matched, because the proxy buffers bodies up to 10 MB and photo uploads reach 15 MB.
- **Session cookie**: `auth/session.ts` keeps the login JWT in localStorage and in the JS-readable `auth_token` cookie (`Path=/; SameSite=Lax`, `Max-Age` from the JWT `exp`, `Secure` on https) in lockstep; every write goes through `setSession`/`clearSession`. The server render uses the cookie for `initialToken`, the proxy rewrite and the gate, and never forwards it to the backend. The backend also accepts it on GET/HEAD (see `standards/backend/security.md`). Client data calls stay relative (`/api`) with the Bearer header from localStorage.
- **Routing facade**: feature code reaches the router only through `src/routing/navigation.tsx`; ESLint `no-restricted-imports` bans `next/navigation`/`next/link` outside `src/routing/`, `src/app/` and the test mocks, and `react-router-dom` everywhere.
- **Reserved slugs**: `routing/reservedSlugs.ts` lists every top-level static segment of the route tree (`home` included); `test/reservedSlugs.test.ts` checks that each is in the backend's `RESERVED_SLUGS` (`app/organizations/slugs.py`).
- **Plugin SDK**: `vite.sdk.config.ts` builds `src/plugin-sdk` as one IIFE into `public/assets/plugin-sdk.js` (git-ignored) on `predev`/`prebuild`; Next serves it with `public/assets/plugin-ui.css` at `/assets/` on :5173.

## Data Flow

```
Client Request → FastAPI Router → Auth Dependency (require_any) → Service Layer → SQLAlchemy (ORM or Core) → PostgreSQL
```

Each route enforces its own requirement through `Depends(require_any(...))` (no dependency for PUBLIC routes). `AUTHORIZATION_MATRIX` in `app/core/authorization_matrix.py` is a reference table of those requirements, verified by `tests/test_authorization_matrix.py`; nothing applies it centrally at request time (see `standards/backend/security.md`).

Page requests take a separate path: browser → nginx → Next (`src/proxy.ts` → root layout → route). Public pages render their metadata and palette from anonymous `src/api/server.ts` reads; the browser then calls `/api` with the Bearer token, through nginx to the backend.

Plugin iframes reach the same routers via the host's browser SDK, which attaches the same JWT the router-level auth dependency validates — there is no separate plugin-specific auth path on the server side (see `standards/backend/plugin-auth.md`).

## Domain clock (Europe/Warsaw)

`Term.occurs_on` is a naive Europe/Warsaw wall clock (unlike the naive-UTC audit columns such as `created_at`). `app/core/clock.py` is the only definition of "now" for Term logic: `clock.local_now()` converts the current UTC instant to Warsaw time through `zoneinfo`, so it never depends on the host or container `TZ`. Call sites use `clock.local_now()` (module attribute access) so the opt-in `freeze_local_now` test fixture reaches all of them. The same module holds the Polish short date formatters and the notification-length cap. `tests/test_domain_clock_guard.py` forbids `datetime.now(` and `date.today(` in `app/groups/application`, `app/groups/router`, `app/events`, `app/pages`, `app/search` and `app/wants`. The wants matcher (`src/matcher`) uses no Warsaw time: only `matcher/clock.py` reads the host clock (`clock.utcnow()`, naive UTC), enforced by `src/matcher/tests/test_clock_guard.py`, which also forbids `datetime.utcnow(` elsewhere in the package.

Ops: the `lifespan` startup calls `clock.check_timezone()` before the outbox poller and APScheduler start. It fails with an "install tzdata" error if the zone cannot load, and otherwise logs one line, `Europe/Warsaw (CET|CEST)`. Setting `TZ=Europe/Warsaw` in compose is optional and no code relies on it.

## Photo Upload and Content Moderation

```
POST /api/products/{id}/photos (multipart) → Pillow sanitize → Spaces (private)
      → one transaction under the product FOR UPDATE lock:
          product_photos(PENDING) → COMMIT (listings are left untouched)
                                   ↓ (shared Postgres, polled)
VPS B moderation-cron (group-thing-ai, python -m app.moderation_cron, every 30 s)
      → claim PENDING (FOR UPDATE SKIP LOCKED) → Spaces get → ShieldGemma-2 in-process
      → APPROVED (files public-read, CDN)
      | NEEDS_REVIEW → /api/moderation (ADMIN)   (files private)
      | REJECTED                                 (files private)
      + one moderation_decisions row (source AI, automated)

PUT /api/item-listing-preferences/{item_id} (mode ≠ null) → listed whatever the photo status
```

Two independent flags, both default `false`: `MODERATION_TEXT_ENABLED` (API) and `MODERATION_IMAGE_ENABLED` (API). The API logs both at startup. The old `MODERATION_ENABLED` is ignored (unknown env vars are dropped), so a stale `.env` that still sets it gets photos approved on upload. `MODERATION_IMAGE_ENABLED=true` must be paired with `MODERATION_CRON_ENABLED=true` on VPS B: with the app flag on and the cron off, photos stay PENDING and are hidden from non-owners, although their items can still be listed (an admin can still decide them in the queue); with the app flag off, uploads are APPROVED at once and the cron has nothing to do.

**Text: synchronous and reject-only, in the API process.**
- `app/moderation/text_guard.py` `check_text(field, new, current=None)` runs Bielik-Guard-0.1B (ONNX, 1 intra-op thread) via `asyncio.to_thread` before the write.
- Checked fields: organization name, group name, term description, product name, the shared product description, and a needed item's name and description (checked as product name/description). This includes the resolve/create branch and the `plugin_data` PUT.
- A value is scored only when it changes (normalised comparison with `current`), so untouched legacy text is never re-checked.
- Any category score ≥ `MODERATION_TEXT_REJECT_THRESHOLD` (default 0.8) → 400 with a Polish message and no scores. Model unavailable → 503 (fail-closed).
- With the flag on, the API lifespan loads the model from `MODERATION_MODELS_DIR` (`<dir>/text`), and startup fails if that is impossible.
- No text status is stored and no text goes through the queue: products have no `text_status`/`text_moderated_hash` (migration 0047 marks leftover `moderation.text_requested` events PROCESSED and moves PENDING photos whose event already FAILED to NEEDS_REVIEW; 0048 drops the columns). Old `PRODUCT_TEXT` decisions remain only as audit rows.
- The synchronous contact-info regex rules (`rules.py`, 400) are unchanged.

**Photos: asynchronous, decided by the cron on VPS B.**
- The decision logic lives only in `group-thing-ai` (`app/photo_moderation.py`, `app/moderation_cron.py`; see its README "Photo moderation cron"). The `moderation-cron` compose service (profile `shield`, switched by `MODERATION_CRON_ENABLED`) reads PENDING `product_photos` straight from the shared Postgres and scores them with ShieldGemma-2 in-process. The app sends nothing to VPS B for moderation.
- Every `MODERATION_CRON_INTERVAL_S` (30) it processes up to `MODERATION_CRON_BATCH` (5) photos, oldest first, one at a time. A tick is skipped while the shield is unhealthy, so an outage uses up no attempts.
- Per category: `sexual`/`violence`/`dangerous` score ≥ `MODERATION_IMAGE_REVIEW_THRESHOLD` (0.5) → NEEDS_REVIEW, ≥ `MODERATION_IMAGE_REJECT_THRESHOLD` (0.9) → REJECTED; `weapons` is review-only. The most severe outcome wins. The cron reads these thresholds from its own `.env.cron`; the app has no image thresholds.
- APPROVED makes both files (`w1600`, `w400`) public before the status write. Every other outcome makes both files private first, every time, because an earlier attempt may have left them public.
- **Retry state** is on the photo row (migration 0049): `moderation_attempts` (INTEGER NOT NULL, default 0) and `moderation_retry_at` (naive UTC TIMESTAMP), plus the partial index `ix_product_photos_pending_created_at` on `(created_at, id) WHERE status = 'PENDING'`. Only VPS B writes them.
  - The claim increments `moderation_attempts` and sets a lease in `moderation_retry_at`. The finalize is guarded with `WHERE status = 'PENDING' AND moderation_attempts = :claimed`, so an admin decision or a delete during scoring wins and the cron's result is discarded.
  - A failed attempt is retried after timeout + 30 s·2^(n-1), measured from the failure. After 5 attempts the photo goes to NEEDS_REVIEW with the note "AI unavailable after 5 attempts" and a null-score decision (shown as "No model score" in the admin queue).
  - Every B update sets `updated_at` explicitly, because it is the ORM's optimistic-lock token. A concurrent app update of the same photo (e.g. reorder) can rarely fail with the existing 409 `StaleDataError` response.
- VPS A runs no photo worker: `add_product_photo` writes no outbox event for moderation, and the app has no VPS B client or `MODERATION_AI_*` settings. `MODERATION_IMAGE_ENABLED` is the app's only photo-moderation switch (true = uploads stay PENDING until the cron decides). Leftover `moderation.photo_requested` outbox rows from the old worker are marked PROCESSED by the API poller (no handler).

**Listing is not gated by photo moderation (`app/groups/application/term_item_listings.py`).**
- An item can be listed (Oddam/Zamienię) while its product has a PENDING or NEEDS_REVIEW photo. A new pending photo (`add_product_photo`) or re-pointing an item to another product (`update_item`) leaves existing listings untouched; neither takes a groups hook any more. The earlier publish gate, withdraw on upload/re-point and the one-time `withdraw_unmoderated_listings` cleanup script were removed. Non-owners still see only APPROVED photos, so a listed item may show no photo until moderation finishes.
- **UI flag**: `GET /api/inventory-items/mine` still returns `photos_moderation_pending` per item (one batched `product_ids_with_unmoderated_photos` query). It is informational only.
- **`listing_status` lockstep**: `inventory_items.listing_status` (DRAFT/ACTIVE) mirrors the `item_listing_preferences` row: ACTIVE exactly when a preference exists. `register_item` sets it (optionally creating the preference through the router-injected `on_registered` hook); `set_item_listing_preference` (under an item `FOR UPDATE` lock) and `confirm_transaction` change it only through the flush-only `inventory_bridge.set_item_listing_status`, in the same commit as the preference write. Every listing read stays preference-driven.
- **Taken-list fallback**: when an active reservation's preference was cleared by its owner, `list_my_active_taken_term_item_listings` builds a transient `ItemListingPreference` (never added to the session) from the reservation, so the taker still sees the item and can confirm it.
- **Category tree**: `categories` is a tree (`parent_id`, nullable `external_id`) seeded from the Polish Vinted snapshot `alembic/data/vinted_categories_pl.json`. Products may only use leaf categories (`require_leaf_category` in `app/category/service.py`: 404 unknown, 409 non-leaf); admins add, rename, reorder siblings and delete nodes, but cannot reparent them.
- **Needed items** are plain names (`needed_items.name` plus an optional `description`); since `0068` they no longer point at a product.

**VPS B depends on these columns and privileges.** The least-privilege role `gt_moderation_cron` is created by `group-thing-ai/scripts/moderation_db_role.sql` (column-level grants only). The cron's startup self-check verifies the same list (`REQUIRED_PRIVILEGES` in `group-thing-ai/app/photo_store.py`) and exits non-zero if a column or grant is missing. A migration that renames, drops or retypes any of these columns needs a matching change in both files:
- `product_photos` SELECT: `id, storage_key, content_sha256, status, moderation_attempts, moderation_retry_at, created_at, updated_at`
- `product_photos` UPDATE: `status, moderation_attempts, moderation_retry_at, updated_at`
- `moderation_decisions` INSERT: `id, subject_type, subject_id, content_hash, source, automated, model_id, scores, thresholds, outcome, note, created_at, updated_at`

The cron connects over the VPC with `?ssl=require` (`pg_hba.conf`: `hostssl aj gt_moderation_cron <VPS_B_VPC_IP>/32 scram-sha-256`; the firewall allows 5432 only from VPS B). Its DB and Spaces credentials live only in `.env.cron` on VPS B, which the B `api` service does not load.

**Shared pieces.**
- `app/storage/` — `ObjectStorage` protocol + `SpacesStorage` (boto3); `get_storage()` returns `None` while the `SPACES_*` settings are unset (upload disabled). `storage.objects_delete` outbox events delete files after their rows are gone.
- `app/moderation/` — `ModerationStatus` (PENDING/APPROVED/NEEDS_REVIEW/REJECTED) per photo; append-only `moderation_decisions` audit log (automated rows are written by VPS B); ADMIN queue/decisions router (photos only), which sets the file ACLs on every decision.
- Non-owners see only APPROVED photos.

**Images and deployment.**
- The production API image is the default (last) Dockerfile stage `runtime`. It contains the `ml` uv group and Bielik-Guard, which is exported to ONNX at build time from the gated HF repo, so it needs the secret: `docker build --secret id=hf_token,env=HF_TOKEN src/backend`. Expect about +0.6–0.8 GB RSS per uvicorn process.
- Compose builds this `runtime` target too, with the `hf_token` build secret (from `HF_TOKEN` in the environment) and `MODERATION_TEXT_ENABLED: "true"`. `runtime-dev` has no model and needs no secret; build it by hand (`docker build --target runtime-dev src/backend`) and run it with `MODERATION_TEXT_ENABLED=false` when no token is at hand.
- 0048 is not zero-downtime: any API or worker process from before it fails on every product query once the columns are dropped. Rolling back past 0048: first run `alembic downgrade 0046` **with the new image** (restores the columns; 0047's data changes are not reverted), then deploy the old image.

**Cutover to the VPS B cron.** The app ships as **one combined release**: migration 0049, the taken-list fallback and the UI flag, together with the removal of the old `moderation-worker`. The `group-thing-ai` README ("Cutover") lists the same steps with the full smoke check.
1. **Network and role prepared.** Add the `pg_hba` entry, the VPC listen address with TLS and the firewall rule, and have `moderation_db_role.sql` and a generated password ready. No SQL yet: the script grants columns that only exist after 0049.
2. **VPS B, cron off.** Check that Docker Compose is 2.24 or newer (`docker compose version`); the compose file needs it. Put `.env.cron` in place with `MODERATION_CRON_ENABLED=false` and deploy; a disabled cron exits 0. Check that the B `api` container has no `DATABASE_URL`/`SPACES_*`.
3. **VPS A, app release.** Keep `MODERATION_IMAGE_ENABLED=false` and deploy with `docker compose up -d --remove-orphans`. Migration 0049 runs and `--remove-orphans` removes the old `moderation-worker` container. `--remove-orphans` removes **every** running container that is not defined in the deployed compose file, so first make sure everything that must keep running on VPS A is in that file. **Then** run `moderation_db_role.sql` as the DB owner.
4. **Cleanup.** No longer needed: the cleanup script was removed together with the listing gate.
5. **Enable the cron.** Set `MODERATION_CRON_ENABLED=true` and recreate `moderation-cron`. Its self-check (config, TLS, columns, per-column privileges) must pass.
6. **Smoke test with real Spaces and ShieldGemma.** Re-queue a benign and a borderline test photo as PENDING. The benign one must end APPROVED with public files, the borderline one NEEDS_REVIEW/REJECTED with private files, and each must have one new `moderation_decisions` row.
7. **Only then** set `MODERATION_IMAGE_ENABLED=true` on VPS A and recreate the backend.

**Moderation gap.** From step 3 until step 7 nothing moderates photos: the worker is gone and the cron is either off or only being verified. This is deliberate and safe, because with `MODERATION_IMAGE_ENABLED=false` new uploads are auto-approved, the same as before the release. Keep the gap short.

Rollback: set `MODERATION_IMAGE_ENABLED=false` on VPS A (uploads are auto-approved again) and/or `MODERATION_CRON_ENABLED=false` on VPS B. Migration 0049 is additive, so there is no need to downgrade it. Nothing withdraws listings any more, so there is nothing to restore. If you redeploy an older app image that still contains the old `moderation-worker`, **first** disable the cron (`MODERATION_CRON_ENABLED=false` and recreate, or stop `moderation-cron`) so the two never moderate photos at the same time.

## Page media and appearance (`app/media/`, `features/editor/`)
One moderated image table, `media` (0082), serves every public page: rows belong to a party (`owner_party_id`: a person, or an Organization's **own** party) and are a `LOGO`, `AVATAR` or `COVER` slot (newest APPROVED per slot is public, at most one unmoderated row per slot, `uq_media_one_pending_per_slot`) or one of up to 3 `GALLERY` photos. `app/media/service.py` (ported from the removed `app/organizations/media.py`) reads, uploads, deletes, reorders and sweeps superseded slot rows under a `parties` row lock; callers check ownership first (`organizations/router.py::_require_owned`, the principal's own profile for `/api/people/me/media`). Moderation logs one subject type, `MEDIA`, titled with the Organization's name, else the person's. `organization_media` and `profile_avatars` are gone (0083).
- **Profile appearance**: `user_profiles.page_layout`/`palette_preset`/`primary_color`/`accent_color` (0081), written by `PATCH /api/people/me/appearance` (omitted keeps, `null` clears; bio text-moderated), layouts allowlisted in `app/users/profile_layouts.py` (`BANNER` only; parity with `features/profile-public/layouts/registry.ts`). `GET /api/public/parties/{id}` (public for every account profile, even with nothing listed or planned; 404 only for unknown parties and family members without an account) returns the person as `owner` (their own name, `slug` null; an owned Organization is the separate `organization {name, slug}` link), `logo`/`avatar`/`cover`/`gallery` and the theme; `GET /api/people/me` returns the own `media` in any status.
- **Founding an Organization** (`POST /api/organizations/mine`, first creation only) copies the founder's visible profile media (public slots, non-REJECTED gallery) to the Organization's party with fresh storage keys and the same status (`media.copy_media`); colors and layout stay on the profile.
- **Frontend**: `/<party-id>` renders the profile in its layout and colors (`features/profile-public/layouts/ProfileLayoutRenderer.tsx`: banner, centered avatar, bio, gallery, nearest pickup dates, "Rzeczy użytkownika" with infinite scroll); the owner's gear opens `/<slug-or-party-id>/appearance` (`app/(public)/[slug]/appearance/`, owner-only, `isAppearancePath` login-gated in `proxy.ts`), the shared `features/editor/AppearanceEditor.tsx` with tabs photos, layout+colors and name. On a profile the four Organization layouts are shown locked with an invite to `/organization` (now only the founding form; an owner is sent to the name tab). `/profile` redirects to `/<party-id>`.

## Locations (`app/locations/`)

`app/locations/` is its own bounded context: a person's saved places (`Location`), owned by their PERSON party (`profile.party_id`), used by their items and by the groups (Circles), Terms and events they lead. Since `0080` a place is a **locality** from the TERYT dictionary plus an optional street address (OLX-style); it has no name or notes. Routes: `GET /api/locations/mine`, `POST /api/locations` (201, every POST creates a row — no Google place dedup any more), `PUT /api/locations/{id}` (full replace; `PATCH` was removed and answers 405) and `DELETE /api/locations/{id}` (owner only, soft delete), plus `GET /api/localities`. Migrations `0057_locations`, `0058_group_term_location_capacity` (`location_id`/`capacity` on groups and terms), `0078`–`0080` (runbook "Deploy / rollback for item location (migrations 0078–0080)" below).

- **Locality dictionary** (`Locality`, `LocalityPostalCode` in `app/locations/models.py`; search in `app/locations/localities.py`): `localities` holds every independent TERYT SIMC locality (GUS TERYT SIMC/TERC, stan 2026-01-01) — 54,440 rows, 1,026 TOWN / 53,414 VILLAGE, each with `gmina`, `powiat`, `voivodeship` and a precomputed `name_search` (`fold_polish`: lower case, diacritics and `ł` folded); city districts are folded into their city. `locality_postal_codes` holds 72,245 `(postal_code, locality_id)` pairs derived from the GUGiK PRG address points (free for any use). Both are seeded from gzipped CSV fixtures in `src/backend/alembic/data/` (`localities_pl.csv.gz`, `locality_postal_codes_pl.csv.gz`; sources, licence, hashes and the rebuild command `scripts/build_localities.py` in `localities_pl.README.md`). The 7-character SIMC id is a natural string PK (see `standards/backend/models.md`).
- **Search**: `GET /api/localities?q=&limit=` (`READ`, `limit` 1–20, default 10) → `{results: [LocalitySearchResult], total}`. A `q` shorter than 2 characters returns nothing; a digits query (`32`, `32650`, `32-6`) is a postal-code prefix search (each result carries its `postal_code`), anything else a folded name prefix. Towns first, then exact matches, then name/voivodeship/powiat/gmina/id. Request-validation errors in this app are **400** with `fieldErrors` (`app/core/errors.py`), not 422.
- **Label and loading**: `Location.label` (model property) is the single place label — `"Kęty, małopolskie"` without an address, `"Kęty — {address}"` with one; every response's `label` and every term/event `location_name` comes from it. `Location.locality` is `lazy="raise"`, so every row that is serialised or labelled must come from `service.load_location`/`load_locations_by_ids` (`joinedload` + `populate_existing`), including the reload after create and update; the three `locations_acl` modules delegate to these loaders.
- **Address fields**: `formatted_address` and `source` are nullable together under `ck_locations_address_fields` (no address ⇒ no source, place id or coordinates; an address needs a source). Request shapes: `{locality_id}`, `{locality_id, formatted_address, source: MANUAL}` (optionally with a pinned point: `lat` and `lng` together, never `google_place_id`) or `{…, source: GOOGLE, google_place_id, lat, lng}`. The place form has one address field and no modes: typed text is saved as typed (MANUAL); picking a Google suggestion fills the field and saves GOOGLE with its point, and retyping afterwards drops the place id and that point. "Wskaż na mapie" on an empty field reverse-geocodes the point into the field (`PlaceMapPicker` `onPick`, GOOGLE); with text already typed it sets only the bare point (`onPoint`, MANUAL with `lat`/`lng`), which survives later edits of the text. "Usuń pinezkę" clears the point, a point without an address blocks the save, and without the Maps key (or when Places or the map fail to load, each with a notice) the field is plain text. The Maps script is ready on Google's `callback`, not on the tag's `load` event (`lib/googleMaps.ts`).
- **Boundary**: `app/groups/infrastructure/locations_acl.py`, `app/events/infrastructure/locations_acl.py` and `app/inventory/infrastructure/locations_acl.py` are their BC's only import of `app.locations`. They validate newly assigned ids against the caller's own active places (404 unknown/soft-deleted, then 403 foreign) and batch-load referenced rows (one `IN` query, soft-deleted rows included so old groups, terms and items still render). None may import its own BC's `..schemas` (import cycle). Groups, terms, events and items store only a plain `location_id` FK.
- **Read shape**: READ-level embeds (`GroupResponse.default_location`, `TermResponse.location`, events) use the narrow `LocationRefResponse` (`id`, `locality`, `label`, `formatted_address`, `google_place_id`, `deleted_at`; no `owner_party_id`, no coordinates). Term and event addresses stay public: context `location_name` carries the full label (user decision). Unchanged ids are not re-validated on save, and the group's own default is never ownership-checked (it may be soft-deleted).
- **CSP**: none is configured today; if a Content-Security-Policy is introduced, allow `script-src https://maps.googleapis.com` and `connect-src https://places.googleapis.com https://maps.googleapis.com` or the address field falls back to manual entry.
- **Inheritance**: `create_term` copies the group's default place and capacity **by value**; later changes to the group default never touch existing terms.
- **Google Places caching**: the backend never calls Google. The browser looks addresses up via Places API (New) (`importLibrary("places")`, session tokens, `src/frontend/src/lib/googleMaps.ts`), biased by the query suffix `"{locality}, {voivodeship}"`, and posts the result. `google_place_id` may be stored indefinitely; `formatted_address`, `lat` and `lng` are cached Google data subject to Google's caching limits, and refreshing them is out of scope (`updated_at` is the cache timestamp). Without `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` (a frontend build arg inlined by `next build`, never committed) the address is typed by hand (MANUAL); the locality never needs Google.

### Item location
Each item has its own pickup place, `inventory_items.location_id` (FK `fk_inventory_items_location_id_locations` without ON DELETE, partial index `ix_inventory_items_location_id`); it replaced the owner-wide `inventories.location_id` from `0075`, which `0080` dropped together with `GET|PUT /api/inventories/mine/location` and the Moje rzeczy pickup-place card.

- **Write**: `POST /api/inventory-items` requires `location_id` — one of the inventory owner's live places, checked through `app/inventory/infrastructure/locations_acl.py` (404 then 403); `PATCH /api/inventory-items/{id}` may move it to another own live place (`null` is refused). A GIFT or SWAP transfer clears it (`ledger._apply_projection`), so the new owner sets their own; LEND/RETURN keep it.
- **Read**: `location_id` is not on `InventoryItemResponse`; `GET /api/public/items/{id}/details` returns it to the owner only, and `null` once the place is soft-deleted (`repository.find_item_live_location_id`).
- **Listing guard** (`term_item_listings.py`): only the **first** listing of a DRAFT item (DRAFT → ACTIVE) without a live location is refused, 409 "Ustaw lokalizację przedmiotu, aby go wystawić". Changing the mode of an ACTIVE listing is never blocked, and soft-deleting a place leaves its items' listings ACTIVE.
- **Personal pickup** is gated by the item's own live place (`inventory_bridge.get_item_live_location_id`): without one `load_personal_context` gives 409 "Właściciel nie ustawił lokalizacji przedmiotu" and `/actions` reports `personal_pickup_available: false`.
- **Privacy** (`item_actions._viewer_location`, `ItemLocationResponse {locality, formatted_address, deleted_at}`): the owner gets the address and `deleted_at`; every other viewer, anonymous included, gets only the locality (`formatted_address` and `deleted_at` null, even for a removed place). Never the place id, label, coordinates or Google place id.

### Event reservations
Items listed by event participants can be taken (GIFT) or swapped (SWAP) for an event, the same way as for a term. Migration `0073_event_reservations` makes `reservations.term_id` nullable and adds `event_id` (FK `fk_reservations_event_id_events` **ON DELETE SET NULL**, partial index `ix_reservations_event_id`). 0073's CHECK `ck_reservations_context` allowed at most one of `term_id`/`event_id` and required exactly one on open (PENDING/CONFIRMED) rows; since `0074` it is only `num_nonnulls(term_id, event_id) <= 1`, because an open row with neither is a personal pickup (see **Product page reservations** below). Rows detached from a deleted event keep both NULL and are always terminal. Runbooks: "Deploy / rollback for event reservations (migration 0073)" and "… for product page reservations (migrations 0074–0077)" below.

- **Write side**: `inventory.service.create_reservation(...)` (and `inventory_bridge.create_reservation`) takes keyword-only `term_id`/`event_id`, at most one of them (none = personal pickup). `POST /api/reservations` stays term-only.
- **`ReservationContext`** (`app/groups/application/reservation_context.py`, `TermContext | EventContext | PersonalContext`): one code path in `term_item_listings` (`take_item`, `propose_item_swap`, `accept_swap_proposal`, `_resolve_transaction_reservations_for_action`) serves all three. The context supplies eligibility (term: `_require_term_eligibility`; event: the author or an active attendee whose party has an account), the date and `has_started`, the notification name/`when` text, `link_path`, the reservation's context column, `allows_visibility` and the `ItemContextResponse` (`kind` TERM|EVENT, `id`, `name`, `starts_at`, `path`, `has_started`; None for a personal pickup). `load_for_reservation` returns `PersonalContext.for_reservation()` for an **open** row with both columns NULL and None for a **terminal** one (its event was deleted). Term behaviour and messages are unchanged.
- **Routes**: takes and proposals go through the unified `POST /api/items/{item_id}/take|propose` with `context {kind: EVENT, id}` (see **Product page reservations**); the old `POST /api/events/{event_id}/items/{item_id}/take|propose` (`event_item_listings.py`) was removed. An event take/propose holds the event `FOR SHARE`, like sign-up; 404 unknown event/item, 403 ineligible taker or owner, 409 once the event has started ("Wydarzenie już się rozpoczęło"), own/unavailable item, mode mismatch or SWAP via take. Accept (`/api/swap-proposals/{id}/accept`) also locks the event `FOR SHARE`; a deleted event gives 409. Confirm/cancel use the existing `/api/reservations/{id}/confirm-transaction|cancel-transaction`.
- **Timing**: take/propose/accept while `clock.local_now() < starts_at`; confirm/cancel from `starts_at` on (before: 409 "Wydarzenie jeszcze się nie rozpoczęło"). `starts_at` is read live, so editing the event moves both gates. Withdrawing an attendance never cancels reservations. Confirm/cancel check the terminal/already-resolved status before loading the context, so a contextless CANCELLED reservation returns 409 `already_resolved`, never 404/500.
- **Import discipline**: `app/groups/infrastructure/events_acl.py` is the only `app.groups` module that reads events, and it imports `app.events.models` only (`app.events.service` imports groups through its own `groups_acl`; importing the service would close a cycle). Inventory never imports `app.events`: its readers reach `events` through Core `table()` refs in `inventory/infrastructure/repository.py`. The `events_acl` reads used by the owner pages are exported through `groups.service` for `app.pages`.
- **Readers**: `ReservationResponse` (`term_id` nullable, `event_id`), `ReservationDetailResponse` (the context date in `term_occurs_on`, plus `event_id`), `ItemStatusResponse` and `AcceptedSwapProposalResponse` (`event_id`, `event_slug`; the latter's `term_id`/`group_id` nullable). Event privacy follows the term rule (non-parties see the date only). Notifications reuse the term kinds (`TERM_ITEM_LISTING_TAKEN`, `ITEM_RESERVED_FOR_PICKUP`, `SWAP_*`, `TERM_CONFIRMATION_NEEDED`) with the event name and `format_term_when(starts_at)`.
- **End-of-event scan**: `term_end_scan` adds an event pass for events whose `starts_at + TERM_END_GRACE` (2 h) falls in the scan window. It is reservation-driven and ignores eligibility and listing preferences, so a withdrawn attendee still gets the prompt: GIFT = open reservations with that `event_id`; SWAP = ACCEPTED, not-yet-notified proposals whose proposer reservation belongs to the event. It reuses `TERM_CONFIRMATION_NEEDED` with `link_path=/{author_slug}/event/{id}`, and each party's swap prompt carries its own `reservation_id` (the outbox listener sets it only when the payload has one, so term prompts are unchanged). The existing markers make it idempotent. Frontend `pendingActions.ts` recognises `/…/event/{id}` links (`termId` null, confirm by `reservation_id`).
- **Delete rules** (`events/service.py::delete_event`, under the event `FOR UPDATE` lock, in order): (1) 409 `EventHasAttendees` while anyone is signed up; (2) 409 `EventHasOpenReservations` ("Wydarzenie już się rozpoczęło i ma otwarte rezerwacje — potwierdźcie lub anulujcie przekazania") when open reservations or swaps exist and the event has started; (3) otherwise `groups_acl.cancel_open_event_reservations` → `groups/application/event_reservations.py` cancels, in the same uncommitted transaction, every PENDING/CONFIRMED reservation of the event incl. both swap legs (`inventory_bridge.cancel_reservations_without_commit`: `FOR UPDATE`, skips terminal rows, releases items to AVAILABLE), sets PROPOSED **and ACCEPTED** proposals to REJECTED (term `cancel_transaction` leaves ACCEPTED alone) and notifies both parties with `RESERVATION_CANCELLED`. The event row is then deleted, `SET NULL` detaches the terminal rows, and one commit ends it. The UI (`EventAuthorCard`) shows "Usuń i anuluj rezerwacje" before start and an `aria-disabled` delete with a hint after start.
- **`RESERVATION_CANCELLED`**: new `NotificationKind` (21 chars in the non-native `VARCHAR(30)` column, no migration), `link_path=/<owner slug>/product/{item_id}` (`groups/application/item_links.py::item_path`), sent to both parties of a reservation or swap cancelled because its event was deleted. `NotificationBell` renders it generically; `pendingActions.ts` derives no action from it.

### Product page reservations, pickup place and item visibility
Reservations start on the item page (`/:slug/product/:id`), not on term or event pages. Migrations `0074` (personal pickups), `0075` (`inventories.location_id`) and `0076` (`item_listing_preferences.visibility`); `0077` indexes pending swap proposals by listed item; runbook "Deploy / rollback for product page reservations (migrations 0074–0077)" below.

- **Personal pickup (`PersonalContext`)**: the third `ReservationContext`, a pickup arranged in chat at the owner's place. A personal reservation has neither `term_id` nor `event_id` and no date window: take/propose/accept are open at any time and confirm/cancel settle at once (`require_open`/`require_ended` are no-ops). Two ways to build it: **create-time** `load_personal_context` (404 unlisted item; 409 "Właściciel nie ustawił lokalizacji przedmiotu" while the item has no live `location_id` — since `0080`, see **Item location**; carries the owner and the item's visibility for eligibility) and **reservation-derived** `PersonalContext.for_reservation()` (field-free, lifecycle methods only). `term_end_scan` is term/event driven, so personal reservations get no end-of-date prompt.
- **Open vs terminal no-context rule** (accepted risk L7, no discriminator column): a row with both context columns NULL is personal while PENDING/CONFIRMED and "event deleted" once terminal; `load_for_reservation` decides by status. This stays sound only because `delete_event` cancels open event reservations before `ON DELETE SET NULL` detaches them; a test pins that no open no-context row survives an event delete. Terminal personal rows read like deleted-event rows in history (non-parties see no context anyway).
- **Unified write endpoint** (`app/groups/router/item_reservations.py`, `EDIT`): `POST /api/items/{item_id}/take` (`ItemTakeRequest {context, reservation_type}` → `ItemTakeResponse {item_id, product_name, context}`, `context` null for a personal pickup) and `POST /api/items/{item_id}/propose` (`ItemProposeRequest {context, offered_item_id}` → `SwapProposalResponse`). `context` is `ReservationContextRef {kind: PERSONAL|TERM|EVENT, id?}`: PERSONAL forbids `id`, TERM/EVENT require it; violations are 400 with `fieldErrors` (`app/core/errors.py` maps request validation to 400, not 422). Removed: `POST /api/term-item-listings/{id}/take|propose` and `POST /api/events/{event_id}/items/{item_id}/take|propose` (`tests/test_item_reservations_router.py::test_removedTakeProposeRoutes_returns404or405`); `/api/term-item-listings*` is now read-only. ## Messaging (`app/messaging/`)

`app/messaging/` is its own bounded context: private text chats between logged-in users. Tables `conversations`, `messages` and `conversation_reads` (migration `0061_messaging`). Routes live under `/api/conversations`: the inbox (`GET ""`), `GET /unread-count`, get-or-create `POST /item`, `/group`, `/term` and `/event`, `GET /{id}`, `GET`/`POST /{id}/messages` and `POST /{id}/read`. Authorization matrix rows 53-54 accept only the login `READ`/`EDIT` permissions, not the OAuth `mcp:read`/`mcp:edit` scopes.

- **Kinds**:
  - `ITEM` is a 1:1 chat between someone asking about an item and its current owner. Asking about your own item returns 409. Creating a new one for a PRIVATE item the caller may not see returns 404 (item visibility gate); existing chats stay accessible.
  - `GROUP` is for the organizer and the active members of a PRIVATE group. It is read-only while the group is PUBLIC.
  - `TERM` is for the organizer and the non-withdrawn attendees of a term.
  - GROUP and TERM chats are read-only once their group is soft-deleted.
  - `EVENT` (`POST /api/conversations/event {event_id}`, migration `0071`; one per event via the partial unique index `uq_conversations_event_id`) is for the event's author and its active attendees. Withdrawing revokes access on the next request, and the chat stays open (never read-only) after the event ends. Deleting the event cascades to the conversation, its messages and read markers.
- **Access computed per request**: no participant table is stored. Every call resolves the caller's right to read or write from current group, term, event and item state, in `application/access.py`. The inbox uses the same audience (EVENT chats listed via `events_acl`: events the party authored or actively attends), and the `/{id}` routes return 404 before 403. Foreign contexts are reached only through `infrastructure/{groups,inventory,users,events}_acl.py`.
- **Read markers**: `conversation_reads` holds one `last_read_at` per party and conversation. `POST /{id}/read` takes a `message_id` and only moves the marker forward. Sending upserts the sender's own marker, and read-only chats can still be marked read. The unread badge counts messages, not conversations.
- **Send ordering**: moderation runs first, outside the lock. The send then takes `SELECT … FOR UPDATE` on the conversation row and stamps `created_at = max(utcnow, last_message_at + 1 µs)`, so commit order equals cursor order. An `after=` poll from the last server-fetched id never skips a row. Sending moves the sender's own marker to their message, so a message that crossed it is shown in the open thread but never counted as unread.
- **Keyset cursor**: `GET /{id}/messages` pages by message id on `(created_at, id)`, 50 per page with `has_more`. `before=` loads older history and `after=` polls for new messages. Both cursors at once, or a cursor from another conversation, return 400.
- **Polling, no push**: the frontend polls. The 💬 badge (`useUnreadMessages`) and the inbox (`useConversations`) poll every 20 s, and an open thread (`useThread`) polls `after=` every 5 s into one cached query. None of them polls in the background.
- **Moderation**: each body goes through `app/moderation/text_guard.check_text(TextField.MESSAGE_BODY, …)`. A rejection returns 400 and writes no row. If the guard is unavailable the send returns 503, and the composer keeps the text.
- **Rate limits**: `application/send_limiter.py` is an in-memory sliding window, like `join_code_limiter`. It allows 30 messages per minute and 20 new ITEM conversations per hour per party, and returns 429 with `Retry-After` when exceeded. Its state is **per uvicorn worker** and resets on restart, so the limits multiply if the app ever runs several workers.

## Group membership and visibility (`app/groups/infrastructure/`)

"A party is in a group" and "who sees what" are each defined once, as unexecuted SQL that the read paths compose.

## Search (`app/search/`)

A read-only module behind `/search`, built like `app/pages/`: it owns no table and writes nothing.

- **Layout**: `router/search.py` → `application/search.py` (`search_items`, `search_meetings`) → `domain/` (pure: `ranking.py`, `links.py` with the path f-strings only; the party/group slug rules are the groups ones, re-exported by `infrastructure/groups_acl.py`) and `schemas.py`. Other contexts only through `infrastructure/{groups,inventory,product,category,events,organizations,locations,users}_acl.py` (no media ACL: thumbnails come via product); no ACL imports `..schemas`. Boundary test `tests/test_module_boundaries.py`: only `app/main.py` imports `app.search`, and outside `infrastructure/` it imports only `app.core`, `app.db`, `app.storage` and `app.search`. `tests/test_domain_clock_guard.py` covers `app/search`.
- **Endpoint**: `GET /api/public/search` (PUBLIC via the `^/api/public/.*$` row, `OptionalPrincipal`; an unresolvable token is a guest). Params: `q` (≥2 characters after folding, ≤100; blank or absent is a browse: the newest listed items within the item filters, ranked 0, or only the upcoming terms and events — no groups or organizations — soonest first, with `other_mode_count` the other mode's browse total), `mode` `items|events`, `scope` `mine|all` (default `all`, guests forced to `all`), `category`, `condition`, `offer_type`, `date_from`/`date_to` (terms and events by their date; with a window a group appears only when its next term inside the window exists, and links to it; `date_from` is clamped to now), `page` (≤ 50, deeper is 400), `size` (≤ 100). Every search statement runs under `SET LOCAL statement_timeout = '3s'` (search transaction only, not the engine); a statement it cancels (SQLSTATE 57014) is a 503 `ServiceUnavailableException` „Wyszukiwanie trwa zbyt długo. Spróbuj zawęzić zapytanie.” without cache headers, other database errors stay 500. Guests get `reserved_until: null` (still `reserved: true`). Response `SearchPage {items, total, page, size, other_mode_count}` with kind-discriminated results (`product`, `term`, `event`, `group`, `organization`). `other_mode_count` is the other mode for the same `q` and scope without filters, computed sequentially. `set_personalised_cache_headers(response, principal)` after success.
- **Near a locality** (both modes): `locality` (a 7-digit SIMC id; unknown = 400) with an optional `radius` in km (0–100, 400 without a locality; unset = that locality alone). One extra statement loads the origin's point, then `_near` keeps a place in the origin locality or within the radius (haversine in SQL, no PostGIS). Items are placed by their place's locality point, never the exact address; terms and events by the address's own point when it has one (Google address or a pin), else the locality's. With a locality the meetings list holds only terms and events (groups and organizations have no place), and `other_mode_count` is counted around the same locality. The 21 localities without a point match by id only. The `/search` „Filtry” sheet (opened by the round button beside the search field) has „Lokalizacja” in both modes: a `LocalityCombobox` plus „Tylko tu” / +10 / +25 / +50 km; `locality` and `radius` live in the URL and survive the mode switch. Guests pick a locality through the public `GET /api/public/localities?q=&limit=` and `GET /api/public/localities/{id}` (the same dictionary search as `/api/localities`, no login); they are not in the nginx rate-limit list yet. Without a locality the section also offers the one picked last on this device (`features/search/lastLocality.ts`, localStorage `search.lastLocality`, a suggestion only, never applied by itself) and a voivodeship `<select>` with its larger towns as chips from `GET /api/public/localities/major` (the 66 cities with county rights: `kind = TOWN` and `powiat = name`, the dictionary has no population; declared before the `{id}` route).
- **Matching**: `fold_pl()` (0087) folds the query and the indexed text in SQL; `search_vector @@ plainto_tsquery('simple', …)` on products, events and terms (group, organization and place names are joined at query time) and the trigram word-similarity `<%` on folded names, `fold_pl(groups.description)`, `fold_pl(organizations.slug)` and `categories.path_text` (a category matches on `path_text` only, which ends with its folded name; the name still ranks the leaf with weight B); `q` is always a bound parameter. ## Wants (`app/wants/` and `src/matcher/`)

A want („Szukam”) is what a logged-in party is looking for: a name, optionally a category, an offer mode, a locality with a radius, and a note only the seeker sees. The backend module `app/wants` stores wants, serves them and writes the bell rows. The matching runs in a separate process, the **matcher service** (`src/matcher`, compose service `matcher`), which reads and writes the backend's database in raw SQL through a contract defined in migration `0099_wants` (amended, see the 0099 runbook) and extended by `0100_pgvector` and `0101_want_similar` for the semantic SIMILAR tier (see the 0100–0101 runbook). Tables `wants`, `want_matches`, `want_scan_markers`, `product_embeddings` and `want_embeddings`.

**Semantic tier release gate**: SIMILAR („Powiązane rzeczy”) ships behind the gate of the 0100–0101 runbook (at least 300 labelled pairs scored on the deployed int8 export), which must pass before that runbook's web step (step 8); the shadow deploy of steps 1–7 may run first. `SEMANTIC_SIMILARITY_MIN = 0.86` (`matcher/rules.py`) is provisional until that sweep sets it, and it holds only for the pinned `EMBEDDING_MODEL_ID`.

**Release gate (a rule, not a switch)**: the feature has no feature switch. **Do not deploy it until the labelled Polish sample (at least 200 want/item pairs, a follow-up task) has been scored against the per-word rule (stems, stop-list, the 4-character exact limit and the 0.65 word similarity) and the thresholds are set from it.** `WORD_SIMILARITY_MIN = 0.65` (`src/matcher/matcher/rules.py`, a bound parameter, changed there) and the 4-character short-word limit are starting values and have not been measured. The short-word limit is **not** tunable in `rules.py` alone: `stem_word_pl` and `stem_query_pl` in `0099_wants.py` hard-code it, and the stored `wants.stem_query`/`stem_words` are generated from them; `rules.SHORT_WORD_MAX_CHARS` only mirrors it for the similarity check, pinned by `src/matcher/tests/test_constants_drift.py::test_stemQueryPl_shortWordExact_oneCharLongerIsAPrefix`. Changing it means, while 0099 is unreleased, amending 0099 (and re-running the old-0099 detection and downgrade/upgrade path of runbook steps 4–5 on every database already at 0099); after release, a new revision that replaces both functions and DROP/ADDs the generated `wants` columns (runbook, **Future changes**). Either way, the same value goes into `rules.py` and the drift test must pass.

### Name vectors (`app/embeddings`, the product and want writers)

- **Embedder** (`app/embeddings`, compute only; imports only `app.config`, `app.core` and itself, `tests/test_module_boundaries.py`): `sdadas/mmlw-roberta-base` as an int8 ONNX export in `EMBEDDINGS_MODEL_DIR` (default `/models/embed`), CLS pooling and L2 normalisation, 768 dimensions. Listing names are embedded as stored, want names with the query prefix „zapytanie: ”. `EMBEDDING_MODEL_ID = "sdadas/mmlw-roberta-base@bdeb29a43c3d58af1e6ed9d1836703a1ddfbe1d7+int8"` (`app/embeddings/service.py`) must equal the model directory's `model_id.txt` (checked at load), the Dockerfile ARGs and `matcher/rules.py` (drift tests). Inference runs on a dedicated single-worker executor, so moderation's `to_thread` calls never queue behind it; `EMBED_TIMEOUT_SECONDS = 2.0` per name on the write paths and handlers, `RECONCILE_EMBED_TIMEOUT_SECONDS = 2.0` per reconcile batch of 8 names. A call that outlives its timeout cannot be cancelled; while it runs, `is_busy()` is true and every call misses as `busy`.
- **Fail open**: every miss (`missing`, `busy`, `timeout`, `error`) is one WARNING `Embedding skipped reason=… texts=… timeout_seconds=…` that never names the text, and the write commits without a vector. With `EMBEDDINGS_ENABLED=false` (the default) nothing is embedded, no retry is staged, the reconcile does nothing and the stored vectors and SIMILAR rows stay readable.
- **Writers** (synchronous, best effort): a product create, rename or get-or-create by name (`app/product/service.py` → `app/product/embeddings.py`) and a want create or name-changing edit (`app/wants/application/writes.py` → `embeddings.py`; the want name is embedded on the unlocked read, before the row lock) store the vector in the caller's transaction. `update_product` flushes the product row before it writes the vector, so a rename takes its locks in the same order as the handler and the reconcile (the product row first, then its vector row) and cannot deadlock against them. On a miss a renamed product or want loses its stale vector (a stale meaning is never matched) and, while embeddings are on, an `embeddings.requested` outbox row (`{"subject": "product"|"want", "id": …}`) is staged for the retry. The handlers read the owner's current name and embed it with no row lock held; then, in a savepoint, they take the owner's row lock with plain `FOR NO KEY UPDATE` (never `SKIP LOCKED`, so a row held by a rename is not taken for gone; never `FOR UPDATE`, so an item insert's `KEY SHARE` on `products` is never blocked), re-check that the name is still the one embedded and upsert. The lock is held only for that check and the upsert, never during inference. A miss raises, so the outbox dispatcher retries and finally marks the row FAILED.
- **Reconcile** (`_run_embedding_reconcile` in `app/main.py`, APScheduler every 1 min, always scheduled, a no-op without an embedder): products, then ACTIVE wants, without a vector or with another `model_id`, at most 300 per tick in sub-batches of `RECONCILE_EMBED_BATCH` = 8 names, so a user write waits behind at most one batch (~0.1 s). Like the handlers, a sub-batch is embedded with no row lock held; then its rows are locked `FOR NO KEY UPDATE SKIP LOCKED`, their names re-checked (for a want also that it is still ACTIVE and not expired) and the vectors upserted. Both sides return the `ReconcileResult` type shared from `app/embeddings`. Reconcile batches are kept small, or yield, so user writes do not wait behind them. One log line `embedding reconcile: products=… wants=… misses=… duration_ms=…`; a `busy` miss ends the tick, a lost race (deadlock, serialization failure) is one WARNING and retried next tick, products and wants run in separate sessions with their own error handling, so a failure on one side (logged with the side named) counts as 0 and the other side still runs; the summary line is always logged. It is the backfill after 0101 and repairs FAILED retries.
- **Re-triggers**: a product vector written later moves `matchable_listings.changed_at`, so the window reads the listing again. A want vector filled in the background (handler or reconcile) sets `similar_requested_at`, never `match_requested_at`, through a Core update that leaves `updated_at` (the version column) alone, so no lexical pair is stored born seen behind the seeker's back and a concurrent seeker edit gets no 409.

### Tiers and the match rule

`src/matcher/matcher/statements.py` holds six `INSERT … SELECT … ON CONFLICT … RETURNING` statements into `want_matches`, one per tier (MATCH, SUGGESTION, SIMILAR) and direction. A stored pair is left alone, except that the lexical statements upgrade a stored SIMILAR row (see SIMILAR below). A pair is a candidate when the shared predicates hold:

1. The want is ACTIVE, `expires_at > now` and has at least one word (`stem_words` not empty).
2. The listing is in `matchable_listings` and its owner is not the seeker.
3. The seeker may see it: the listing is PUBLIC (a plain column comparison at the call site), or PRIVATE and `EXISTS` a `private_group_peers` row for owner and seeker.
4. Offer mode: the want has none, or it equals the listing's mode.
5. Category: the want has none, or its category is in the listing's `category_path` (the product's category and its ancestors).
6. Locality: the want has none, or the item's place is in that locality, or the haversine distance between the two locality points is at most `radius_km`. Without a radius, or when either locality has no point, only the same locality matches.
7. The pair is not stored yet, or, for MATCH and SUGGESTION, it is stored only as SIMILAR.

The name is then checked **word by word** (`stem_words` is position-aligned with `words_pl(name)`): a want word hits when its stem prefix (a short word: its exact lexeme) is in weight A of the product's `search_vector`, or, for a word longer than 4 characters, when its trigram `word_similarity` to the listing's folded name is at least 0.65.

- **MATCH**: every want word hits. The first 20 per want and run, ranked by score, newest listing, item id. Stored pairs are left out before the ranking, so a later run adds up to 20 further pairs.
- **SUGGESTION** („Może Cię zainteresuje”): a want of at least 3 words where exactly one word misses and at least 2 hit; `missing_words` names the missing word as the seeker wrote it. At most 10 per want (only stored suggestions whose item is still in `matchable_listings` count, so suggestions for items that left are replaced; counted from the run's snapshot, so two concurrent runs can store slightly more; `/suggestions` returns at most 10). Suggestions are stored seen and never ring the bell.
- **SIMILAR** („Powiązane rzeczy”): no word check. The want's vector and the listing's vector, both of `EMBEDDING_MODEL_ID` (`we.model_id`/`l.model_id` bound as `$6`), lie within `SEMANTIC_SIMILARITY_MIN` cosine similarity (`embedding <=> … <= 1 - 0.86`; the score is `1 - distance`), and the lexical tiers would not claim the listing: a listing that qualifies for MATCH or SUGGESTION is never SIMILAR, whether or not that tier stores it in the same run, so a lexical candidate capped out of its tier is not shown as SIMILAR either (it keeps its lexical tier for a later run). At most 10 per want (`SEMANTIC_CAP`, counted like suggestions: only stored SIMILAR rows whose item is still in `matchable_listings`). Runs last in every run (MATCH → SUGGESTION → SIMILAR), is born seen in both directions and never rings the bell. **Upgrade**: a stored SIMILAR pair is upgraded in place to MATCH or SUGGESTION when a later run finds it lexically (for example after the owner re-points the item to another product). The upgraded row takes that tier's seen rule: a window MATCH is born unseen and rings its bell, a forward MATCH and every SUGGESTION are stored seen. Never the reverse: a MATCH or SUGGESTION row never becomes SIMILAR (the unique pair key). A want or listing without a current vector simply has no SIMILAR pairs. **Stale pairs**: a stored SIMILAR row is never re-scored. A pair found for an old name (a product renamed in place) or under an old `EMBEDDING_MODEL_ID` stays until the want is edited so that it matches differently (which deletes all its matches) or the item leaves `matchable_listings`; until then it is listed by `/similar` and counts toward `SEMANTIC_CAP`.
- **Counts**: `match_count` and `new_match_count` count MATCH only. The closing prompt (`?matched_item_id=`) ignores SIMILAR.

Directions:

- **Forward** (one claimed want against all listings, request loop): pairs get `source = FORWARD` and `seen_at = now` for every tier, so they are never "new" and get no bell. SIMILAR forward is an exact scan over the listings' vectors (the want vector an InitPlan evaluated once; about 37 ms p95 at 20,000 listings, linear in the listing count). The listings are reached through the product text indexes (`search_vector @@` any of the want's stems, or `name_folded <%` the folded product name); the want's values are read through scalar subqueries so the planner keeps the index conditions with the multi-table view.
- **Window** (every matchable want against the listings created in `(start, end]`, window loop): `source = SCAN`; MATCH pairs are unseen (they ring the bell), SUGGESTION and SIMILAR pairs are stored seen. The window's listings sit in a `MATERIALIZED` CTE selected from the view, and offer mode, category and locality are compared before the names (`CASE WHEN <plain columns> THEN <name check> ELSE false END`).

Both directions share every predicate and store the same pairs.

### Matcher service

`python -m matcher` (`src/matcher/matcher/__main__.py`): wait for the contract, then run the request loop and the window loop until stopped. asyncpg, a pool of 1–4 connections plus one LISTEN connection (≤ 5 per copy). Any number of copies can run: claims skip locked rows and the window runs under an advisory lock.

- **Startup gate** (`db.wait_for_contract`): retries until `alembic_version` is at least 101 (`CONTRACT_REVISION`) **and** `to_regclass` is set for `public.matchable_listings`, `public.product_embeddings` and `public.want_embeddings`, logging „waiting for the database contract (attempt N): …” and then „database contract ready (attempt N)”. It never logs the DSN or a connect error's text.
- **Request loop** (`requests.py`): LISTENs on `wants_changed` (log line „listening”), and polls every 10 s as well; on each wake-up it drains the flagged wants, one transaction per want. Two request kinds share one claim: a **full** request (`match_requested_at`, a seeker's write) and a **SIMILAR-only** request (`similar_requested_at`, a background vector fill). The claim takes a want with either flag `FOR NO KEY UPDATE SKIP LOCKED`, full requests first, then the oldest flag. For an ACTIVE want a full claim runs the three forward statements (MATCH, SUGGESTION, SIMILAR); a SIMILAR-only claim runs only the forward SIMILAR statement, so a background re-trigger stores no lexical pair born seen and the window still rings the bell for a lexical one. Clear rules, compare-and-clear against the claimed values (a newer request stays) without touching `updated_at` (a seeker's loaded version stays valid): a full claim clears `match_requested_at` when it still equals the claimed value and, since a full run includes SIMILAR, `similar_requested_at` when it is at or before the claimed one; a SIMILAR-only claim clears only `similar_requested_at` when it still equals the claimed value. A failing want is rolled back with both flags kept. A lost LISTEN connection is reconnected.
- **Failing wants** (H4): a per-process in-memory backoff map skips a failing want (for claims of either kind) for 60 s, doubling to 15 min, cleared on success, so one want never blocks the others. No schema state.
- **Window loop** (`window.py`): every 60 s one run under the session advisory lock `pg_try_advisory_lock(0x77616E7473)` (a run held by another copy is skipped at DEBUG; released after the run), in **two transactions**, each with `statement_timeout = 30s` and `jit = off`. The **sweep** (steps 1–3 and the reminders' outbox row) commits first; the **match** (steps 4–6) follows. A failing or timed-out match rolls back only itself: the sweep stays committed and the marker stays, so the next run repeats the match.
  1. **Expire**: ACTIVE wants with `expires_at <= now` become EXPIRED with `closed_at = expires_at`.
  2. **Remind**: ACTIVE wants with `expires_at <= now + 7 days` and `reminded_at IS NULL` get `reminded_at = now`; once per validity period, whatever the want's notification switch.
  3. **Purge**: wants that are not ACTIVE and have `closed_at <= now - 30 days` are deleted; their matches go with them (CASCADE), their bell rows stay. The sweep stages one `wants.bells_due` row `{"pairs": [], "expiring": [...]}` for the reminded wants (none without any).
  4. **Window match** (MATCH, SUGGESTION, then SIMILAR) of the listings whose `changed_at` lies in `(start, end]`. On the first run `start` is `now - 20 minutes`. After that it is `max(marker - 2 minutes, min(marker, previous_run_at - 2 minutes))`, where `previous_run_at` is the marker's `updated_at`, the clock of the run that moved it (`window.window_start`). The overlap is for a listing whose `changed_at` predates its commit by up to 2 minutes, so the previous run's snapshot missed it. That can only happen within 2 minutes before the previous run's clock, and the unique key of a pair makes the repeat harmless. After a capped run whose `end` lies further back, the next run starts at the marker itself and re-reads nothing. `end` is `now`, unless more than `WINDOW_MAX_LISTINGS = 300` matchable listings wait after the marker (`WAITING_LISTINGS`, `LIMIT 301`). Then `end` is the `changed_at` of the 300th, every listing tied with it is included (`changed_at <= end`), and the run is **capped**. A run reads at most about 300 listings (plus ties) and those changed in the 2 minutes before the previous run's clock, so the window does not grow from run to run. Pair timestamps (`created_at`, `seen_at`) are still the real `now`.
  5. **Bells due**: `wants.bells_due` outbox rows for the new MATCH pairs (`outbox.py`), always with `"expiring": []`; reminders come only in the sweep's row. The handler contract is unchanged.
  6. **Marker**: compare-and-set `scanned_through = end`, with `updated_at` (and `created_at` on the first insert) set to the run's real `now`, so the marker stays the liveness signal during a drain and gives the next run its overlap; a miss is a lost race and rolls the match back. If the explicit unlock fails (a broken connection), it is logged at DEBUG so the run's own error is the one logged; the server or the pool reset drops the lock. Then one log line `window run: start=… end=… capped=True|False matches=… suggestions=… similar=… outbox_rows=… expired=… reminded=… purged=… duration_ms=…` (INFO when the run did anything or was capped, DEBUG otherwise). After a capped run the loop starts the next one at once instead of sleeping, until the backlog is drained (about 300 listings and roughly 13 s per back-to-back run at 10,000 wants).
- **Concurrency**: request-loop claims and the backend's re-matching edit both take `FOR NO KEY UPDATE` on the want, so they serialise; window inserts need only the FK's `KEY SHARE` and never wait behind a claim. Expire and remind set `updated_at`, the version column, so a seeker's write that loaded the want before the run gets the 409 instead of overwriting it.
- **Failure policy** (`db.log_failure`): a deadlock (`40P01`), serialization failure (`40001`) or a lost marker race is one WARNING and the work is repeated later; anything else is logged once with its traceback and not re-raised, so the loops keep running.
- **Shutdown**: on SIGTERM or SIGINT the matcher logs `<SIGNAL> received, stopping` (e.g. `SIGTERM received, stopping`), cancels both loops (an open transaction is rolled back), closes the pool within `SHUTDOWN_GRACE = 5 s` (else terminates its connections with a WARNING), logs `stopped` and exits 0, so `docker stop` (10 s) ends it cleanly. Compose restarts it (`restart: unless-stopped`); it has no healthcheck (python is PID 1, so a process check proves nothing more than a running container), and its health signal is the window log line and the marker (runbook step 7).

### Bells (outbox)

In-app only: rows in `notifications` shown by the bell. Two kinds, both for the want's seeker: `WANT_MATCH_FOUND` and `WANT_EXPIRING`. The matcher never writes `notifications`; it stages `wants.bells_due` outbox rows, the reminders in the sweep transaction and the MATCH pairs in the match transaction:

```json
{"pairs": [["<want_id>", "<item_id>"], ...], "expiring": ["<want_id>", ...]}
```

At most 1000 pairs per row (as `storage.objects_delete` takes ≤ 1000 keys); a run's reminded wants go in the sweep's row with `"pairs": []` and every match row has `"expiring": []`; the insert sets every NOT NULL column of `outbox_entries`. The backend's handler `application/bells_due.py` (registered in the lifespan through `outbox_acl`, dispatched by the 60 s outbox poller with `SKIP LOCKED` and a commit per entry) runs in a savepoint and **re-checks** each pair: a bell only while the pair is still stored as MATCH and passes `visible_matches` (an edit may have deleted it, the item may have left the seeker's sight), a reminder only while the want is ACTIVE. So a bell arrives at most about 2 minutes after the listing (≤ 60 s window + ≤ 60 s poll). It then calls `match_notifications.write_bell_rows`:

- **Match row**: one per want with new pairs and `notifications_enabled`. One new pair names the item („Szukasz: «…». Ktoś wystawił: «…».”) and links to the item page; several give a count and link to `/wanted/{id}`.
- **At most one unread match row per want**: if the previous one (`match_notification_id`) is still unread, it is deleted and its count is added to the new row's; a read one stays and the new row counts the new pairs only. The want's pointer and count are then set to the new row.
- **Muted want**: no match row; the pairs are still stored and the pointer and count are kept.
- **Reminder row**: one `WANT_EXPIRING` per reminded want, linking to its match list; it ignores the switch.
- **Removing the match row**: an edit that re-matches and a withdrawal delete the unread match row and reset the pointer. Marking matches seen does not touch it.
- `app/notifications/service.py` `create_notifications(db, entries)` (one multi-row insert returning the ids in entry order) and `delete_unread_notifications(db, ids)`; neither commits. Messages are capped with `clock.fit_notification_message`.

### Lifecycle

`domain/lifecycle.py` holds which status allows which action; a refused action is 409 with a Polish message. "Flags" = sets `match_requested_at`, so the matcher runs a forward match within seconds and the response carries `matching: true`.

| Action | Allowed in | Effect |
|---|---|---|
| Create | — | ACTIVE, `expires_at = now + 90 days`, flags. 409 at 30 ACTIVE wants. |
| Edit (`PATCH`) | ACTIVE | Only the sent fields change. The text checks and lookups run on an unlocked read; then the want row is locked `FOR NO KEY UPDATE` and its version (`updated_at`) compared with the read: a seeker write committed in between is the shared 409 (`StaleDataError`), and the status is checked again under the lock. Clearing the locality clears the radius. A changed name, category, offer mode, locality or radius deletes the stored matches of every tier and the unread match row, then flags (a changed name also replaces the want's vector, see **Name vectors**); the note and the notification switch do not. |
| Extend | ACTIVE | A new 90-day period from now, `reminded_at` cleared; matches stay. |
| Close | ACTIVE | `FULFILLED` or `WITHDRAWN`, `closed_at = now`. The closing response still returns a withdrawn want; every later request for it is 404. |
| Resume | EXPIRED, FULFILLED | ACTIVE for a new period (the cap applies), stored matches kept, flags so the forward match adds the missing pairs. |
| Expire | ACTIVE | By the matcher's window run, see above. |
| Seen (`matches/seen`) | any but WITHDRAWN | Every unseen stored match becomes seen. An ACTIVE want with 30 days or less left also starts a new period. |
| Purge | not ACTIVE, closed 30 days | By the matcher's window run; matches go with the want. |

Name and note are checked before any database statement: `ensure_no_contact_info`, then `check_text` with `TextField.WANT_NAME` and `TextField.WANT_NOTE` (synchronous; on an edit only a changed text). Rule violations are 400 with a Polish message. On an edit these checks and the lookups below run before the want is locked, so the classifier (up to 5 s) never holds the row lock; the stored matches are still deleted under the lock (H3). Then one statement asks `public.words_pl` (the stop-list lives only there, `writes._ensure_name_has_word`): a name of stop-words only is 400 „Wpisz, czego szukasz — nazwa nie może składać się z samych spójników i przyimków.” on create and on a name-changing edit. An unknown category or locality is 400. A write that deadlocks or fails to serialize is rolled back and answered with the shared `StaleDataError` 409; there is no statement timeout on the backend write path any more.

### Known limits

- **Changes the window does not see**: a listing is read again when its `changed_at` moves (edited, mode or visibility changed, available again, proposal rejected), but not after a place edit (a new locality for a radius want) or a category moved in the tree. A product renamed in place is read again once it is re-embedded (its vector write moves `changed_at`); not while embeddings are off, and not until the retry or the reconcile lands after an embed miss. A forward match (create, resume, re-matching edit) still finds it. Re-reading an edited listing costs one more window pass for it; pairs already stored are skipped.
- **Fixed stop-list and stemmer**: extending the stop-list or changing a suffix is a new revision with DROP/ADD of the generated columns (runbook, **Future changes**). The stemmer is a suffix list, not a dictionary.
- **In-app notifications only**: no e-mail and no push. SIMILAR has no bell, badge or count at all.
- **SIMILAR scans exactly**: no vector index, so forward SIMILAR grows linearly with the listings (about 37 ms p95 at 20,000; a synthetic worst case with every listing within the distance took 334 ms). Revisit an index (iterative scan, short-result tests) at about 500,000 listings or a forward above 200 ms.
- **Vector writes are best effort**: a missed embed leaves the product or want without a vector until the `embeddings.requested` retry or the next reconcile tick; until then it has no SIMILAR pairs. The int8 parity margin is thin (0.9904 against the 0.99 gate), so an onnxruntime or model change can fail the build.
- **The match list has no limit and no paging**; each run adds at most 20 MATCH pairs per want.
- **Bell-row timestamps**: `create_notifications` stamps `created_at` from its own `datetime.utcnow()`, not from the matcher run's `now`.
- **Backoff is per process**: a restarted matcher retries a failing want at once.
- **Window cost**: about 43 ms per takeable listing at 10,000 wants for both tiers together (re-measured after the verification fixes; 39 ms before), so about 21 ms per statement. A run matches at most 300 new listings (`WINDOW_MAX_LISTINGS`, about 6.5 s per statement and 13 s per capped run against the 30 s statement timeout), and the overlap re-reads only listings created in the 2 minutes before the previous run's clock, so a backlog, a burst or a run of equal `created_at` drains at about 300 listings per back-to-back run instead of growing past the timeout. The remaining limit is the rate near real time: more than roughly 1,000–1,200 listings created within 2 minutes can put one run over the timeout. That run then fails the same way on every retry, because its marker and overlap stay put; the sweep keeps running, and the repeated `window run failed` ERROR with the same `start` is the signal (about 500 listings a minute is the sustained ceiling). Sustained traffic above about 300 new listings per run keeps the matcher capped and the bells late; watch `capped=True` and `duration_ms` in the window log line. Follow-up: batch `visible_matches` in the bells handler (one statement per distinct seeker, about 3 s per 1000-pair row). Details in the 0099 runbook, **Measured cost**.

## Points and reputation (`app/points/`)

Stage 1 of the points system: people earn non-transferable points for giving items away, for swaps, for giving someone an item from their „Szukam” list and for attending terms, and a separate reputation counter measures generosity. Both come from an append-only ledger and are visible only to their owner; spending (the POINTS offer mode) is stage 2. Tables `point_accounts`, `point_transactions`, `point_entries` and the single-row `points_config` (migrations 0103–0105, see the 0103–0105 runbook).

- **Layout**: `router.py` (`/api/points`) → `application/` (`config.py` the tunable config, `awards.py` the exchange and attendance awards, `reads.py` the owner reads) → `domain/` (pure: `valuation.py`, `awards.py` the award planning), plus `models.py`, `schemas.py` and `service.py`, the entry points the consumer ACLs call. Other contexts are reached only through `infrastructure/`: `ledger.py` (the only writer of the ledger tables), `category_acl.py`, `users_acl.py`, `families_acl.py`, `wants_acl.py` and `inventory_acl.py`. The wants, inventory and category ACLs use ad-hoc `table()`/`column()` refs instead of importing those modules (no `app.wants` import, so the wants boundary guard holds, and no inventory ↔ points import cycle); `users_acl` and `families_acl` import those models.
- **Both ACL directions**: `app.points` is imported only by `app/main.py`, `groups/infrastructure/points_acl.py` (confirm awards, attendance rules and awards) and `inventory/infrastructure/points_acl.py` (item valuation). Boundary tests in `tests/test_module_boundaries.py` (not a `MODULES` entry, which assumes `main.py` as the only importer): the importers of `app.points` are exactly `main.py` and those two ACLs (an equality check, so a missing or extra importer fails), outside `infrastructure/` it imports only `app.core`, `app.db` and `app.points`, and `domain/` imports only itself. `tests/test_domain_clock_guard.py` covers `app/points`.
- **Ledger contract** (docstring of `infrastructure/ledger.py`): `TRANSACTION_RULES` declares each type once — its source type, whether it uses a pair slot, whether it counts toward reputation and which account type is debited (always EMISSION in stage 1) — pinned by a completeness test. `post_points` is the only writer of `point_transactions`/`point_entries` (a test guards that nothing else constructs them); it checks that the rule exists, no amount is 0 and the amounts sum to 0, refuses to debit a PARTY account (so no balance goes below 0), raises `LedgerInvariantError` (a `RuntimeError`, so a logged 500, never a 400) before writing anything, and only flushes. The source key `(transaction_type, source_type, source_id)` is unique (`uq_point_transactions_type_source`): callers skip a key that `source_key_exists` reports, and the constraint (IntegrityError → 409) is the backstop for a concurrent post. One SYSTEM account, EMISSION (partial unique index), is seeded by 0105; PARTY accounts (`uq_point_accounts_party_id`) are created lazily, only for PERSON parties with a login, by `lock_accounts` (a sorted Core `INSERT … ON CONFLICT DO NOTHING` with explicit timestamps, then `SELECT … FOR UPDATE ORDER BY party_id`); reads never create one. **Balance** = `SUM(point_entries.amount)` of the account; **reputation** = the SUM of its GIVE_FREE entries; neither is stored, and a person without an account reads 0/0. `point_transactions` keeps `party_id` (the beneficiary; the lower party id for EXCHANGE), `counterparty_party_id` (NULL exactly for ATTENDANCE), `cap_month` (set exactly for ATTENDANCE), a `description` frozen at posting (product name, „A ↔ B”, or the group name) and naive-UTC `occurred_at`, with the index `ix_point_transactions_party_counterparty_occurred_at` (shorter than the spec's name, to fit PostgreSQL's 63-character identifier limit).
- **Entry shapes**: GIVE_FREE = EMISSION −v, giver +v (v = the item's `points_value`), source the gift leg, one pair slot, reputation +v; EXCHANGE = EMISSION −2a, each party +a (a = `swap_award`), source the lower leg id, one pair slot per swap; WISHLIST_MATCH = EMISSION −b, leg giver +b (b = `wants_bonus`), source that leg, its own pair slot; ATTENDANCE = EMISSION −n, attendee +n, source `term_attendances.id`, no pair slot. Only GIVE_FREE counts toward reputation.
- **Valuation** (`domain/valuation.py`, own string keys, Decimal): `raw = base[size_class] × multiplier[condition]`, snapped below 30 → 20, 30 to under 50 → 40, 50 and above → 60 (thresholds and the three values fixed in code). `size_class` comes from `category_acl` (an upward recursive CTE built with `join_from`: the nearest non-NULL class, MEDIUM when there is none up to the root; pinned by a lint-compile test). `inventory_items.points_value` (SMALLINT, nullable) is set by `register_item` and recomputed by `update_item` only when the condition or `product_id` actually changes, both through `inventory/infrastructure/points_acl.py`; a `size_class`, product category or config change never recomputes stored values. `categories.size_class` (`SMALL`/`MEDIUM`/`LARGE`, NULL = inherit, roots MEDIUM from 0105) is returned in `CategoryResponse` and accepted by the category create and PUT (a full replace: an omitted value resets to inherit).
- **Award rules at confirm** (`points.service.award_exchange`, flush-only): `groups.confirm_transaction` calls it through `groups/infrastructure/points_acl.py` after `_may_confirm` passes and **before** the listing preferences are deleted, in every reservation context (term, event, personal). Both user ids map to parties through `users_acl`; nothing is posted when either is not an eligible PERSON with a login, when both are the same party, or when they share an active `FamilyMembership` in one family (`families_acl`, the `list_family_party_ids` query shape). Both accounts are then locked in party-id order and the **pair limit** counts the pair's GIVE_FREE, EXCHANGE and WISHLIST_MATCH transactions in either direction within `pair_window_days`; each award posts only while `used < pair_reward_limit` and increments it. GIFT: GIVE_FREE (skipped when `points_value` is NULL or 0), then WISHLIST_MATCH. SWAP: EXCHANGE, then per leg in reservation-id order a WISHLIST_MATCH to that leg's giver. **Wants bonus (Q1)**: due when the recipient party (`wants.seeker_party_id`) has a `want_matches` row of tier MATCH for that leg's item and the want was ACTIVE at reservation time — created by then (`wants.created_at <= reservation.created_at`) and `status = 'ACTIVE'`, or `FULFILLED` with `closed_at >= reservation.created_at`; a want resumed after the reservation still counts, since no status history is kept (so the close-want prompt after a take does not cancel it); WITHDRAWN, EXPIRED, SUGGESTION and SIMILAR never count (`wants_acl`, Core refs). A zero-value award posts nothing and uses no slot; an existing source key is skipped silently. The item transfer itself is unchanged, and an award that posts nothing never blocks it.
- **Conflicts**: `app/db.py::mapped_transaction_conflicts(db)` (moved out of `wants/application/writes.py`, where it was `_mapped_database_errors`; wants imports it from `app.db`) rolls back on a `40P01`/`40001` and raises `StaleDataError` → 409. `confirm_transaction` runs the award, the preference delete and `fulfill_exchange` inside it, so any failure rolls the award and the transfer back together (two parallel confirms give 200 + 409 and one award set); the attendance close, the presence PUT and the config PUT use it too.
- **Lock order**: term row (attendance only, `FOR UPDATE`) → point accounts (inserted and locked in party-id order) → item rows. On confirm the award is posted first, so the account locks come before the item row locks taken by the listing-status and projection UPDATE flushes; `fulfill_exchange` takes no `FOR UPDATE`, and concurrent moves are caught by the version column (`StaleDataError` → 409).
- **`points_config`** (one row, singleton index `uq_points_config_singleton` on `((true))`, every column NOT NULL): bases 20/40/60, condition multipliers NUMERIC(4,2) 1.50/1.25/1.00/0.75/0.50, `swap_award` 10, `wants_bonus` 10, `attendance_levels` `integer[]` {0,10,20} (1–5 distinct values, stored ascending), `attendance_monthly_cap` 40, `attendance_min_present` 3, `attendance_auto_close_days` 7, `pair_reward_limit` 3, `pair_window_days` 30, `max_points_offers` 5 (stored for stage 2, not enforced). `GET`/`PUT /api/points/config` (ADMIN, no cache headers); the PUT takes the full body plus the `updated_at` the client read, a mismatch is 409 „Konfiguracja została zmieniona w międzyczasie. Odśwież stronę.”, and validation lives in the application layer, so the 400s carry Polish messages. The config is read at award time, at close and by the job, so a change applies only to future awards.
- **Term attendance**: `terms.attendance_points` (NOT NULL DEFAULT 0; on create an omitted value is the lowest allowed level, a sent value must be in `attendance_levels` — 400 „Wybierz jeden z dozwolonych poziomów punktów.”; re-sending the current value is always a no-op, a different value after close is 409 (Q4); not in `TermResponse`, which a test pins), `term_attendances.present_marked_at` (non-NULL = present) and the close snapshot `attendance_closed_at`/`attendance_min_present`/`attendance_present_count`/`attendance_rewarded` (all NULL or all set, `ck_terms_attendance_closed`; partial index `ix_terms_occurs_on_attendance_open`). States from `clock.local_now()`: `NOT_STARTED` before `occurs_on`, `OPEN` from then until closed, `CLOSED`. Organizer-only routes (`_require_active_organizer` + `_require_term_in_group`, 403 before 409): `GET /api/groups/{g}/terms/{t}/attendance` (state, level, allowed levels, attendee count, live or frozen present count, min present, `auto_close_on` = `occurs_on` + `attendance_auto_close_days`, `rewarded`, `closed_at`), `PUT …/terms/{t}/attendees/{party}/presence` `{present}` → 204 (term `FOR UPDATE`, OPEN only, 404 without an active RSVP, idempotent) and `POST …/terms/{t}/attendance/close` → 200 with the attendance read. `TermAttendeeResponse` gains `present`.
- **Close algorithm** (`groups/application/attendance_points.py`, shared by the manual close and the job; `attendance.py` is untouched): lock the term (`FOR UPDATE`; the job adds `SKIP LOCKED`), re-check that it is open and started, count the active attendances with `present_marked_at` set, minus the parties who hold the group's current leadership (Q3: organizers neither earn points nor count toward the minimum; `membership.holds_active_leadership` as a correlated predicate, so soft-deleted groups included; the attendee list exposes the same rule as `is_organizer`, labelled in the UI and left out of „Teraz: X z Y”), `rewarded = attendance_points > 0 AND present_count ≥ attendance_min_present`, freeze the result on the term (Q2), and when rewarded call `points_acl.award_attendance` for the present rows: eligible persons only, accounts locked in party-id order, `award = min(level, monthly_cap − used in cap_month)` (the Warsaw calendar month of the close, so past-dated terms closed together share one cap), ATTENDANCE posted when above 0; one commit. A later withdrawal changes neither the frozen result nor the counts: `list_term_attendees` returns the **listed rows** of `repository.listed_attendance_condition` — the counted rows (while open the active rows; once closed the rows active at close, `withdrawn_at IS NULL OR withdrawn_at > attendance_closed_at`, with the presence they had then) **plus every PAID row**, so a PAID attendee who withdrew (before or after the close) stays listed as a refund case (see Paid terms). Each row carries `withdrawn` (`withdrawn_at IS NOT NULL`, any withdrawal) and `counted` (part of the attendance record, `repository.is_counted`); only counted rows drive the counts, counted rows sort first. A withdrawn row is reactivated by a new RSVP (`public_view.create_rsvp`): `withdrawn_at` is cleared, presence is cleared only while the list is open (after the close it stays as frozen) and the payment status is kept. `rewarded = true` does not promise anyone was paid (a person may be capped to 0 or ineligible).
- **Auto-close job**: `_run_attendance_close` in `app/main.py`, on the existing scheduler every 15 minutes (`_ATTENDANCE_CLOSE_INTERVAL_MINUTES`), runs `close_due_attendance`: candidate ids are read without locks (`attendance_closed_at IS NULL AND occurs_on <= local_now − auto_close_days`, oldest first, at most `CLOSE_BATCH_SIZE` = 100), and each is closed in its own transaction under `SKIP LOCKED` with the re-check, so a closed or locked term is skipped and a rerun is a no-op. A `40P01`/`40001` is one WARNING and the term is retried on the next run; any other failure is logged once with its traceback and the loop goes on; a failed candidate read is logged by the wrapper. One INFO line per run: `attendance close: closed=%d awarded=%d`.
- **Owner reads** (READ only, no `mcp:*` scope, `set_personalised_cache_headers`): `GET /api/points/me` → `{balance, reputation}`; `GET /api/points/me/history?page=&size=` → `Page[PointHistoryEntryResponse]` `{id, type, amount, reputation, description, counterparty_name, occurred_at}`, one row per account per transaction, `occurred_at DESC, id DESC`, counterparty names in one batched lookup (the statement count is constant in rows, pinned by a test). `GET /api/points/attendance-rules` → `{levels, min_present, auto_close_days}` (READ) for the add-term form.
- **Authorization matrix**: row 68 `GET, PUT ^/api/points/config$` → ADMIN; row 69 `GET ^/api/points(/.*)?$` → READ (no `mcp:read`); row 70 `PUT ^/api/groups/[^/]+/terms/[^/]+/attendees/[^/]+/presence$` → EDIT / `mcp:edit`, declared ahead of rows 26–27, which do not cover PUT; row 71 `PUT ^/api/groups/[^/]+/terms/[^/]+/attendees/[^/]+/payment$` → EDIT / `mcp:edit` (the paid-terms payment toggle), declared the same way. The attendance GET falls under row 26 and the close POST under row 27.
- **Visibility (R8)**: no points field (balance, reputation, `points_value`, attendance level or state) appears in `app/pages`, `app/search`, `TermResponse`/`PublicTermResponse`/`MyTermResponse`, item or inventory responses, `/actions` or `/details`; the existing exact key-set tests guard it. Only `CATEGORY_KEYS` (gains `size_class`, category reference data rather than a person's points), the organizer-only attendee key set (gains `present`), the search term `meta` and `PublicTermResponse` grew. The one exception to the rule is a term's attendance level (0 = none, public information about the term): `GET /api/public/search` returns it as `meta.attendance_points` (the „+N pkt” badge on the search term card, `features/search/SearchResultCard.tsx`) and the public circle read `GET /api/public/groups/{id}?term_id=` as `term.attendance_points` (the „+N pkt za obecność” badge with a „Co to są punkty?” link in the public term page's `TermCard`); the public explainer `/about/points` (`features/points/AboutPointsView.tsx`, `(public)` route group, reserved slug `about`, no configured numbers since the admin can change them all) is linked from that badge and from `/points`; the attendance state and everything about a person stay out, coming only from the organizer and owner reads.
- **Frontend**: `/admin/points` (`features/admin/PointsConfigPage.tsx` + `pointsConfigForm.ts`; nav label "Points" with the lucide Coins icon, ADMIN only); the size class select in `CategoryFormPage` („Klasa wielkości (wycena punktowa)”, „Dziedzicz …” plus the three classes with their bases) and the resolved class with „· dziedziczona” in `CategoryListPage` (inheritance resolved on the client from the loaded tree, `utils/categoryTree.ts`); `/points` (reserved slug, `features/points/AccountPointsView.tsx`; `AccountView` shows the same `PointsTiles` above its menu as a link to it, a client-only panel page: „Twoje punkty”, balance and reputation tiles, the „wkrótce” note, history with „Pokaż starsze”, empty and error states), linked from `AccountView` as „Moje punkty” with the balance as meta; hooks `usePointsConfig` and `useMyPoints` over `src/api/points.ts`. The term form level picker `features/terms/components/AttendancePointsPicker.tsx` („Punkty za obecność”, `aria-pressed` segments) is used in `TermEditForm` and `AddTermView` (no picker in the first-term stepper); the organizer attendance list `features/meetings/TermAttendeesPage.tsx` derives its view from `resolveAttendanceView()` in `features/meetings/attendanceViewState.ts` (checkboxes while OPEN, „Zatwierdź obecność” with a confirm dialog, read-only closed variants).
- **Out of scope / stage 2**: the POINTS offer mode with its recorded decisions (spending model A: the buyer's price burned and the giver paid from EMISSION as SALE, which never counts toward reputation; `points_price` frozen at listing and only lowered; a per-party HELD account on „Biorę”; widening `uq_point_accounts_party_id` to `(party_id, account_type)`; the enum ripple — see the task spec's stage 2 notes), START_BONUS (dropped), the objection stage and 7-day auto-confirm for GIFT, attendance at events, notifications about awards, badges and retroactive awards. Accepted farming surfaces (an organizer's past-dated term with friendly RSVPs, an owner raising `points_value` with condition NEW) are bounded by the monthly cap, the pair limit and the family rule.
- **Soft-deleted groups**: a term whose group was soft-deleted after it started still closes and pays its present guests (the presence was real); the organizer exclusion uses `membership.holds_active_leadership`, which has no deleted filter, so the organizer is neither counted nor paid there either.
- **Known limits**: history labels use a fixed „Odbiorca: …”/„Druga strona: …” prefix, because Polish names are not declined. Offset paging may repeat an entry when an award lands between pages.

## Paid terms (migration 0106)

Organizers can charge for circle terms: a price in złoty and an optional external payment link, plus a hand-kept „opłacone” mark per attendee. Nothing is charged by the platform; the data is shaped so that an own gateway can later set the same status. Migration `0106_paid_terms.py` (schema only, see the 0106 runbook).

- **Columns**: `groups.default_price` `Numeric(10,2)`, `default_payment_url` `String(500)`, `default_payment_method` `String(20)` (the Circle defaults); `terms.price`, `payment_url`, `payment_method` (same types; NULL price = free); `term_attendances.payment_status` `String(10)` NOT NULL DEFAULT 'UNPAID' (no table rewrite) and `paid_marked_at` (naive UTC, `datetime.utcnow()`). Models: `PaymentMethod` (`EXTERNAL_LINK`, `PLATFORM`) and `PaymentStatus` (`UNPAID`, `PAID`) StrEnums in `app/groups/models.py` via `_enum_column`, the CHECKs mirrored in `__table_args__`.
- **Nine CHECKs**: `ck_groups_default_price_positive` / `ck_terms_price_positive` (`> 0`, so "free" has the one representation NULL), `ck_groups_default_payment_url_requires_price` / `ck_terms_payment_url_requires_price` (a link needs a price; a price without a link — pay on site — is allowed), `ck_groups_default_payment_method_url` / `ck_terms_payment_method_url` (`num_nonnulls(url, method) IN (0, 2)`, to be relaxed by the future PLATFORM migration), `ck_groups_default_payment_url_https` / `ck_terms_payment_url_https` (`url IS NULL OR url ILIKE 'https://%'`: case-insensitive, so `HTTPS://…` passes like the API's `scheme.lower()` check and the client's `/i`, and the link is stored as typed; a backstop for the request validation against raw SQL or a future write path; the host and userinfo rules stay in the API) and `ck_term_attendances_paid_marked` (`(payment_status = 'PAID') = (paid_marked_at IS NOT NULL)`). The upper bound 100 000,00 lives in the API only, like capacity's `le=10000`.
- **Money on the wire**: `Decimal` in Python, a JSON decimal string such as `"25.50"` in requests and responses, `string` on the frontend, never a float (`standards/backend/models.md`). `schemas._validate_price` (`mode="before"`) accepts a number or numeric string > 0, ≤ 100 000 with at most 2 decimals and quantizes to cents; the comma is normalized only by the client.
- **Method derivation**: the server derives the method from the effective link (`application/term_payments.derive_payment_method`: a link → `EXTERNAL_LINK`, none → NULL); the client never sends it. `PLATFORM` is reserved and nothing writes it.
- **Validation and copy table**: `schemas._normalize_payment_url` strips, turns blank into NULL, allows at most 500 characters and requires `https` with a host, no userinfo (`https://bank.pl@evil.tld` hides the real host) and no whitespace or control characters, and returns the trimmed input as typed (no trailing slash), the same value the client's `parsePaymentUrl` returns, so an untouched edit form sends no patch. The link is not free text (no `check_text`). `term_payments.ensure_payment_url_has_price` checks the effective (merged) state on circle create/update and term create/update (400 „Link wymaga ceny — wpisz cenę albo usuń link.”), backed by the CHECKs. One Polish copy table serves both stacks: „Podaj kwotę od 0,01 do 100 000 zł albo zostaw puste.”, „Link musi zaczynać się od https://”, „Link do płatności może mieć najwyżej 500 znaków.” and the link-needs-price text (`PRICE_MESSAGE` etc. in `groups/schemas.py`, the `*_ERROR` constants with `parsePrice`/`parsePaymentUrl`/`parsePayment`/`formatPrice` in `utils/appHelpers.ts`).
- **Circle defaults**: set on `POST /api/groups/mine/new` and `PATCH /api/groups/{id}` via `model_fields_set` (omitted keeps, `null` or a blank link clears).
- **Term create inherits by value** (`application/terms.create_term`): an omitted `price` copies `group.default_price`; an omitted `payment_url` copies `group.default_payment_url`, **except** when `price: null` was sent explicitly — an explicit free term does not inherit the link. Later changes of the defaults never propagate. On term update both fields are independent (`null` clears, omitted keeps), so clearing the price of a term that keeps its link is a 400 unless `payment_url: null` is sent too.
- **Privacy of the status**: price, link and method are public on the term (`PublicTermResponse` on the public circle read, the term card's price badge; not in search). `payment_status` is never public: only the viewer's own status on `GET /api/public/groups/{id}/access` (`access.payment_status`, `None` without an active attendance; the route is already `private, no-store`), the viewer's own rows on `GET /api/groups/mine/attendances`, and the organizer-only attendee list.
- **Payment PUT** (`PUT /api/groups/{g}/terms/{t}/attendees/{party}/payment` `{paid}` → 204, `router/circles.py`, matrix **row 71** EDIT / `mcp:edit`, declared ahead of rows 26/27 like row 70): `attendance_points.set_payment_status` (next to `set_presence`; `term_payments` keeps only the shared price/link rules) checks the active organizer (403), the term's group (404), then locks the row matched by `listed_attendance_condition` `FOR UPDATE` (404 for a row the list does not show); it works in every attendance state (NOT_STARTED, OPEN, CLOSED), is idempotent and runs inside `mapped_transaction_conflicts`. PAID sets `paid_marked_at`, UNPAID clears it. An actual change logs one INFO line `Term payment status set term_id=… party_id=… status=… organizer_party_id=…` (ids only, no URL). The attendee list and `GET /mine/attendances` send `private, no-store` + `Vary: Authorization, Cookie` via `set_personalised_cache_headers`.
- **Listed-row predicate** (`infrastructure/repository.py`): `listed_attendance_condition(term_id, closed_at)` = counted rows OR `payment_status = 'PAID'`, shared by `list_listed_attendances` (the organizer list, counted first, then by RSVP time) and the payment PUT, so the toggle accepts exactly the rows the organizer sees. `withdrawn` and `counted` (`is_counted`) on `TermAttendeeResponse` let the UI show a withdrawn PAID row as „wypisany — do zwrotu” with a refund note while the counts stay equal to `attendee_count` and the close result.
- **Withdrawal and re-RSVP**: withdrawn rows no longer count for `is_attending` nor appear in the public guardian list (active rows only). A re-RSVP reactivates the row (clears `withdrawn_at`), clears presence only while the attendance list is open and keeps the payment status.
- **Frontend**: `PriceField`/`PaymentUrlField` (`components/shared/appComponents.tsx`) in the circle settings and the term forms (create forms prefilled from the Circle defaults; „Edytuj termin” patches only changed fields), the price badge on `TermCard`, the payment variant of `SignUpFooter` on the public term page (link out, own status), and the `role="switch"` „opłacone” toggle in `TermAttendeesPage` (shown when the term has a price or the row is PAID; optimistic pending state) through `useTermAttendance.setPaymentStatus`, which awaits the prefix invalidation.
- **Accepted risks**: an attendee who withdrew before the close and re-RSVPs after it is reactivated with presence unchanged and shows on the closed list, although the close did not count them. `term_attendances` has no unique `(term_id, party_id)` constraint, so a duplicate row would make the payment PUT's `scalar_one_or_none` raise (500), as `create_rsvp` already would. Rolling back with `downgrade 0105` loses every price, link and payment mark (no guard; no ledger rows depend on these columns).

## Deployment Architecture
- `docker-compose.yml` (repo root) brings up the stack via `docker-compose up`: Postgres 18 (`pgvector/pgvector:0.8.7-pg18-trixie`), the FastAPI backend (port 8080, build context `src/backend/`), the wants `matcher` (no port, build context `src/matcher/`), `web` (the Next.js server, build context repo root, `BACKEND_INTERNAL_URL=http://backend:8080`) and `frontend` (the stock `nginx:1.27-alpine` image with `src/frontend/nginx.conf` mounted read-only, published on **:5174**) — the full plugin-architecture stack (host app + backend + DB) in one command. `.env.example` lives at the repo root alongside it (moved from `src/backend/.env.example`) since that's where docker-compose looks for a `.env` file by default
- **Matcher service**: `matcher` (build context `src/matcher/`, `python:3.12-slim` + uv, `CMD python -m matcher`, built without any secret) gets only `DATABASE_URL`, the same literal as `backend` (`postgresql+asyncpg://aj:aj@postgres:5432/aj`; the driver suffix is stripped, the URL is never logged). No ports. `depends_on` postgres `service_healthy` and backend `service_started`; it does not wait for the migrations through compose but at its own startup gate (see **Wants**). `restart: unless-stopped`; no healthcheck and no `init` (python is PID 1 with its own SIGTERM handler and no children). At most 5 connections per copy (pool 1–4 + 1 LISTEN)
- **Topology**: browser → nginx (`frontend`) → `web` (Next) or `backend`. nginx routes `/api/` → backend, `~ ^/oauth2/(token|register|introspect)$` and `/.well-known/` → backend, and everything else (`/`) → `web:3000`, including `/oauth2/authorize` (the GET is the Next consent page; `src/proxy.ts` rewrites the form POST to the backend, which then sees `Host: backend:8080` while the `X-Forwarded-*` headers carry the public values). Every location forwards `Host`, `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`. There is no SPA fallback: the backend serves no pages and returns a JSON 404 for an unmatched GET
- **Web service**: `src/frontend/Dockerfile` builds in three stages (`npm ci`; `npm run build` with the build args `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` (empty = manual place picker) and `BACKEND_INTERNAL_URL` (default `http://backend:8080`, because the `next.config.ts` rewrites are fixed at build time), which also builds the plugin SDK; a node:22-alpine runner with `.next/standalone`, `.next/static` and `public`, `PORT=3000`, `HOSTNAME=0.0.0.0`, `TZ=Europe/Warsaw`, running as `USER node` with `node server.js`). Compose passes `BACKEND_INTERNAL_URL=http://backend:8080` at runtime as well, for `src/proxy.ts` and `src/api/server.ts`. The build context is the **repo root** — not `src/frontend/` — because `src/frontend`'s test suite imports the sibling `plugins/server-sdk.ts` by relative path, so that file must be present in the build context too (see `.dockerignore` at the repo root, which scopes that context down to just `src/frontend/` + `plugins/server-sdk.ts`). `next.config.ts` sets `outputFileTracingRoot`/`turbopack.root` to `src/frontend`, since the repo root has its own `package-lock.json`
- **Dev and ports**: `npm run dev` in `src/frontend` is `next dev -p 5173` (Turbopack). `next.config.ts` rewrites `/api/:path*`, `/oauth2/register`, `/oauth2/token`, `/oauth2/introspect` and `/.well-known/:path*` to `BACKEND_INTERNAL_URL` (server-only, default `http://localhost:8080`), in dev and whenever nginx is not in front; `src/proxy.ts` rewrites the `POST /oauth2/authorize` form. So the dev host is :5173, the compose stack is :5174 (nginx) and the backend is :8080. The backend's CORS default stays `http://localhost:5173`, and plugins load the SDK from `http://localhost:5173/assets/…`, so plugin development runs the host with `npm run dev`
- Individual plugin apps (`plugins/warehouse`, `plugins/box-size`, `plugins/ai-description`) are **not** part of `docker-compose.yml` — they remain standalone dev-server processes per `plugins/CLAUDE.md`'s documented workflow, registered with the host via `PUT /api/plugins/{pluginId}/manifest`
- `backend` builds the `runtime` target with the `hf_token` build secret (`HF_TOKEN` must be set for `docker compose build backend`; check its presence only, never print it) and `MODERATION_TEXT_ENABLED` fixed to `"true"`. The throwaway `models` stage also exports the embed model to `/models/embed`: `snapshot_download` of `sdadas/mmlw-roberta-base` at the pinned `EMBED_REVISION` (public, no secret), the optimum `feature-extraction` ONNX export, `onnxruntime.quantization.quantize_dynamic` QInt8 on MatMul weights only, then `scripts/check_embed_parity.py`, which fails the build when the minimum cosine against fp32 is below 0.99 (0.9904 measured on 2026-11-18; plain QInt8 gave 0.9895, `per_channel` 0.63). `model.onnx` is about 241 MB. Any change to the model, revision or onnxruntime re-runs that gate. There is no photo worker service: photo moderation runs only in VPS B's `moderation-cron`, so a local stack with `MODERATION_IMAGE_ENABLED=true` keeps photos PENDING unless that cron is running
- nginx allows request bodies up to 16 MB on `/api/` (photo uploads; the backend caps a photo at 15 MB)
- No CI/CD yet

### Cutover / rollback for the category-tree release (migrations 0064–0069)
The backend runs `alembic upgrade head` on every start (`docker-compose.yml` `backend` command), so deploying the image applies 0064–0069 at once. 0067 and 0069 delete data irreversibly: every needed item and pledge (0067), and every legacy product, inventory item, reservation, swap proposal, item conversation and ledger row (0069). 0068 drops `needed_items.product_id`, so the old and new backend cannot run side by side.

1. Take a `pg_dump -Fc` of the database and verify it (`pg_restore --list` succeeds, dump is non-empty). Keep it off the database host.
2. Confirm the target environment's Spaces bucket and prefix belong to that environment (check that the variables are set and compare the bucket/prefix names only; never print the keys). 0069 queues deletes of every wiped product photo, so a wrong bucket deletes another environment's files.
3. If product photos must survive a rollback, copy the bucket's product photo prefix now (see **Rollback**).
4. Stop the VPS B moderation cron (`MODERATION_CRON_ENABLED=false` or stop the `moderation-cron` service).
6. Deploy frontend and backend together; expect a short downtime while the backend migrates.
6. Verify: 9 root categories and 2286 categories in total (`SELECT count(*) FROM categories [WHERE parent_id IS NULL]`), `alembic_version` = `0069`, and `GET /api/categories` returns the tree.
7. Verify the photo deletes: `SELECT status, count(*) FROM outbox_entries WHERE event_type = 'storage.objects_delete' GROUP BY status` reaches only `PROCESSED`. `FAILED` entries are expected only where Spaces is not configured (e.g. a local stack); anywhere else, find the cause in the backend log.
8. Start the moderation cron again.
9. Smoke test: register an item with a mode; an 11th GIFT listing → 409; registering on a non-leaf category → 409; add a needed item by name.

**If 0069 fails**: each migration commits on its own, so 0064–0068 stay applied, `alembic_version` stays at `0068` and the backend crash-loops on start. Check `SELECT version_num FROM alembic_version`, read the error in the backend log, fix the cause (e.g. a missing category fixture in the image) and restart the backend, which re-runs 0069. If the cause cannot be fixed quickly, restore the dump as below.

**Rollback**: `pg_restore` the dump into an empty database, then deploy the previous image. The previous image cannot start on a database at 0069, and the downgrades of 0067–0069 do not bring data back (0069's refuses while any product exists), so restoring the dump is the only rollback. After 0069 the outbox deletes the wiped photos' files from Spaces (`storage.objects_delete`), so the restored photo rows point at files that are gone unless the product photo prefix was copied before the deploy (step 3); copy it back before starting the previous image.

### Deploy / rollback for the event page release (migrations 0071–0072)
`alembic upgrade head` on start applies both at once. 0071 adds `conversations.event_id` (FK `fk_conversations_event_id_events` ON DELETE CASCADE), the partial unique index `uq_conversations_event_id` (`WHERE kind = 'EVENT'`) and `ix_conversations_event_id`. It also drops and recreates `fk_messages_conversation_id_conversations` and `fk_conversation_reads_conversation_id_conversations` **with ON DELETE CASCADE for every conversation kind**, not only EVENT: deleting any conversation row now silently removes its messages and read markers, where before the FK refused to delete a conversation that had messages. 0072 adds the indexes on `events.author_party_id` and `event_attendances.party_id`. Recreating the FKs takes ACCESS EXCLUSIVE locks on `conversations`, `messages` and `conversation_reads` and validates every existing row; 0071 sets `lock_timeout = '5s'`, so a long-running query on those tables makes the migration fail instead of queueing all chat traffic behind it.

1. Deploy off-peak. Check the table sizes first (`SELECT count(*) FROM messages`, `SELECT count(*) FROM conversation_reads`); at a size where FK validation takes long, split it into `NOT VALID` + `VALIDATE CONSTRAINT` before deploying.
2. Run `SELECT id FROM organizations WHERE slug = 'event'`. `"event"` is now a reserved slug and `/event/...` paths under it become event URLs; if a row comes back, rename that organization's slug before the deploy.
3. Take a `pg_dump -Fc` of at least `conversations`, `messages` and `conversation_reads` (needed for any downgrade, see **Rollback**).
4. Deploy frontend and backend together (the old `/events/:eventId` page links stop working; there is no redirect).
5. Verify: `alembic_version` = `0072`; `\d messages` shows the conversation FK with `ON DELETE CASCADE`; open an event page, sign up while logged in, and open the event chat as the author and as a logged-in attendee.

**If 0071 fails** (typically `lock_timeout` while a query held the tables): each migration runs in its own transaction (`transaction_per_migration=True`), so nothing of 0071 is applied, `alembic_version` stays at `0070` and the backend crash-loops on start. Find and end the blocking query (`pg_stat_activity`) or wait for a quieter moment, then restart the backend, which re-runs 0071.

**Rollback**: prefer an image-only rollback without a downgrade. The previous image ignores `conversations.event_id`, the extra indexes and the cascades, but its `ConversationKind` has no EVENT: its inbox queries filter by ITEM/GROUP/TERM columns and do not list EVENT chats, and loading an EVENT row by id (`/api/conversations/{id}`) fails with a server error. The chats are intact and return when the new image is redeployed. `alembic downgrade 0070` **deletes every EVENT conversation together with its messages and read markers** and restores the non-cascading FKs; dump the messaging tables (step 3) before running it. Downgrading 0072 only drops its two indexes.

### Deploy / rollback for event reservations (migration 0073)
0073 is additive for existing data: `reservations.term_id` becomes nullable, `event_id` is added (FK `fk_reservations_event_id_events` **ON DELETE SET NULL**, partial index `ix_reservations_event_id`) and CHECK `ck_reservations_context` is validated against every existing row (all have a `term_id`, so it passes). `ON DELETE SET NULL` means deleting an event never deletes reservations: `delete_event` first cancels the open ones (see **Event reservations**), then the FK detaches the now-terminal rows, which stay with `term_id` and `event_id` both NULL because `inventory_entries.reservation_id` (the ledger) still references them.

1. Take a `pg_dump -Fc` of the database before deploying (the only lossless way back once event reservations exist).
2. Deploy frontend and backend together; the old frontend cannot render event contexts, and the old backend's `Reservation.term_id` is NOT NULL.
3. Verify: `alembic_version` = `0073`; `\d reservations` shows `event_id`, the SET NULL FK and `ck_reservations_context`; take an item on an event page and confirm it after `starts_at`.

**Rollback**: an image-only rollback (no downgrade) is safe only while no row has `term_id IS NULL`, because the previous image assumes every reservation has a term. `alembic downgrade 0072` is **guarded**: it counts `reservations WHERE term_id IS NULL` (event reservations and rows detached from a deleted event) and, if any exist, raises naming the recovery path instead of dropping data. Recovery: either cancel and purge those event reservations **and the `inventory_entries` rows referencing them** manually (keeping item balances consistent), then re-run the downgrade; or restore the pre-0073 dump from step 1. With no such rows the downgrade drops the CHECK, the index, the FK and the column, then restores `term_id NOT NULL`.

### Deploy / rollback for product page reservations (migrations 0074–0077)
`alembic upgrade head` on start applies all four. Each is small and additive for existing data:
- **0074** (`0074_personal_pickup_reservations.py`) only recreates `ck_reservations_context` as `num_nonnulls(term_id, event_id) <= 1` (under `SET LOCAL lock_timeout = '5s'`, like 0073); no column.
- **0075** (`0075_inventory_location.py`) adds nullable `inventories.location_id`, FK `fk_inventories_location_id_locations` and partial index `ix_inventories_location_id` (`WHERE location_id IS NOT NULL`).
- **0076** (`0076_item_listing_visibility.py`) adds `item_listing_preferences.visibility VARCHAR(10) NOT NULL DEFAULT 'PUBLIC'` (permanent server default, as `0036`), so every existing listing stays public.
- **0077** (`0077_swap_proposals_listing_item_index.py`) builds the partial index `ix_swap_proposals_listing_item_id_proposed` on `swap_proposals(listing_item_id) WHERE status = 'PROPOSED'` CONCURRENTLY (as `0053`), for the pending-proposal lookup of every listing read and take/propose.
0074–0076 run under `SET LOCAL lock_timeout = '5s'`.

1. Take a `pg_dump -Fc` of the database before deploying (the lossless way back once personal pickups, pickup places or PRIVATE listings exist).
2. Deploy frontend and backend together: the old frontend calls the removed take/propose routes and the old `/actions` shape.
3. Verify: `alembic_version` = `0077`; set a pickup place on Moje rzeczy, take an item with "Odbiorę osobiście" and confirm it at once; switch an item to PRIVATE and check it disappears from the public organizer page.

**Rollback**: downgrades run 0077 → 0076 → 0075 → 0074, each in its own transaction, so a refusal leaves the schema at the refusing revision with the later ones already undone.
- **Before any downgrade (or image-only rollback), run both guard counts** and resolve them first: `SELECT count(*) FROM reservations WHERE status IN ('PENDING', 'CONFIRMED') AND term_id IS NULL AND event_id IS NULL` (0074/0075) and `SELECT count(*) FROM item_listing_preferences WHERE visibility = 'PRIVATE'` (0076). Proceed only when both are 0.
- **0077** only drops the index (CONCURRENTLY); no data is lost.
- **0076 is guarded**: it counts `item_listing_preferences WHERE visibility = 'PRIVATE'` and refuses, because dropping the column would silently publish those items. Recovery: (a) the owners clear those listings (`PUT /api/item-listing-preferences/{item_id}` with `{"mode": null}`) or switch them back to PUBLIC, then re-run; or (b) restore the pre-0076 dump.
- **0075 is guarded and lossy**: it first runs 0074's count and refuses with the same recovery steps, so a downgrade below 0074 can no longer drop the pickup places and then stop at 0074. Past the guard it drops the index, the FK and the column, so **every owner's pickup place is lost** (owners must set it again after re-upgrading; personal pickups are unavailable meanwhile).
- **0074 is guarded**: it counts open (PENDING/CONFIRMED) reservations with neither `term_id` nor `event_id` and refuses, since 0073's CHECK would reject them. Recovery is split: (a) the listing owner **rejects** pending personal swap proposals with `POST /api/swap-proposals/{id}/reject` (`cancel-transaction` refuses an unpaired proposer leg); (b) either party **cancels** accepted personal swaps and personal gifts with `POST /api/reservations/{id}/cancel-transaction`; (c) otherwise restore a pre-0074 dump. After a downgrade, **terminal** personal reservations stay with both columns NULL and read as reservations of a deleted event.
- An image-only rollback (no downgrade) has the same hazards without the guards: the previous image ignores `visibility` (PRIVATE items become public) and resolves an open no-context reservation as having no context, so its parties cannot confirm or cancel it. Use it only while neither kind of row exists.

### Item ownership and movement rules (migration 0102)
`inventory_items.owner_inventory_id` (NOT NULL, FK, `ix_inventory_items_owner_inventory_id`) is whose the item is and `inventory_id` where it is now; they differ only while the item is away from its owner (a LEND until its RETURN). Ownership and permission reads (`resolve_owning_inventory`, the messaging ACL, the product owner check, item details) read `owner_inventory_id`; the old `home_inventory_id` and its `coalesce` are gone. What each `MovementType` may do is declared once in `ledger.py::MOVEMENT_RULES` (leg count, source/target side, whether it hands ownership over, whether the item must be at its owner, whether it clears the pickup place; `test_movementRules_everyMovementType_hasRule` pins that every type has a rule), and the ledger contract is in that module's docstring: only `post_movement` writes the ledger and the projection, other modules never read `accounts`/`inventory_entries` directly. A new movement type is a `MovementType` value plus its rule. VIRTUAL inventories (the old loan model), `inventory_balances.lent_at`/`returned_at` and the RETURNED status are removed; `LEND`/`RETURN` and the LENT status stay for a future loan flow. API: item responses carry `owner_inventory_id` instead of `home_inventory_id`, balances drop `lent_at`/`returned_at`.

Deploy: `alembic upgrade head` **refuses** while a VIRTUAL inventory holds an item or has ledger entries (return those items first); otherwise it backfills `owner_inventory_id = coalesce(home_inventory_id, inventory_id)`, deletes the empty VIRTUAL inventories and their accounts, turns RETURNED balances AVAILABLE, drops the two loan timestamps and recreates the PERSONAL-only unique index `uq_inventories_owner_user_id_personal`, under `lock_timeout` 5s (it rewrites `inventory_items`, so off-peak). No image-only rollback: `alembic downgrade 0101` with the previous image restores `home_inventory_id` (set where owner ≠ holder), the two empty timestamp columns and the old index; deleted VIRTUAL inventories are not restored. The matcher's test seed writes `owner_inventory_id` too.

A failed or interrupted CONCURRENTLY build leaves an INVALID index behind; each revision runs `DROP INDEX CONCURRENTLY IF EXISTS` first, so rerunning `alembic upgrade head` drops the leftover and builds it again.

1. **Pre-deploy legacy-data query** (read-only). The membership primitive assumes every Membership points at a MEMBER role, every Leadership at an ORGANIZATOR role, and that no `group_roles` row has ended. Each count must be **0**; otherwise **stop the deploy** and review the rows:
   ```sql
   SELECT
     (SELECT count(*) FROM memberships m JOIN group_roles r ON r.id = m.from_role_id
       WHERE r.role_type <> 'MEMBER')                   AS memberships_not_member,
     (SELECT count(*) FROM leaderships l JOIN group_roles r ON r.id = l.from_role_id
       WHERE r.role_type <> 'ORGANIZATOR')              AS leaderships_not_organizator,
     (SELECT count(*) FROM group_roles WHERE valid_to IS NOT NULL) AS group_roles_ended;
   ```

2. **pg_trgm privilege check**, as the migration role: `SELECT has_database_privilege(current_user, current_database(), 'CREATE')` must be `t`, or the role is a superuser (`SELECT rolsuper FROM pg_roles WHERE rolname = current_user`). pg_trgm is a trusted extension on PostgreSQL 13+, so CREATE on the database is enough. If neither holds, a DBA runs `CREATE EXTENSION pg_trgm` beforehand (0086 then does nothing).

   ```sql
   SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) AS total_size
   FROM pg_class WHERE relname IN ('products', 'events', 'terms');
   ```
   To keep the old backend serving during the migrations instead, build the new image first (`docker compose build backend`, which leaves the running container on the old image), run the migrations as a one-off with it before swapping it in: `docker compose run --rm backend alembic upgrade head` (the old image ignores the new columns and indexes, see Rollback), then restart the backend on the new image, whose own `alembic upgrade head` is then a no-op. The old backend still waits on each 0088–0090 rewrite: its requests touching `products`, `events` or `terms` block (or time out) until that table's rewrite commits, so run this off-peak as well.
4. Take a `pg_dump -Fc` of the database (group descriptions are the only non-derived data the downgrade drops).
5. **Deploy off-peak**: 0088–0090 rewrite `products`, `events` and `terms`. If one fails on `lock_timeout`, nothing of it is applied, `alembic_version` stays at the previous revision and the backend crash-loops on start; end the blocking query (`pg_stat_activity`) or wait, then restart the backend.

**Rollback**: no guarded downgrades. Every downgrade is the exact reverse and loses only derived data (`search_vector`, `path_text`, the indexes, `fold_pl`) plus **every group description** (0085). An image-only rollback works: the previous image ignores the new columns and indexes (but its `GET /api/categories` is no longer public and its search is the mock).

     ```sql
      WHERE status = 'ACTIVE' AND expires_at > (now() AT TIME ZONE 'UTC');
     ```
     (`wants` timestamps are naive UTC.) The update leaves `updated_at` alone, so no seeker edit gets a 409; the trigger NOTIFYs `wants_changed` and the matcher drains the flags as SIMILAR-only claims. Watch the count above fall to 0 again.
7. **Shadow metrics for 2–4 weeks**:
   - SIMILAR rows per want and the score histogram (`SELECT width_bucket(score, 0.86, 1, 14), count(*) FROM want_matches WHERE tier = 'SIMILAR' GROUP BY 1`);
   - a 100-pair spot check ≥ 0.80;
   - window `duration_ms` and the share of `capped=True`;
   - the forward p95;
   - embed timeouts (WARNING lines) and the API RSS;
   - FAILED `embeddings.requested` entries;
   - the stale/missing vector counts of step 5;
   - bells and MATCH counts unchanged against the pre-deploy baseline.
   - **7b. Release gate** (see above): the held-out sweep sets `SEMANTIC_SIMILARITY_MIN`, or the tier is dropped (roll back the matcher and backend per the rollback list; step 8 never runs).
   - **7c. Threshold change** (when the gate's value differs from the provisional 0.86). `/api/wants/{id}/similar` and `SEMANTIC_CAP` do not filter stored rows by score, so rows stored under the old minimum would show from step 8 on and hold cap slots, and a lower minimum would never reach wants already scanned:
     1. Set the new value in `matcher/rules.py` (and the drift test), tag the running matcher image under a new name (`docker tag <project>-matcher:latest <project>-matcher:pre-threshold`; keep `pre-semantic` as the pre-SIMILAR target of rollback 3), then `docker compose build matcher` and `docker compose up -d --remove-orphans matcher`. Verify „database contract ready” and the `window run:` line.
     2. Delete the stored rows below the new minimum: `DELETE FROM want_matches WHERE tier = 'SIMILAR' AND score < <new_min>;`
     3. Re-flag every ACTIVE want once with the `UPDATE` of step 6 and watch `SELECT count(*) FROM wants WHERE similar_requested_at IS NOT NULL` fall to 0. The forward SIMILAR runs refill the freed cap slots and, after a lowered minimum, add the pairs in between.
     The same three steps apply to any later threshold change.
8. **Web deploy** with „Powiązane rzeczy” (`docker compose build web` then `docker compose up -d --remove-orphans web`); this ends the web freeze. Track the open rate per score band (`want_matches.opened_at` of SIMILAR rows).

**Rollback, least to most invasive**:
1. Roll the web image back. This hides the section.
2. Set `EMBEDDINGS_ENABLED=false` and recreate the backend (`docker compose up -d backend`). This freezes the vectors: no embedding, no retries, no reconcile; the stored SIMILAR rows stay readable.
3. Roll the matcher image back to the pre-SIMILAR build (the `pre-semantic` tag of step 6). It passes the ≥ 99 gate and stops creating SIMILAR pairs. It also lacks the upgrade in place: while it runs, a stored SIMILAR row is not upgraded to MATCH or SUGGESTION by a later lexical hit, so that pair gets no lexical tier and no bell. When the new matcher is deployed again, re-flag every ACTIVE want once with the `UPDATE` of step 6: wants created or renamed while the old matcher ran had their requests cleared without a SIMILAR run.
4. Full revert: `docker compose stop matcher backend` (a still-running new backend would hit the dropped tables: rename deletes, the reconcile tick). Then, from the **new** backend image, `docker compose run --rm --no-deps backend alembic downgrade 0100` (the head is 0101; a later revision chains after it and must be downgraded first, under its own runbook). It deletes the SIMILAR rows, all vectors and the `similar_requested_at` column and trigger, and restores the 0099 view and CHECKs. Then `docker compose run --rm --no-deps backend alembic downgrade 0099`, which drops the extension (superuser; check ownership first: `SELECT e.extname, r.rolname FROM pg_extension e JOIN pg_roles r ON r.oid = e.extowner WHERE e.extname = 'vector'`, and stop at 0100 when a DBA installed it before this release). Only then deploy the old backend and matcher images from their `pre-semantic` tags (never `up -d` while the compose tag still names the new backend image: its `alembic upgrade head` would re-apply 0100–0101). The postgres image may go back to `postgres:18` only after the extension is dropped.

There is **no image-only rollback** for the backend once the database is at 0100 or later. Both downgrades are plain and unguarded; they lose only derived data (vectors, SIMILAR pairs, pending SIMILAR-only requests), which the reconcile re-creates after a later upgrade.

**Future changes**:
- A model, prefix, pooling or revision change is a new `EMBEDDING_MODEL_ID` in all three places (`app/embeddings/service.py`, the Dockerfile ARGs, `matcher/rules.py`; the drift tests fail until they agree), a re-run parity gate and a re-scored threshold. Deploy the backend first and let the reconcile re-embed (rows carry their `model_id`, and the matcher compares only vectors of its own id), then deploy the matcher with the new id and threshold. After the new-id matcher is up and the re-embed has drained (the two counts of step 5 at 0), re-flag every ACTIVE want once with the `UPDATE` of step 6: the old-id matcher cleared the re-embed's SIMILAR-only flags and moved its marker past the re-embedded listings without comparing the new vectors. Old-model SIMILAR rows carry no model id; they stay and keep counting toward `SEMANTIC_CAP` until the want is edited.
- A `SEMANTIC_SIMILARITY_MIN` change follows step 7c (matcher deploy, delete the SIMILAR rows below the new minimum, re-flag), because stored rows are not filtered by score on read or in the cap.
- An onnxruntime upgrade, or any other version bump in the `models` stage pins, re-runs the parity gate in the build; the margin is thin (0.9904 against 0.99). A changed `model.sha256` under the same `EMBEDDING_MODEL_ID` means re-running the release-gate sweep. The `models` stage quantizes with onnxruntime 1.32.0 while the runtime `ml` group infers with 1.30.0 (`uv.lock`).
- A dimension change is a new revision (`halfvec(N)`), with the view recreated.
- A vector index needs iterative scan and short-result tests (ADR-008). Revisit at about 500,000 listings or a forward SIMILAR above 200 ms (about 37 ms p95 at 20,000 listings, measured 2026-11-18 on PostgreSQL 18 + pgvector 0.8.7).
- The side tables deviate from the `BaseEntity`/UUID-PK rules of `standards/backend/models.md` and `migrations.md`: one-to-one derived rows keyed by the owner id, unmapped, written in `sa.text`, like `want_scan_markers`. A new side table follows the same shape.

### Deploy / rollback for points and reputation (migrations 0103–0105)

Three revisions, per `migrations.md`: **0103** `0103_points_tables` creates `point_accounts`, `point_transactions`, `point_entries` and `points_config` with every named constraint and index and touches no existing table; **0104** `0104_points_columns` starts with `SET LOCAL lock_timeout = '5s'` and adds `categories.size_class`, `inventory_items.points_value`, the five `terms` attendance columns with their CHECKs and the partial index `ix_terms_occurs_on_attendance_open` (not built concurrently, `terms` is small; `attendance_points NOT NULL DEFAULT 0` needs no table rewrite) and `term_attendances.present_marked_at`; **0105** `0105_points_seed` (data only) inserts the EMISSION account and the default config row, sets `size_class = 'MEDIUM'` on root categories, backfills `points_value` for every item in one `UPDATE … FROM` (a top-down recursive CTE with the default bases and multipliers and the code's snap rule) and closes every term that has already started and is still open (`attendance_closed_at` = now UTC, min present 3, present count 0, not rewarded), so there are no retroactive points and no auto-close backlog.

1. **Before deploy**: take a `pg_dump`; it is the only lossless rollback once any award exists. Run the matcher suite (`uv run python -m pytest` from `src/matcher`): 0104 alters `categories` and `inventory_items`, which its fixtures seed.
2. **Deploy**: build the images and `docker compose up -d`; the backend runs `alembic upgrade head` on start (0103 → 0104 → 0105). 0104 takes short locks on `categories`, `inventory_items`, `terms` and `term_attendances` under the 5 s `lock_timeout`; retry if it times out. Verify: `SELECT count(*) FROM point_accounts WHERE account_type = 'EMISSION'` is 1, `SELECT count(*) FROM points_config` is 1, and after 15 minutes the backend log has an `attendance close: closed=… awarded=…` line.
3. **There is no image-only rollback.** Compose runs `alembic upgrade head` on every start, so an old image fails on the unknown revision 0105.
4. **Guard count first**: `SELECT count(*) FROM point_transactions`. The 0105 downgrade refuses while it is above 0, with an error naming the recovery path. Once any award exists, the only lossless path is restoring the dump; purging `point_entries` and `point_transactions` and rerunning the downgrade loses every balance and reputation.
5. **Rollback by downgrade** (guard count 0): stop the backend and the matcher, run `docker compose run --rm --no-deps backend alembic downgrade 0102` **from the new image**, then deploy the old images. Never `docker compose up` while the compose tag still names the new backend image: its start would upgrade to head again. Order 0105 → 0104 → 0103, only 0105 guarded. Losses: 0105 deletes the config and EMISSION rows and NULLs **every** `size_class` (also values the admin set after deploy), every `points_value` and the four close columns of every closed term (including closes made after deploy that posted nothing); 0104 drops those columns with the term levels and presence marks; 0103 drops the (by then empty) point tables and `points_config`.
6. **Rollback by restore**: stop the stack, restore the pre-deploy dump, deploy the old images.

### Deploy / rollback for paid terms (migration 0106)

One revision, per `migrations.md`: **0106** `0106_paid_terms` starts with `SET LOCAL lock_timeout = '5s'` and only adds columns and the nine CHECKs (see Paid terms): three nullable columns each on `groups` and `terms`, and `term_attendances.payment_status` NOT NULL DEFAULT 'UNPAID' (a constant default, no table rewrite) plus the nullable `paid_marked_at`. Schema only, no backfill, no new table or index; existing terms stay free and every existing attendance reads UNPAID.

1. **Before deploy**: take a `pg_dump`; it is the only way back to the prices, links and payment marks after a rollback.
2. **Deploy**: build the images and `docker compose up -d`; the backend runs `alembic upgrade head` on start (0105 → 0106). It takes short ACCESS EXCLUSIVE locks on `groups`, `terms` and `term_attendances` under the 5 s `lock_timeout`; retry if it times out. Deploy the web image together with the backend, never ahead of it: the new pages read `price`/`payment_status` fields an old backend does not return. Verify: `SELECT count(*) FROM term_attendances WHERE payment_status <> 'UNPAID'` is 0 right after the deploy, and the `ck_%payment%`/`ck_%price%` constraints exist on the three tables. Then confirm the migration actually ran: `docker compose ps backend` shows the container running (it has no restart policy, so an `alembic upgrade head` that hits the `lock_timeout` leaves it exited and the API down) and `docker compose exec -T backend alembic current` prints `0106 (head)`. If the backend exited or `alembic current` is still 0105, check `docker compose logs backend` for the lock timeout and retry `docker compose up -d backend` off-peak, when no long transaction holds `groups`, `terms` or `term_attendances`.
3. **There is no image-only rollback past 0106.** Compose runs `alembic upgrade head` on every start, so an old image fails on the unknown revision 0106.
4. **Rollback by downgrade** (lossy, **no guard**): stop the backend and the matcher, run `docker compose run --rm --no-deps backend alembic downgrade 0105` **from the new image**, then deploy the old images. Never `docker compose up` while the compose tag still names the new backend image: its start would upgrade to head again. The downgrade drops the nine CHECKs, then the columns, losing every term price, payment link and method, the Circle defaults and every payment mark (`payment_status`, `paid_marked_at`). There is no guard, because no ledger rows depend on these columns; organizers lose only what they typed and the „opłacone” marks.
5. **Rollback by restore**: when the prices and payment marks must survive, stop the stack, restore the pre-deploy dump (it predates any price set after deploy), deploy the old images.
