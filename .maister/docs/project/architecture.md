# System Architecture

## Overview

**aj** is a plugin-based microkernel platform. The backend (`src/backend/`) was migrated from a Java/Spring Boot scaffold to Python/FastAPI + SQLAlchemy + Alembic (see `.maister/tasks/migrations/2026-08-31-java-to-python-fastapi/` for the full migration record). The frontend (`src/frontend/`) runs on Next.js 16.4 App Router (migrated from a Vite + React Router SPA, see `.maister/tasks/migrations/2026-11-02-frontend-vite-to-nextjs/`; see **Frontend Application** below). The system is no longer pre-alpha scaffolding — it has real business logic across four verticals (category, product, plugin, footprint) plus a full hand-rolled OAuth2 authorization server, is runnable end-to-end via `docker-compose up`, and passed a 53/53-check integration verification pass with the fully wired application (no regressions across any prior module's acceptance criteria).

## Architecture Pattern

**Pattern**: Microkernel (Plugin-Based) — plugins are frontend iframes (`plugins/`) that talk to the host API via a browser SDK (`postMessage`/`hostApp.getToken()`) and a server-side SDK (`createServerSDK`), not a server-side plugin-loading framework. See `standards/backend/plugin-auth.md`.

**Current state**: A single FastAPI application (`app/main.py`) exposing category, product, plugin, footprint, auth, and OAuth2 routers behind one centralized authorization dependency layer. No server-side plugin-loading mechanism exists yet — that remains a future decision (see `project/tech-stack.md`'s "Architectural Decisions Pending").

## System Structure

### Application Core
- **Location**: `src/backend/app/`
- **Purpose**: FastAPI application bootstrap, cross-cutting infrastructure, and per-vertical routers
- **Key Files**: `app/main.py` (entry point — instantiates `FastAPI()`, wires CORS, registers every exception handler, includes every router with `system_router` registered last so its catch-all, which answers every unmatched GET with a JSON 404 in the `ErrorResponse` envelope, doesn't shadow more specific routes)

### Configuration
- **Location**: `src/backend/app/config.py`
- **Purpose**: Environment-variable-backed settings (`pydantic_settings.BaseSettings`). `JWT_SECRET` and `DATABASE_URL` are required with no default (fail-loud `ValidationError` on startup if missing); the remaining vars (`JWT_EXPIRATION_MS`, `CORS_ALLOWED_ORIGINS`, `FOOTPRINT_PROBLEM_BASE_URI`, `FOOTPRINT_AUDIT_RETRY_*`, `SPACES_*`, `MODERATION_*`) are operational tuning knobs with defaults matching `.env.example`/`docker-compose.yml`
- **Key Files**: `.env.example`, `docker-compose.yml`, `Dockerfile`

### Database Layer
- **Location**: `src/backend/alembic/`
- **Purpose**: Alembic database migrations
- **Technology**: PostgreSQL 18 via SQLAlchemy 2.0 (async, `asyncpg` driver)
- **Status**: One migration (`alembic/versions/0001_initial_schema.py`) reconstructs the entire schema, since no Liquibase changelog was ever populated in the Java source. Includes 6 explicitly-reconstructed FK/constraint items that existed nowhere as DDL in the original repo (see the migration's `work-log.md`, Group 2 entry, for the full checklist).

### Test Infrastructure
- **Status**: No automated pytest/TestContainers-python suite exists yet (deliberately deferred — see `project/tech-stack.md` and the migration's `spec.md` "Out of Scope"). Each vertical was verified during migration via live-uvicorn + real-Postgres manual verification scripts, not committed as a formal suite. `standards/testing/backend-testing.md` remains the target strategy for that follow-up work.

### Frontend Application
- **Location**: `src/frontend/` — Next.js 16.4 App Router (Turbopack), `output: "standalone"`; migrated from a Vite + React Router SPA (see `.maister/tasks/migrations/2026-11-02-frontend-vite-to-nextjs/`). The backend serves no HTML.
- **Route files only in `src/app/`**: the root `layout.tsx` (reads the `auth_token` cookie into `initialToken`, Google Fonts `<link>`, root default metadata), `providers.tsx` (`QueryClientProvider` with `getQueryClient()`, an Emotion `useServerInsertedHTML` registry for Chakra's SSR styles, `ChakraProvider`, `AuthProvider`, `NavigationTracker`), `not-found.tsx`, `globals.css`, and 61 `page.tsx` under the route groups `(site)` (with `(panel)`; `[slug]/layout.tsx` gives every page under the slug the Organization palette, event and term pages nest their own), `(standalone)` (only the OAuth2 consent page `oauth2/authorize`, with no app chrome) and `admin/(shell)`. Pages are thin and render a feature entry from `src/features/<domain>/`. Legacy URLs are server `redirect()`s; such a page never sits under a layout that withholds `children` during SSR (it would become a client redirect with status 200), which is why the admin pages live in `admin/(shell)/` and the slug item page in `product/[id]/(item)/`. `/:slug/group/:groupId` has no page (404).
- **Rendering**: `(panel)`, `(standalone)` and admin render only in the browser (`routing/ClientOnly.tsx` returns `null` on the server). The panel layout renders `features/panel/PanelGate.tsx` around its `children`: the session gate, then `AppPage` (AppDataProvider, `PhoneFrame`, modals, toast), kept mounted while switching sections so the panel data loads once. Every section page renders its own view; `AppPage` puts every section but the chat thread in one padded scroller (`PanelSection`, matched by path, no route group), while `/messages/:conversationId` fills the frame between the top bar and the bottom tab bar. Panel pages render no header (no title row, no back link; navigation is the top bar and the bottom tab bar); places and organization re-read panel data via `usePanelReload()`. Tests render the real section pages through `test/panelPages.ts` + `test/PanelPageOutlet.tsx` (`panelPages.test.ts` keeps the list in step with `src/app`). Registration has no onboarding wizard: the login page's `AuthGuard` sends a new account to `returnTo` or `homePath`. The `(site)` chrome, `/`, `/login`, `/product/*` and the slug pages are server-rendered.
- **Public metadata and palette**: the organization, event and term pages are server components with `generateMetadata` (`lib/publicMetadata.ts`: title, description, `og:*` and `twitter:*` tags, image) that wrap a `"use client"` feature entry in `theme/ServerThemeProvider.tsx`, so the organizer palette is in the first HTML response (`OrganizerThemeScope` prefers the page's own data). Server-side backend reads go only through `src/api/server.ts` (see `standards/frontend/data-fetching.md`); a failed read falls back to the root default metadata, and private circles get the default preview.
- **In-page login on public pages**: account-requiring actions on public pages (term/event sign-up, "Ja to przyniosę", item reserve/chat, a PRIVATE term's login step, an anonymous item 404) never navigate to `/login`. They open the one `features/auth/AuthSheet.tsx` bottom sheet (login and register tabs from `AuthTabs`, shared with `/login`), driven by `features/auth/useAccountGate.ts` (`guard(fn)`, `open(tab)`, closed once a token exists) or by `AuthPromptButtons` for an inline card. Logging in swaps the token in place; the page's token-aware queries refetch. There is no guest sign-up for terms or events and no anonymous-profile merge (removed 2026-11-04).
- **Request proxy** (`src/proxy.ts`, the pure `resolveProxy` plus a matcher that excludes `api/`, `_next/`, `assets/`, `.well-known/`, `favicon.svg` and `icons.svg`), rules in order: `/home` → 307 to `/` (query kept); `/` with an `auth_token` cookie → internal rewrite to `/home`, the visible URL stays `/`; `POST /oauth2/authorize` → rewrite to `${BACKEND_INTERNAL_URL}/oauth2/authorize` (the GET is the Next consent page); a `PROTECTED_PREFIXES` path (`routing/paths.ts`, segment-boundary match) without the cookie → `/login?returnTo=…`. It checks cookie presence only and never verifies the JWT; the client `AuthGuard` stays authoritative. `/api/*` is never matched, because the proxy buffers bodies up to 10 MB and photo uploads reach 15 MB.
- **Session cookie**: `auth/session.ts` keeps the login JWT in localStorage and in the JS-readable `auth_token` cookie (`Path=/; SameSite=Lax`, `Max-Age` from the JWT `exp`, `Secure` on https) in lockstep; every write goes through `setSession`/`clearSession`. The server render uses the cookie for `initialToken`, the proxy rewrite and the gate, and never forwards it to the backend. The backend also accepts it on GET/HEAD (see `standards/backend/security.md`). Client data calls stay relative (`/api`) with the Bearer header from localStorage.
- **Routing facade**: feature code reaches the router only through `src/routing/navigation.tsx`; ESLint `no-restricted-imports` bans `next/navigation`/`next/link` outside `src/routing/`, `src/app/` and the test mocks, and `react-router-dom` everywhere.
- **Reserved slugs**: `routing/reservedSlugs.ts` lists every top-level static segment of the route tree (`home` included); `test/reservedSlugs.test.ts` checks that each is in the backend's `RESERVED_SLUGS` (`app/organizations/slugs.py`).
- **Plugin SDK**: `vite.sdk.config.ts` builds `src/plugin-sdk` as one IIFE into `public/assets/plugin-sdk.js` (git-ignored) on `predev`/`prebuild`; Next serves it with `public/assets/plugin-ui.css` at `/assets/` on :5173.

## Data Flow

```
Client Request → FastAPI Router → Auth Dependency (require_any) → Service Layer → SQLAlchemy (ORM or Core) → PostgreSQL
```

Each route enforces its own requirement through `Depends(require_any(...))` (no dependency for PUBLIC routes). `AUTHORIZATION_MATRIX` in `app/core/authorization_matrix.py` is a reference table of those requirements, verified by `tests/test_authorization_matrix.py`; nothing applies it centrally at request time (see `standards/backend/security.md`).

Page requests take a separate path: browser → nginx → Next (`src/proxy.ts` → root layout → route). Public pages render their metadata and palette from anonymous `src/api/server.ts` reads; the browser then calls `/api` with the Bearer token, through nginx to the backend.

Plugin iframes reach the same routers via the host's browser SDK, which attaches the same JWT the router-level auth dependency validates — there is no separate plugin-specific auth path on the server side (see `standards/backend/plugin-auth.md`).

## Domain clock (Europe/Warsaw)

`Term.occurs_on` is a naive Europe/Warsaw wall clock (unlike the naive-UTC audit columns such as `created_at`). `app/core/clock.py` is the only definition of "now" for Term logic: `clock.local_now()` converts the current UTC instant to Warsaw time through `zoneinfo`, so it never depends on the host or container `TZ`. Call sites use `clock.local_now()` (module attribute access) so the opt-in `freeze_local_now` test fixture reaches all of them. The same module holds the Polish short date formatters and the notification-length cap.

Ops: the `lifespan` startup calls `clock.check_timezone()` before the outbox poller and APScheduler start. It fails with an "install tzdata" error if the zone cannot load, and otherwise logs one line, `Europe/Warsaw (CET|CEST)`. Setting `TZ=Europe/Warsaw` in compose is optional and no code relies on it.

## Photo Upload and Content Moderation

```
POST /api/products/{id}/photos (multipart) → Pillow sanitize → Spaces (private)
      → one transaction under the product FOR UPDATE lock:
          product_photos(PENDING) → COMMIT (listings are left untouched)
                                   ↓ (shared Postgres, polled)
VPS B moderation-cron (group-thing-ai, python -m app.moderation_cron, every 30 s)
      → claim PENDING (FOR UPDATE SKIP LOCKED) → Spaces get → ShieldGemma-2 in-process
      → APPROVED (files public-read, CDN)
      | NEEDS_REVIEW → /api/moderation (ADMIN)   (files private)
      | REJECTED                                 (files private)
      + one moderation_decisions row (source AI, automated)

PUT /api/item-listing-preferences/{item_id} (mode ≠ null) → listed whatever the photo status
```

Two independent flags, both default `false`: `MODERATION_TEXT_ENABLED` (API) and `MODERATION_IMAGE_ENABLED` (API). The API logs both at startup. The old `MODERATION_ENABLED` is ignored (unknown env vars are dropped), so a stale `.env` that still sets it gets photos approved on upload. `MODERATION_IMAGE_ENABLED=true` must be paired with `MODERATION_CRON_ENABLED=true` on VPS B: with the app flag on and the cron off, photos stay PENDING and are hidden from non-owners, although their items can still be listed (an admin can still decide them in the queue); with the app flag off, uploads are APPROVED at once and the cron has nothing to do.

**Text: synchronous and reject-only, in the API process.**
- `app/moderation/text_guard.py` `check_text(field, new, current=None)` runs Bielik-Guard-0.1B (ONNX, 1 intra-op thread) via `asyncio.to_thread` before the write.
- Checked fields: organization name, group name, term description, product name, the shared product description, and a needed item's name and description (checked as product name/description). This includes the resolve/create branch and the `plugin_data` PUT.
- A value is scored only when it changes (normalised comparison with `current`), so untouched legacy text is never re-checked.
- Any category score ≥ `MODERATION_TEXT_REJECT_THRESHOLD` (default 0.8) → 400 with a Polish message and no scores. Model unavailable → 503 (fail-closed).
- With the flag on, the API lifespan loads the model from `MODERATION_MODELS_DIR` (`<dir>/text`), and startup fails if that is impossible.
- No text status is stored and no text goes through the queue: products have no `text_status`/`text_moderated_hash` (migration 0047 marks leftover `moderation.text_requested` events PROCESSED and moves PENDING photos whose event already FAILED to NEEDS_REVIEW; 0048 drops the columns). Old `PRODUCT_TEXT` decisions remain only as audit rows.
- The synchronous contact-info regex rules (`rules.py`, 400) are unchanged.

**Photos: asynchronous, decided by the cron on VPS B.**
- The decision logic lives only in `group-thing-ai` (`app/photo_moderation.py`, `app/moderation_cron.py`; see its README "Photo moderation cron"). The `moderation-cron` compose service (profile `shield`, switched by `MODERATION_CRON_ENABLED`) reads PENDING `product_photos` straight from the shared Postgres and scores them with ShieldGemma-2 in-process. The app sends nothing to VPS B for moderation.
- Every `MODERATION_CRON_INTERVAL_S` (30) it processes up to `MODERATION_CRON_BATCH` (5) photos, oldest first, one at a time. A tick is skipped while the shield is unhealthy, so an outage uses up no attempts.
- Per category: `sexual`/`violence`/`dangerous` score ≥ `MODERATION_IMAGE_REVIEW_THRESHOLD` (0.5) → NEEDS_REVIEW, ≥ `MODERATION_IMAGE_REJECT_THRESHOLD` (0.9) → REJECTED; `weapons` is review-only. The most severe outcome wins. The cron reads these thresholds from its own `.env.cron`; the app has no image thresholds.
- APPROVED makes both files (`w1600`, `w400`) public before the status write. Every other outcome makes both files private first, every time, because an earlier attempt may have left them public.
- **Retry state** is on the photo row (migration 0049): `moderation_attempts` (INTEGER NOT NULL, default 0) and `moderation_retry_at` (naive UTC TIMESTAMP), plus the partial index `ix_product_photos_pending_created_at` on `(created_at, id) WHERE status = 'PENDING'`. Only VPS B writes them.
  - The claim increments `moderation_attempts` and sets a lease in `moderation_retry_at`. The finalize is guarded with `WHERE status = 'PENDING' AND moderation_attempts = :claimed`, so an admin decision or a delete during scoring wins and the cron's result is discarded.
  - A failed attempt is retried after timeout + 30 s·2^(n-1), measured from the failure. After 5 attempts the photo goes to NEEDS_REVIEW with the note "AI unavailable after 5 attempts" and a null-score decision (shown as "No model score" in the admin queue).
  - Every B update sets `updated_at` explicitly, because it is the ORM's optimistic-lock token. A concurrent app update of the same photo (e.g. reorder) can rarely fail with the existing 409 `StaleDataError` response.
- VPS A runs no photo worker: `add_product_photo` writes no outbox event for moderation, and the app has no VPS B client or `MODERATION_AI_*` settings. `MODERATION_IMAGE_ENABLED` is the app's only photo-moderation switch (true = uploads stay PENDING until the cron decides). Leftover `moderation.photo_requested` outbox rows from the old worker are marked PROCESSED by the API poller (no handler).

**Listing is not gated by photo moderation (`app/groups/application/term_item_listings.py`).**
- An item can be listed (Oddam/Zamienię) while its product has a PENDING or NEEDS_REVIEW photo. A new pending photo (`add_product_photo`) or re-pointing an item to another product (`update_item`) leaves existing listings untouched; neither takes a groups hook any more. The earlier publish gate, withdraw on upload/re-point and the one-time `withdraw_unmoderated_listings` cleanup script were removed. Non-owners still see only APPROVED photos, so a listed item may show no photo until moderation finishes.
- **UI flag**: `GET /api/inventory-items/mine` still returns `photos_moderation_pending` per item (one batched `product_ids_with_unmoderated_photos` query). It is informational only.
- **`listing_status` lockstep**: `inventory_items.listing_status` (DRAFT/ACTIVE) mirrors the `item_listing_preferences` row: ACTIVE exactly when a preference exists. `register_item` sets it (optionally creating the preference through the router-injected `on_registered` hook); `set_item_listing_preference` (under an item `FOR UPDATE` lock) and `confirm_transaction` change it only through the flush-only `inventory_bridge.set_item_listing_status`, in the same commit as the preference write. Every listing read stays preference-driven.
- **Taken-list fallback**: when an active reservation's preference was cleared by its owner, `list_my_active_taken_term_item_listings` builds a transient `ItemListingPreference` (never added to the session) from the reservation, so the taker still sees the item and can confirm it.
- **Category tree**: `categories` is a tree (`parent_id`, nullable `external_id`) seeded from the Polish Vinted snapshot `alembic/data/vinted_categories_pl.json`. Products may only use leaf categories (`require_leaf_category` in `app/category/service.py`: 404 unknown, 409 non-leaf); admins add, rename, reorder siblings and delete nodes, but cannot reparent them.
- **Needed items** are plain names (`needed_items.name` plus an optional `description`); since `0068` they no longer point at a product.

**VPS B depends on these columns and privileges.** The least-privilege role `gt_moderation_cron` is created by `group-thing-ai/scripts/moderation_db_role.sql` (column-level grants only). The cron's startup self-check verifies the same list (`REQUIRED_PRIVILEGES` in `group-thing-ai/app/photo_store.py`) and exits non-zero if a column or grant is missing. A migration that renames, drops or retypes any of these columns needs a matching change in both files:
- `product_photos` SELECT: `id, storage_key, content_sha256, status, moderation_attempts, moderation_retry_at, created_at, updated_at`
- `product_photos` UPDATE: `status, moderation_attempts, moderation_retry_at, updated_at`
- `moderation_decisions` INSERT: `id, subject_type, subject_id, content_hash, source, automated, model_id, scores, thresholds, outcome, note, created_at, updated_at`

The cron connects over the VPC with `?ssl=require` (`pg_hba.conf`: `hostssl aj gt_moderation_cron <VPS_B_VPC_IP>/32 scram-sha-256`; the firewall allows 5432 only from VPS B). Its DB and Spaces credentials live only in `.env.cron` on VPS B, which the B `api` service does not load.

**Shared pieces.**
- `app/storage/` — `ObjectStorage` protocol + `SpacesStorage` (boto3); `get_storage()` returns `None` while the `SPACES_*` settings are unset (upload disabled). `storage.objects_delete` outbox events delete files after their rows are gone.
- `app/moderation/` — `ModerationStatus` (PENDING/APPROVED/NEEDS_REVIEW/REJECTED) per photo; append-only `moderation_decisions` audit log (automated rows are written by VPS B); ADMIN queue/decisions router (photos only), which sets the file ACLs on every decision.
- Non-owners see only APPROVED photos.

**Images and deployment.**
- The production API image is the default (last) Dockerfile stage `runtime`. It contains the `ml` uv group and Bielik-Guard, which is exported to ONNX at build time from the gated HF repo, so it needs the secret: `docker build --secret id=hf_token,env=HF_TOKEN src/backend`. Expect about +0.6–0.8 GB RSS per uvicorn process.
- `runtime-dev` (used by compose) has no model and needs no secret, so text moderation is off in dev.
- 0048 is not zero-downtime: any API or worker process from before it fails on every product query once the columns are dropped. Rolling back past 0048: first run `alembic downgrade 0046` **with the new image** (restores the columns; 0047's data changes are not reverted), then deploy the old image.

**Cutover to the VPS B cron.** The app ships as **one combined release**: migration 0049, the taken-list fallback and the UI flag, together with the removal of the old `moderation-worker`. The `group-thing-ai` README ("Cutover") lists the same steps with the full smoke check.
1. **Network and role prepared.** Add the `pg_hba` entry, the VPC listen address with TLS and the firewall rule, and have `moderation_db_role.sql` and a generated password ready. No SQL yet: the script grants columns that only exist after 0049.
2. **VPS B, cron off.** Check that Docker Compose is 2.24 or newer (`docker compose version`); the compose file needs it. Put `.env.cron` in place with `MODERATION_CRON_ENABLED=false` and deploy; a disabled cron exits 0. Check that the B `api` container has no `DATABASE_URL`/`SPACES_*`.
3. **VPS A, app release.** Keep `MODERATION_IMAGE_ENABLED=false` and deploy with `docker compose up -d --remove-orphans`. Migration 0049 runs and `--remove-orphans` removes the old `moderation-worker` container. `--remove-orphans` removes **every** running container that is not defined in the deployed compose file, so first make sure everything that must keep running on VPS A is in that file. **Then** run `moderation_db_role.sql` as the DB owner.
4. **Cleanup.** No longer needed: the cleanup script was removed together with the listing gate.
5. **Enable the cron.** Set `MODERATION_CRON_ENABLED=true` and recreate `moderation-cron`. Its self-check (config, TLS, columns, per-column privileges) must pass.
6. **Smoke test with real Spaces and ShieldGemma.** Re-queue a benign and a borderline test photo as PENDING. The benign one must end APPROVED with public files, the borderline one NEEDS_REVIEW/REJECTED with private files, and each must have one new `moderation_decisions` row.
7. **Only then** set `MODERATION_IMAGE_ENABLED=true` on VPS A and recreate the backend.

**Moderation gap.** From step 3 until step 7 nothing moderates photos: the worker is gone and the cron is either off or only being verified. This is deliberate and safe, because with `MODERATION_IMAGE_ENABLED=false` new uploads are auto-approved, the same as before the release. Keep the gap short.

Rollback: set `MODERATION_IMAGE_ENABLED=false` on VPS A (uploads are auto-approved again) and/or `MODERATION_CRON_ENABLED=false` on VPS B. Migration 0049 is additive, so there is no need to downgrade it. Nothing withdraws listings any more, so there is nothing to restore. If you redeploy an older app image that still contains the old `moderation-worker`, **first** disable the cron (`MODERATION_CRON_ENABLED=false` and recreate, or stop `moderation-cron`) so the two never moderate photos at the same time.

## Page media and appearance (`app/media/`, `features/editor/`)
One moderated image table, `media` (0082), serves every public page: rows belong to a party (`owner_party_id`: a person, or an Organization's **own** party) and are a `LOGO`, `AVATAR` or `COVER` slot (newest APPROVED per slot is public, at most one unmoderated row per slot, `uq_media_one_pending_per_slot`) or one of up to 3 `GALLERY` photos. `app/media/service.py` (ported from the removed `app/organizations/media.py`) reads, uploads, deletes, reorders and sweeps superseded slot rows under a `parties` row lock; callers check ownership first (`organizations/router.py::_require_owned`, the principal's own profile for `/api/people/me/media`). Moderation logs one subject type, `MEDIA`, titled with the Organization's name, else the person's. `organization_media` and `profile_avatars` are gone (0083).
- **Profile appearance**: `user_profiles.page_layout`/`palette_preset`/`primary_color`/`accent_color` (0081), written by `PATCH /api/people/me/appearance` (omitted keeps, `null` clears; bio text-moderated), layouts allowlisted in `app/users/profile_layouts.py` (`BANNER` only; parity with `features/profile-public/layouts/registry.ts`). `GET /api/public/parties/{id}` (public for every account profile, even with nothing listed or planned; 404 only for unknown parties and family members without an account) returns the person as `owner` (their own name, `slug` null; an owned Organization is the separate `organization {name, slug}` link), `logo`/`avatar`/`cover`/`gallery` and the theme; `GET /api/people/me` returns the own `media` in any status.
- **Founding an Organization** (`POST /api/organizations/mine`, first creation only) copies the founder's visible profile media (public slots, non-REJECTED gallery) to the Organization's party with fresh storage keys and the same status (`media.copy_media`); colors and layout stay on the profile.
- **Frontend**: `/<party-id>` renders the profile in its layout and colors (`features/profile-public/layouts/ProfileLayoutRenderer.tsx`: banner, centered avatar, bio, gallery, nearest pickup dates, "Rzeczy użytkownika" with infinite scroll); the owner's gear opens `/<slug-or-party-id>/appearance` (`app/(site)/[slug]/appearance/`, owner-only, `isAppearancePath` login-gated in `proxy.ts`), the shared `features/editor/AppearanceEditor.tsx` with tabs photos, layout+colors and name. On a profile the four Organization layouts are shown locked with an invite to `/organization` (now only the founding form; an owner is sent to the name tab). `/profile` redirects to `/<party-id>`.

## Locations (`app/locations/`)

`app/locations/` is its own bounded context: a person's saved places (`Location`), owned by their PERSON party (`profile.party_id`), used by their items and by the groups (Circles), Terms and events they lead. Since `0080` a place is a **locality** from the TERYT dictionary plus an optional street address (OLX-style); it has no name or notes. Routes: `GET /api/locations/mine`, `POST /api/locations` (201, every POST creates a row — no Google place dedup any more), `PUT /api/locations/{id}` (full replace; `PATCH` was removed and answers 405) and `DELETE /api/locations/{id}` (owner only, soft delete), plus `GET /api/localities`. Migrations `0057_locations`, `0058_group_term_location_capacity` (`location_id`/`capacity` on groups and terms), `0078`–`0080` (runbook "Deploy / rollback for item location (migrations 0078–0080)" below).

- **Locality dictionary** (`Locality`, `LocalityPostalCode` in `app/locations/models.py`; search in `app/locations/localities.py`): `localities` holds every independent TERYT SIMC locality (GUS TERYT SIMC/TERC, stan 2026-01-01) — 54,440 rows, 1,026 TOWN / 53,414 VILLAGE, each with `gmina`, `powiat`, `voivodeship` and a precomputed `name_search` (`fold_polish`: lower case, diacritics and `ł` folded); city districts are folded into their city. `locality_postal_codes` holds 72,245 `(postal_code, locality_id)` pairs derived from the GUGiK PRG address points (free for any use). Both are seeded from gzipped CSV fixtures in `src/backend/alembic/data/` (`localities_pl.csv.gz`, `locality_postal_codes_pl.csv.gz`; sources, licence, hashes and the rebuild command `scripts/build_localities.py` in `localities_pl.README.md`). The 7-character SIMC id is a natural string PK (see `standards/backend/models.md`).
- **Search**: `GET /api/localities?q=&limit=` (`READ`, `limit` 1–20, default 10) → `{results: [LocalitySearchResult], total}`. A `q` shorter than 2 characters returns nothing; a digits query (`32`, `32650`, `32-6`) is a postal-code prefix search (each result carries its `postal_code`), anything else a folded name prefix. Towns first, then exact matches, then name/voivodeship/powiat/gmina/id. Request-validation errors in this app are **400** with `fieldErrors` (`app/core/errors.py`), not 422.
- **Label and loading**: `Location.label` (model property) is the single place label — `"Kęty, małopolskie"` without an address, `"Kęty — {address}"` with one; every response's `label` and every term/event `location_name` comes from it. `Location.locality` is `lazy="raise"`, so every row that is serialised or labelled must come from `service.load_location`/`load_locations_by_ids` (`joinedload` + `populate_existing`), including the reload after create and update; the three `locations_acl` modules delegate to these loaders.
- **Address fields**: `formatted_address` and `source` are nullable together under `ck_locations_address_fields` (no address ⇒ no source, place id or coordinates; an address needs a source). Request shapes: `{locality_id}`, `{locality_id, formatted_address, source: MANUAL}` or `{…, source: GOOGLE, google_place_id, lat, lng}`.
- **Boundary**: `app/groups/infrastructure/locations_acl.py`, `app/events/infrastructure/locations_acl.py` and `app/inventory/infrastructure/locations_acl.py` are their BC's only import of `app.locations`. They validate newly assigned ids against the caller's own active places (404 unknown/soft-deleted, then 403 foreign) and batch-load referenced rows (one `IN` query, soft-deleted rows included so old groups, terms and items still render). None may import its own BC's `..schemas` (import cycle). Groups, terms, events and items store only a plain `location_id` FK.
- **Read shape**: READ-level embeds (`GroupResponse.default_location`, `TermResponse.location`, events) use the narrow `LocationRefResponse` (`id`, `locality`, `label`, `formatted_address`, `google_place_id`, `deleted_at`; no `owner_party_id`, no coordinates). Term and event addresses stay public: context `location_name` carries the full label (user decision). Unchanged ids are not re-validated on save, and the group's own default is never ownership-checked (it may be soft-deleted).
- **CSP**: none is configured today; if a Content-Security-Policy is introduced, allow `script-src https://maps.googleapis.com` and `connect-src https://places.googleapis.com https://maps.googleapis.com` or the address field falls back to manual entry.
- **Inheritance**: `create_term` copies the group's default place and capacity **by value**; later changes to the group default never touch existing terms.
- **Google Places caching**: the backend never calls Google. The browser looks addresses up via Places API (New) (`importLibrary("places")`, session tokens, `src/frontend/src/lib/googleMaps.ts`), biased by the query suffix `"{locality}, {voivodeship}"`, and posts the result. `google_place_id` may be stored indefinitely; `formatted_address`, `lat` and `lng` are cached Google data subject to Google's caching limits, and refreshing them is out of scope (`updated_at` is the cache timestamp). Without `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` (a frontend build arg inlined by `next build`, never committed) the address is typed by hand (MANUAL); the locality never needs Google.

### Item location
Each item has its own pickup place, `inventory_items.location_id` (FK `fk_inventory_items_location_id_locations` without ON DELETE, partial index `ix_inventory_items_location_id`); it replaced the owner-wide `inventories.location_id` from `0075`, which `0080` dropped together with `GET|PUT /api/inventories/mine/location` and the Moje rzeczy pickup-place card.

- **Write**: `POST /api/inventory-items` requires `location_id` — one of the inventory owner's live places, checked through `app/inventory/infrastructure/locations_acl.py` (404 then 403); `PATCH /api/inventory-items/{id}` may move it to another own live place (`null` is refused). A GIFT or SWAP transfer clears it (`ledger._apply_projection`), so the new owner sets their own; LEND/RETURN keep it.
- **Read**: `location_id` is not on `InventoryItemResponse`; `GET /api/public/items/{id}/details` returns it to the owner only, and `null` once the place is soft-deleted (`repository.find_item_live_location_id`).
- **Listing guard** (`term_item_listings.py`): only the **first** listing of a DRAFT item (DRAFT → ACTIVE) without a live location is refused, 409 "Ustaw lokalizację przedmiotu, aby go wystawić". Changing the mode of an ACTIVE listing is never blocked, and soft-deleting a place leaves its items' listings ACTIVE.
- **Personal pickup** is gated by the item's own live place (`inventory_bridge.get_item_live_location_id`): without one `load_personal_context` gives 409 "Właściciel nie ustawił lokalizacji przedmiotu" and `/actions` reports `personal_pickup_available: false`.
- **Privacy** (`item_actions._viewer_location`, `ItemLocationResponse {locality, formatted_address, deleted_at}`): the owner gets the address and `deleted_at`; every other viewer, anonymous included, gets only the locality (`formatted_address` and `deleted_at` null, even for a removed place). Never the place id, label, coordinates or Google place id.

### Event reservations
Items listed by event participants can be taken (GIFT) or swapped (SWAP) for an event, the same way as for a term. Migration `0073_event_reservations` makes `reservations.term_id` nullable and adds `event_id` (FK `fk_reservations_event_id_events` **ON DELETE SET NULL**, partial index `ix_reservations_event_id`). 0073's CHECK `ck_reservations_context` allowed at most one of `term_id`/`event_id` and required exactly one on open (PENDING/CONFIRMED) rows; since `0074` it is only `num_nonnulls(term_id, event_id) <= 1`, because an open row with neither is a personal pickup (see **Product page reservations** below). Rows detached from a deleted event keep both NULL and are always terminal. Runbooks: "Deploy / rollback for event reservations (migration 0073)" and "… for product page reservations (migrations 0074–0077)" below.

- **Write side**: `inventory.service.create_reservation(...)` (and `inventory_bridge.create_reservation`) takes keyword-only `term_id`/`event_id`, at most one of them (none = personal pickup). `POST /api/reservations` stays term-only.
- **`ReservationContext`** (`app/groups/application/reservation_context.py`, `TermContext | EventContext | PersonalContext`): one code path in `term_item_listings` (`take_item`, `propose_item_swap`, `accept_swap_proposal`, `_resolve_transaction_reservations_for_action`) serves all three. The context supplies eligibility (term: `_require_term_eligibility`; event: the author or an active attendee whose party has an account), the date and `has_started`, the notification name/`when` text, `link_path`, the reservation's context column, `allows_visibility` and the `ItemContextResponse` (`kind` TERM|EVENT, `id`, `name`, `starts_at`, `path`, `has_started`; None for a personal pickup). `load_for_reservation` returns `PersonalContext.for_reservation()` for an **open** row with both columns NULL and None for a **terminal** one (its event was deleted). Term behaviour and messages are unchanged.
- **Routes**: takes and proposals go through the unified `POST /api/items/{item_id}/take|propose` with `context {kind: EVENT, id}` (see **Product page reservations**); the old `POST /api/events/{event_id}/items/{item_id}/take|propose` (`event_item_listings.py`) was removed. An event take/propose holds the event `FOR SHARE`, like sign-up; 404 unknown event/item, 403 ineligible taker or owner, 409 once the event has started ("Wydarzenie już się rozpoczęło"), own/unavailable item, mode mismatch or SWAP via take. Accept (`/api/swap-proposals/{id}/accept`) also locks the event `FOR SHARE`; a deleted event gives 409. Confirm/cancel use the existing `/api/reservations/{id}/confirm-transaction|cancel-transaction`.
- **Timing**: take/propose/accept while `clock.local_now() < starts_at`; confirm/cancel from `starts_at` on (before: 409 "Wydarzenie jeszcze się nie rozpoczęło"). `starts_at` is read live, so editing the event moves both gates. Withdrawing an attendance never cancels reservations. Confirm/cancel check the terminal/already-resolved status before loading the context, so a contextless CANCELLED reservation returns 409 `already_resolved`, never 404/500.
- **Import discipline**: `app/groups/infrastructure/events_acl.py` is the only `app.groups` module that reads events, and it imports `app.events.models` only (`app.events.service` imports groups through its own `groups_acl`; importing the service would close a cycle). Inventory never imports `app.events`: its readers reach `events` through Core `table()` refs in `inventory/infrastructure/repository.py`. The `events_acl` reads used by the owner pages are exported through `groups.service` for `app.pages`.
- **Readers**: `ReservationResponse` (`term_id` nullable, `event_id`), `ReservationDetailResponse` (the context date in `term_occurs_on`, plus `event_id`), `ItemStatusResponse` and `AcceptedSwapProposalResponse` (`event_id`, `event_slug`; the latter's `term_id`/`group_id` nullable). Event privacy follows the term rule (non-parties see the date only). Notifications reuse the term kinds (`TERM_ITEM_LISTING_TAKEN`, `ITEM_RESERVED_FOR_PICKUP`, `SWAP_*`, `TERM_CONFIRMATION_NEEDED`) with the event name and `format_term_when(starts_at)`.
- **End-of-event scan**: `term_end_scan` adds an event pass for events whose `starts_at + TERM_END_GRACE` (2 h) falls in the scan window. It is reservation-driven and ignores eligibility and listing preferences, so a withdrawn attendee still gets the prompt: GIFT = open reservations with that `event_id`; SWAP = ACCEPTED, not-yet-notified proposals whose proposer reservation belongs to the event. It reuses `TERM_CONFIRMATION_NEEDED` with `link_path=/{author_slug}/event/{id}`, and each party's swap prompt carries its own `reservation_id` (the outbox listener sets it only when the payload has one, so term prompts are unchanged). The existing markers make it idempotent. Frontend `pendingActions.ts` recognises `/…/event/{id}` links (`termId` null, confirm by `reservation_id`).
- **Delete rules** (`events/service.py::delete_event`, under the event `FOR UPDATE` lock, in order): (1) 409 `EventHasAttendees` while anyone is signed up; (2) 409 `EventHasOpenReservations` ("Wydarzenie już się rozpoczęło i ma otwarte rezerwacje — potwierdźcie lub anulujcie przekazania") when open reservations or swaps exist and the event has started; (3) otherwise `groups_acl.cancel_open_event_reservations` → `groups/application/event_reservations.py` cancels, in the same uncommitted transaction, every PENDING/CONFIRMED reservation of the event incl. both swap legs (`inventory_bridge.cancel_reservations_without_commit`: `FOR UPDATE`, skips terminal rows, releases items to AVAILABLE), sets PROPOSED **and ACCEPTED** proposals to REJECTED (term `cancel_transaction` leaves ACCEPTED alone) and notifies both parties with `RESERVATION_CANCELLED`. The event row is then deleted, `SET NULL` detaches the terminal rows, and one commit ends it. The UI (`EventAuthorCard`) shows "Usuń i anuluj rezerwacje" before start and an `aria-disabled` delete with a hint after start.
- **`RESERVATION_CANCELLED`**: new `NotificationKind` (21 chars in the non-native `VARCHAR(30)` column, no migration), `link_path=/<owner slug>/product/{item_id}` (`groups/application/item_links.py::item_path`), sent to both parties of a reservation or swap cancelled because its event was deleted. `NotificationBell` renders it generically; `pendingActions.ts` derives no action from it.

### Product page reservations, pickup place and item visibility
Reservations start on the item page (`/:slug/product/:id`), not on term or event pages. Migrations `0074` (personal pickups), `0075` (`inventories.location_id`) and `0076` (`item_listing_preferences.visibility`); `0077` indexes pending swap proposals by listed item; runbook "Deploy / rollback for product page reservations (migrations 0074–0077)" below.

- **Personal pickup (`PersonalContext`)**: the third `ReservationContext`, a pickup arranged in chat at the owner's place. A personal reservation has neither `term_id` nor `event_id` and no date window: take/propose/accept are open at any time and confirm/cancel settle at once (`require_open`/`require_ended` are no-ops). Two ways to build it: **create-time** `load_personal_context` (404 unlisted item; 409 "Właściciel nie ustawił lokalizacji przedmiotu" while the item has no live `location_id` — since `0080`, see **Item location**; carries the owner and the item's visibility for eligibility) and **reservation-derived** `PersonalContext.for_reservation()` (field-free, lifecycle methods only). `term_end_scan` is term/event driven, so personal reservations get no end-of-date prompt.
- **Open vs terminal no-context rule** (accepted risk L7, no discriminator column): a row with both context columns NULL is personal while PENDING/CONFIRMED and "event deleted" once terminal; `load_for_reservation` decides by status. This stays sound only because `delete_event` cancels open event reservations before `ON DELETE SET NULL` detaches them; a test pins that no open no-context row survives an event delete. Terminal personal rows read like deleted-event rows in history (non-parties see no context anyway).

## Messaging (`app/messaging/`)

`app/messaging/` is its own bounded context: private text chats between logged-in users. Tables `conversations`, `messages` and `conversation_reads` (migration `0061_messaging`). Routes live under `/api/conversations`: the inbox (`GET ""`), `GET /unread-count`, get-or-create `POST /item`, `/group`, `/term` and `/event`, `GET /{id}`, `GET`/`POST /{id}/messages` and `POST /{id}/read`. Authorization matrix rows 53-54 accept only the login `READ`/`EDIT` permissions, not the OAuth `mcp:read`/`mcp:edit` scopes.

- **Kinds**:
  - `ITEM` is a 1:1 chat between someone asking about an item and its current owner. Asking about your own item returns 409. Creating a new one for a PRIVATE item the caller may not see returns 404 (item visibility gate); existing chats stay accessible.
  - `GROUP` is for the organizer and the active members of a PRIVATE group. It is read-only while the group is PUBLIC.
  - `TERM` is for the organizer and the non-withdrawn attendees of a term.
  - GROUP and TERM chats are read-only once their group is soft-deleted.
  - `EVENT` (`POST /api/conversations/event {event_id}`, migration `0071`; one per event via the partial unique index `uq_conversations_event_id`) is for the event's author and its active attendees. Withdrawing revokes access on the next request, and the chat stays open (never read-only) after the event ends. Deleting the event cascades to the conversation, its messages and read markers.
- **Access computed per request**: no participant table is stored. Every call resolves the caller's right to read or write from current group, term, event and item state, in `application/access.py`. The inbox uses the same audience (EVENT chats listed via `events_acl`: events the party authored or actively attends), and the `/{id}` routes return 404 before 403. Foreign contexts are reached only through `infrastructure/{groups,inventory,users,events}_acl.py`.
- **Read markers**: `conversation_reads` holds one `last_read_at` per party and conversation. `POST /{id}/read` takes a `message_id` and only moves the marker forward. Sending upserts the sender's own marker, and read-only chats can still be marked read. The unread badge counts messages, not conversations.
- **Send ordering**: moderation runs first, outside the lock. The send then takes `SELECT … FOR UPDATE` on the conversation row and stamps `created_at = max(utcnow, last_message_at + 1 µs)`, so commit order equals cursor order. An `after=` poll from the last server-fetched id never skips a row. Sending moves the sender's own marker to their message, so a message that crossed it is shown in the open thread but never counted as unread.
- **Keyset cursor**: `GET /{id}/messages` pages by message id on `(created_at, id)`, 50 per page with `has_more`. `before=` loads older history and `after=` polls for new messages. Both cursors at once, or a cursor from another conversation, return 400.
- **Polling, no push**: the frontend polls. The 💬 badge (`useUnreadMessages`) and the inbox (`useConversations`) poll every 20 s, and an open thread (`useThread`) polls `after=` every 5 s into one cached query. None of them polls in the background.
- **Moderation**: each body goes through `app/moderation/text_guard.check_text(TextField.MESSAGE_BODY, …)`. A rejection returns 400 and writes no row. If the guard is unavailable the send returns 503, and the composer keeps the text.
- **Rate limits**: `application/send_limiter.py` is an in-memory sliding window, like `join_code_limiter`. It allows 30 messages per minute and 20 new ITEM conversations per hour per party, and returns 429 with `Retry-After` when exceeded. Its state is **per uvicorn worker** and resets on restart, so the limits multiply if the app ever runs several workers.

## Search (`app/search/`)

A read-only module behind `/search`, built like `app/pages/`: it owns no table and writes nothing.

- **Layout**: `router/search.py` → `application/search.py` (`search_items`, `search_meetings`) → `domain/` (pure: `ranking.py`, `links.py` with the path f-strings only; the party/group slug rules are the groups ones, re-exported by `infrastructure/groups_acl.py`) and `schemas.py`. Other contexts only through `infrastructure/{groups,inventory,product,category,events,organizations,locations,users}_acl.py` (no media ACL: thumbnails come via product); no ACL imports `..schemas`. Boundary test `tests/test_module_boundaries.py`: only `app/main.py` imports `app.search`, and outside `infrastructure/` it imports only `app.core`, `app.db`, `app.storage` and `app.search`. `tests/test_domain_clock_guard.py` covers `app/search`.
- **Endpoint**: `GET /api/public/search` (PUBLIC via the `^/api/public/.*$` row, `OptionalPrincipal`; an unresolvable token is a guest). Params: `q` (≥2 characters after folding, ≤100; blank or absent is a browse: the newest listed items within the item filters, ranked 0, or only the upcoming terms and events — no groups or organizations — soonest first, with `other_mode_count` the other mode's browse total), `mode` `items|events`, `scope` `mine|all` (default `all`, guests forced to `all`), `category`, `condition`, `offer_type`, `date_from`/`date_to` (terms and events by their date; with a window a group appears only when its next term inside the window exists, and links to it; `date_from` is clamped to now), `page` (≤ 50, deeper is 400), `size` (≤ 100). Every search statement runs under `SET LOCAL statement_timeout = '3s'` (search transaction only, not the engine); a statement it cancels (SQLSTATE 57014) is a 503 `ServiceUnavailableException` „Wyszukiwanie trwa zbyt długo. Spróbuj zawęzić zapytanie.” without cache headers, other database errors stay 500. Guests get `reserved_until: null` (still `reserved: true`). Response `SearchPage {items, total, page, size, other_mode_count}` with kind-discriminated results (`product`, `term`, `event`, `group`, `organization`). `other_mode_count` is the other mode for the same `q` and scope without filters, computed sequentially. `set_personalised_cache_headers(response, principal)` after success.
- **Matching**: `fold_pl()` (0087) folds the query and the indexed text in SQL; `search_vector @@ plainto_tsquery('simple', …)` on products, events and terms (group, organization and place names are joined at query time) and the trigram word-similarity `<%` on folded names, `fold_pl(groups.description)`, `fold_pl(organizations.slug)` and `categories.path_text` (a category matches on `path_text` only, which ends with its folded name; the name still ranks the leaf with weight B); `q` is always a bound parameter. Items start from the listed-items select (R12), add `owner <> viewer`, and rank by in-my-groups, available before reserved, rank, `created_at`; meetings hide past terms and started events and rank by match class, `sort_at`, in-my-groups, rank, kind, id.
- **Statement budget**: at most **7 statements per mode, constant in the number of rows** (statement timeout, viewer, category check, page rows, total, other-mode count, then one batch each for Organizations + thumbnails or display names + places); asserted in `tests/test_search_api.py` and `tests/test_search_acceptance.py`.
- **Categories are public**: `GET /api/categories(/.*)?` is PUBLIC (matrix row 55), the **one PUBLIC read outside `/api/public/`**, so guests can use the category filter; writes stay ADMIN (row 56). Anonymous GETs get `product_count` 0 (no aggregate; the counts only gate the admin tree) and `Cache-Control: public, max-age=60, s-maxage=300`; a principal gets the counts with `private, no-store`; always `Vary: Authorization, Cookie`. `/api/products?search=` uses `icontains(autoescape=True)`, so `%`/`_` in user input are literals.
- **Frontend**: `/search` lives in the `(public)` route group (`app/(public)/search/page.tsx`, outside `(site)`, so no top bar or bottom tab bar), whose layout `components/layout/PublicPageLayout.tsx` (only for public pages) has a header with „Wróć” to Start and, for guests, „Zaloguj się” returning to the current URL; the page renders `SearchView`, rendered on the server too (field, tabs and filters from the URL; results load in the browser behind `SearchResultsSkeleton`). The route's `loading.tsx` is `SearchPageSkeleton` and its `error.tsx` is `SearchPageError` (`features/search/SearchRouteStates.tsx`), whose „Spróbuj ponownie” resets the `search` queries before `reset()`; a failed search request stays inline. It is open to guests (not in `PROTECTED_PREFIXES`). The window scrolls; `useSearchScrollRestore` remembers the scroll on a result click (sessionStorage, keyed by the URL query) and restores it once the cached pages render on return. URL state in `features/search/useSearchUrlState.ts`, `useSearch` (infinite query over `src/api/search.ts`), `resolveSearchView()` in `searchViewState.ts`, `SearchResultCard` per kind, `OtherModeLine`; "nothing found" links to `HuntingCreateView` with `?name=` prefilled.

## Deployment Architecture
- `docker-compose.yml` (repo root) brings up the stack via `docker-compose up`: Postgres 18, the FastAPI backend (port 8080, build context `src/backend/`), `web` (the Next.js server, build context repo root, `BACKEND_INTERNAL_URL=http://backend:8080`) and `frontend` (the stock `nginx:1.27-alpine` image with `src/frontend/nginx.conf` mounted read-only, published on **:5174**) — the full plugin-architecture stack (host app + backend + DB) in one command. `.env.example` lives at the repo root alongside it (moved from `src/backend/.env.example`) since that's where docker-compose looks for a `.env` file by default
- **Topology**: browser → nginx (`frontend`) → `web` (Next) or `backend`. nginx routes `/api/` → backend, `~ ^/oauth2/(token|register|introspect)$` and `/.well-known/` → backend, and everything else (`/`) → `web:3000`, including `/oauth2/authorize` (the GET is the Next consent page; `src/proxy.ts` rewrites the form POST to the backend, which then sees `Host: backend:8080` while the `X-Forwarded-*` headers carry the public values). Every location forwards `Host`, `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`. There is no SPA fallback: the backend serves no pages and returns a JSON 404 for an unmatched GET
- **Web service**: `src/frontend/Dockerfile` builds in three stages (`npm ci`; `npm run build` with the build args `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` (empty = manual place picker) and `BACKEND_INTERNAL_URL` (default `http://backend:8080`, because the `next.config.ts` rewrites are fixed at build time), which also builds the plugin SDK; a node:22-alpine runner with `.next/standalone`, `.next/static` and `public`, `PORT=3000`, `HOSTNAME=0.0.0.0`, `TZ=Europe/Warsaw`, running as `USER node` with `node server.js`). Compose passes `BACKEND_INTERNAL_URL=http://backend:8080` at runtime as well, for `src/proxy.ts` and `src/api/server.ts`. The build context is the **repo root** — not `src/frontend/` — because `src/frontend`'s test suite imports the sibling `plugins/server-sdk.ts` by relative path, so that file must be present in the build context too (see `.dockerignore` at the repo root, which scopes that context down to just `src/frontend/` + `plugins/server-sdk.ts`). `next.config.ts` sets `outputFileTracingRoot`/`turbopack.root` to `src/frontend`, since the repo root has its own `package-lock.json`
- **Dev and ports**: `npm run dev` in `src/frontend` is `next dev -p 5173` (Turbopack). `next.config.ts` rewrites `/api/:path*`, `/oauth2/register`, `/oauth2/token`, `/oauth2/introspect` and `/.well-known/:path*` to `BACKEND_INTERNAL_URL` (server-only, default `http://localhost:8080`), in dev and whenever nginx is not in front; `src/proxy.ts` rewrites the `POST /oauth2/authorize` form. So the dev host is :5173, the compose stack is :5174 (nginx) and the backend is :8080. The backend's CORS default stays `http://localhost:5173`, and plugins load the SDK from `http://localhost:5173/assets/…`, so plugin development runs the host with `npm run dev`
- Individual plugin apps (`plugins/warehouse`, `plugins/box-size`, `plugins/ai-description`) are **not** part of `docker-compose.yml` — they remain standalone dev-server processes per `plugins/CLAUDE.md`'s documented workflow, registered with the host via `PUT /api/plugins/{pluginId}/manifest`
- `backend` builds the model-free `runtime-dev` target with `MODERATION_TEXT_ENABLED` fixed to `"false"`. There is no photo worker service: photo moderation runs only in VPS B's `moderation-cron`, so a local stack with `MODERATION_IMAGE_ENABLED=true` keeps photos PENDING unless that cron is running
- nginx allows request bodies up to 16 MB on `/api/` (photo uploads; the backend caps a photo at 15 MB)
- No CI/CD yet

### Cutover / rollback for the category-tree release (migrations 0064–0069)
The backend runs `alembic upgrade head` on every start (`docker-compose.yml` `backend` command), so deploying the image applies 0064–0069 at once. 0067 and 0069 delete data irreversibly: every needed item and pledge (0067), and every legacy product, inventory item, reservation, swap proposal, item conversation and ledger row (0069). 0068 drops `needed_items.product_id`, so the old and new backend cannot run side by side.

1. Take a `pg_dump -Fc` of the database and verify it (`pg_restore --list` succeeds, dump is non-empty). Keep it off the database host.
2. Confirm the target environment's Spaces bucket and prefix belong to that environment (check that the variables are set and compare the bucket/prefix names only; never print the keys). 0069 queues deletes of every wiped product photo, so a wrong bucket deletes another environment's files.
3. If product photos must survive a rollback, copy the bucket's product photo prefix now (see **Rollback**).
4. Stop the VPS B moderation cron (`MODERATION_CRON_ENABLED=false` or stop the `moderation-cron` service).
6. Deploy frontend and backend together; expect a short downtime while the backend migrates.
6. Verify: 9 root categories and 2286 categories in total (`SELECT count(*) FROM categories [WHERE parent_id IS NULL]`), `alembic_version` = `0069`, and `GET /api/categories` returns the tree.
7. Verify the photo deletes: `SELECT status, count(*) FROM outbox_entries WHERE event_type = 'storage.objects_delete' GROUP BY status` reaches only `PROCESSED`. `FAILED` entries are expected only where Spaces is not configured (e.g. a local stack); anywhere else, find the cause in the backend log.
8. Start the moderation cron again.
9. Smoke test: register an item with a mode; an 11th GIFT listing → 409; registering on a non-leaf category → 409; add a needed item by name.

**If 0069 fails**: each migration commits on its own, so 0064–0068 stay applied, `alembic_version` stays at `0068` and the backend crash-loops on start. Check `SELECT version_num FROM alembic_version`, read the error in the backend log, fix the cause (e.g. a missing category fixture in the image) and restart the backend, which re-runs 0069. If the cause cannot be fixed quickly, restore the dump as below.

**Rollback**: `pg_restore` the dump into an empty database, then deploy the previous image. The previous image cannot start on a database at 0069, and the downgrades of 0067–0069 do not bring data back (0069's refuses while any product exists), so restoring the dump is the only rollback. After 0069 the outbox deletes the wiped photos' files from Spaces (`storage.objects_delete`), so the restored photo rows point at files that are gone unless the product photo prefix was copied before the deploy (step 3); copy it back before starting the previous image.

### Deploy / rollback for the event page release (migrations 0071–0072)
`alembic upgrade head` on start applies both at once. 0071 adds `conversations.event_id` (FK `fk_conversations_event_id_events` ON DELETE CASCADE), the partial unique index `uq_conversations_event_id` (`WHERE kind = 'EVENT'`) and `ix_conversations_event_id`. It also drops and recreates `fk_messages_conversation_id_conversations` and `fk_conversation_reads_conversation_id_conversations` **with ON DELETE CASCADE for every conversation kind**, not only EVENT: deleting any conversation row now silently removes its messages and read markers, where before the FK refused to delete a conversation that had messages. 0072 adds the indexes on `events.author_party_id` and `event_attendances.party_id`. Recreating the FKs takes ACCESS EXCLUSIVE locks on `conversations`, `messages` and `conversation_reads` and validates every existing row; 0071 sets `lock_timeout = '5s'`, so a long-running query on those tables makes the migration fail instead of queueing all chat traffic behind it.

1. Deploy off-peak. Check the table sizes first (`SELECT count(*) FROM messages`, `SELECT count(*) FROM conversation_reads`); at a size where FK validation takes long, split it into `NOT VALID` + `VALIDATE CONSTRAINT` before deploying.
2. Run `SELECT id FROM organizations WHERE slug = 'event'`. `"event"` is now a reserved slug and `/event/...` paths under it become event URLs; if a row comes back, rename that organization's slug before the deploy.
3. Take a `pg_dump -Fc` of at least `conversations`, `messages` and `conversation_reads` (needed for any downgrade, see **Rollback**).
4. Deploy frontend and backend together (the old `/events/:eventId` page links stop working; there is no redirect).
5. Verify: `alembic_version` = `0072`; `\d messages` shows the conversation FK with `ON DELETE CASCADE`; open an event page, sign up while logged in, and open the event chat as the author and as a logged-in attendee.

**If 0071 fails** (typically `lock_timeout` while a query held the tables): each migration runs in its own transaction (`transaction_per_migration=True`), so nothing of 0071 is applied, `alembic_version` stays at `0070` and the backend crash-loops on start. Find and end the blocking query (`pg_stat_activity`) or wait for a quieter moment, then restart the backend, which re-runs 0071.

**Rollback**: prefer an image-only rollback without a downgrade. The previous image ignores `conversations.event_id`, the extra indexes and the cascades, but its `ConversationKind` has no EVENT: its inbox queries filter by ITEM/GROUP/TERM columns and do not list EVENT chats, and loading an EVENT row by id (`/api/conversations/{id}`) fails with a server error. The chats are intact and return when the new image is redeployed. `alembic downgrade 0070` **deletes every EVENT conversation together with its messages and read markers** and restores the non-cascading FKs; dump the messaging tables (step 3) before running it. Downgrading 0072 only drops its two indexes.

### Deploy / rollback for event reservations (migration 0073)
0073 is additive for existing data: `reservations.term_id` becomes nullable, `event_id` is added (FK `fk_reservations_event_id_events` **ON DELETE SET NULL**, partial index `ix_reservations_event_id`) and CHECK `ck_reservations_context` is validated against every existing row (all have a `term_id`, so it passes). `ON DELETE SET NULL` means deleting an event never deletes reservations: `delete_event` first cancels the open ones (see **Event reservations**), then the FK detaches the now-terminal rows, which stay with `term_id` and `event_id` both NULL because `inventory_entries.reservation_id` (the ledger) still references them.

1. Take a `pg_dump -Fc` of the database before deploying (the only lossless way back once event reservations exist).
2. Deploy frontend and backend together; the old frontend cannot render event contexts, and the old backend's `Reservation.term_id` is NOT NULL.
3. Verify: `alembic_version` = `0073`; `\d reservations` shows `event_id`, the SET NULL FK and `ck_reservations_context`; take an item on an event page and confirm it after `starts_at`.

**Rollback**: an image-only rollback (no downgrade) is safe only while no row has `term_id IS NULL`, because the previous image assumes every reservation has a term. `alembic downgrade 0072` is **guarded**: it counts `reservations WHERE term_id IS NULL` (event reservations and rows detached from a deleted event) and, if any exist, raises naming the recovery path instead of dropping data. Recovery: either cancel and purge those event reservations **and the `inventory_entries` rows referencing them** manually (keeping item balances consistent), then re-run the downgrade; or restore the pre-0073 dump from step 1. With no such rows the downgrade drops the CHECK, the index, the FK and the column, then restores `term_id NOT NULL`.

### Deploy / rollback for product page reservations (migrations 0074–0077)
`alembic upgrade head` on start applies all four. Each is small and additive for existing data:
- **0074** (`0074_personal_pickup_reservations.py`) only recreates `ck_reservations_context` as `num_nonnulls(term_id, event_id) <= 1` (under `SET LOCAL lock_timeout = '5s'`, like 0073); no column.
- **0075** (`0075_inventory_location.py`) adds nullable `inventories.location_id`, FK `fk_inventories_location_id_locations` and partial index `ix_inventories_location_id` (`WHERE location_id IS NOT NULL`).
- **0076** (`0076_item_listing_visibility.py`) adds `item_listing_preferences.visibility VARCHAR(10) NOT NULL DEFAULT 'PUBLIC'` (permanent server default, as `0036`), so every existing listing stays public.
- **0077** (`0077_swap_proposals_listing_item_index.py`) builds the partial index `ix_swap_proposals_listing_item_id_proposed` on `swap_proposals(listing_item_id) WHERE status = 'PROPOSED'` CONCURRENTLY (as `0053`), for the pending-proposal lookup of every listing read and take/propose.
0074–0076 run under `SET LOCAL lock_timeout = '5s'`.

1. Take a `pg_dump -Fc` of the database before deploying (the lossless way back once personal pickups, pickup places or PRIVATE listings exist).
2. Deploy frontend and backend together: the old frontend calls the removed take/propose routes and the old `/actions` shape.
3. Verify: `alembic_version` = `0077`; set a pickup place on Moje rzeczy, take an item with "Odbiorę osobiście" and confirm it at once; switch an item to PRIVATE and check it disappears from the public organizer page.

**Rollback**: downgrades run 0077 → 0076 → 0075 → 0074, each in its own transaction, so a refusal leaves the schema at the refusing revision with the later ones already undone.
- **Before any downgrade (or image-only rollback), run both guard counts** and resolve them first: `SELECT count(*) FROM reservations WHERE status IN ('PENDING', 'CONFIRMED') AND term_id IS NULL AND event_id IS NULL` (0074/0075) and `SELECT count(*) FROM item_listing_preferences WHERE visibility = 'PRIVATE'` (0076). Proceed only when both are 0.
- **0077** only drops the index (CONCURRENTLY); no data is lost.
- **0076 is guarded**: it counts `item_listing_preferences WHERE visibility = 'PRIVATE'` and refuses, because dropping the column would silently publish those items. Recovery: (a) the owners clear those listings (`PUT /api/item-listing-preferences/{item_id}` with `{"mode": null}`) or switch them back to PUBLIC, then re-run; or (b) restore the pre-0076 dump.
- **0075 is guarded and lossy**: it first runs 0074's count and refuses with the same recovery steps, so a downgrade below 0074 can no longer drop the pickup places and then stop at 0074. Past the guard it drops the index, the FK and the column, so **every owner's pickup place is lost** (owners must set it again after re-upgrading; personal pickups are unavailable meanwhile).
- **0074 is guarded**: it counts open (PENDING/CONFIRMED) reservations with neither `term_id` nor `event_id` and refuses, since 0073's CHECK would reject them. Recovery is split: (a) the listing owner **rejects** pending personal swap proposals with `POST /api/swap-proposals/{id}/reject` (`cancel-transaction` refuses an unpaired proposer leg); (b) either party **cancels** accepted personal swaps and personal gifts with `POST /api/reservations/{id}/cancel-transaction`; (c) otherwise restore a pre-0074 dump. After a downgrade, **terminal** personal reservations stay with both columns NULL and read as reservations of a deleted event.
- An image-only rollback (no downgrade) has the same hazards without the guards: the previous image ignores `visibility` (PRIVATE items become public) and resolves an open no-context reservation as having no context, so its parties cannot confirm or cancel it. Use it only while neither kind of row exists.

### Deploy / rollback for global search and group description (migrations 0085–0096)
`alembic upgrade head` on start applies all twelve, each in its own transaction:
- **0085** adds `groups.description TEXT NULL` (metadata-only, `lock_timeout` 5s).
- **0086** `CREATE EXTENSION IF NOT EXISTS pg_trgm`; **0087** creates `fold_pl(text)` (`IMMUTABLE PARALLEL SAFE` SQL, Polish letters only, locale-independent).
- **0088–0090** add the GENERATED STORED `search_vector` columns to `products`, `events` and `terms` (`'simple'::regconfig`). Each **rewrites its table under ACCESS EXCLUSIVE** with `lock_timeout` 5s.
- **0091** adds `categories.path_text TEXT NOT NULL DEFAULT ''`; **0092** backfills it with one recursive-CTE UPDATE (`BACKFILL_SQL`); both `lock_timeout` 5s.
- **0093–0096** build the GIN full-text, trigram (0094 on the names and `path_text`, 0096 on `fold_pl(groups.description)` and `fold_pl(organizations.slug)`) and counterparty indexes CONCURRENTLY inside `autocommit_block()`. A failed or interrupted CONCURRENTLY build leaves an INVALID index behind; each revision runs `DROP INDEX CONCURRENTLY IF EXISTS` first, so rerunning `alembic upgrade head` drops the leftover and builds it again.

1. **Pre-deploy legacy-data query** (read-only). The membership primitive assumes every Membership points at a MEMBER role, every Leadership at an ORGANIZATOR role, and that no `group_roles` row has ended. Each count must be **0**; otherwise **stop the deploy** and review the rows:
   ```sql
   SELECT
     (SELECT count(*) FROM memberships m JOIN group_roles r ON r.id = m.from_role_id
       WHERE r.role_type <> 'MEMBER')                   AS memberships_not_member,
     (SELECT count(*) FROM leaderships l JOIN group_roles r ON r.id = l.from_role_id
       WHERE r.role_type <> 'ORGANIZATOR')              AS leaderships_not_organizator,
     (SELECT count(*) FROM group_roles WHERE valid_to IS NOT NULL) AS group_roles_ended;
   ```
2. **pg_trgm privilege check**, as the migration role: `SELECT has_database_privilege(current_user, current_database(), 'CREATE')` must be `t`, or the role is a superuser (`SELECT rolsuper FROM pg_roles WHERE rolname = current_user`). pg_trgm is a trusted extension on PostgreSQL 13+, so CREATE on the database is enough. If neither holds, a DBA runs `CREATE EXTENSION pg_trgm` beforehand (0086 then does nothing).
3. **Size the downtime window**. The backend runs `alembic upgrade head` before uvicorn starts, so `/api` is down (nginx 502, `web` SSR reads return `null`) for the whole run, dominated by the 0088–0090 rewrites:
   ```sql
   SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) AS total_size
   FROM pg_class WHERE relname IN ('products', 'events', 'terms');
   ```
   To keep the old backend serving during the migrations instead, build the new image first (`docker compose build backend`, which leaves the running container on the old image), run the migrations as a one-off with it before swapping it in: `docker compose run --rm backend alembic upgrade head` (the old image ignores the new columns and indexes, see Rollback), then restart the backend on the new image, whose own `alembic upgrade head` is then a no-op. The old backend still waits on each 0088–0090 rewrite: its requests touching `products`, `events` or `terms` block (or time out) until that table's rewrite commits, so run this off-peak as well.
4. Take a `pg_dump -Fc` of the database (group descriptions are the only non-derived data the downgrade drops).
5. **Deploy off-peak**: 0088–0090 rewrite `products`, `events` and `terms`. If one fails on `lock_timeout`, nothing of it is applied, `alembic_version` stays at the previous revision and the backend crash-loops on start; end the blocking query (`pg_stat_activity`) or wait, then restart the backend.
6. Deploy frontend and backend together (the new frontend calls `/api/public/search` and the public `/api/categories`). nginx rate-limits both per client address (`$binary_remote_addr`, 5 r/s, burst 20, 429 with a JSON envelope); if a TLS proxy, load balancer or CDN fronts nginx, add `set_real_ip_from <proxy CIDR>;`, `real_ip_header X-Forwarded-For;` and `real_ip_recursive on;` to `src/frontend/nginx.conf`, or every visitor shares the proxy's single bucket.
7. Verify: `alembic_version` = `0096`; `SELECT extname FROM pg_extension WHERE extname = 'pg_trgm'` returns a row; `SELECT count(*) FROM categories WHERE path_text = ''` = 0; no INVALID index (`SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid` returns no row); `/search?q=…` works logged out and logged in; a group description shows on its group terms page.

**Rollback**: no guarded downgrades. Every downgrade is the exact reverse and loses only derived data (`search_vector`, `path_text`, the indexes, `fold_pl`) plus **every group description** (0085). An image-only rollback works: the previous image ignores the new columns and indexes (but its `GET /api/categories` is no longer public and its search is the mock).
- **Roll-forward after an image-only rollback**: the previous image does not maintain `categories.path_text`, so categories it created or renamed keep an empty or stale path. After re-deploying the new image, re-run 0092's `BACKFILL_SQL` once and check `SELECT count(*) FROM categories WHERE path_text = ''` = 0.
- **Before downgrading past 0086**, check who owns pg_trgm: `SELECT e.extname, r.rolname FROM pg_extension e JOIN pg_roles r ON r.oid = e.extowner WHERE e.extname = 'pg_trgm'`. 0086's downgrade runs `DROP EXTENSION IF EXISTS pg_trgm`, which also removes an extension a DBA installed earlier and anything else built on it; if it predates this release, stop at 0086.
- **Future category seed revisions** must set `path_text` in SQL with `fold_pl()` (re-run 0092's `BACKFILL_SQL` after inserting), never compute it in Python; the category service keeps it in step on create and rename.
- **Changing `fold_pl`** (or switching `search_vector` to a `polish` dictionary) means a new revision that drops and re-adds the generated `search_vector` columns (a table rewrite, off-peak again), re-runs the `path_text` backfill and REINDEXes the `fold_pl(...)` trigram expression indexes; never `CREATE OR REPLACE` the function alone, or stored values and indexes go stale.
